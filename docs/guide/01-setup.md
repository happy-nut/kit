# kit 설정하기

이 장에서는 플러그인을 설치하고, kit 이 쓸 모델을 고르고, 첫 일을 돌린다. 설정은 명령 하나와 짧은 대화다.

## 플러그인 설치

터미널에서 이렇게 친다.

```bash
claude plugin marketplace add happy-nut/kit
```

```bash
claude plugin install dev@kit
```

Claude Code 는 플러그인 명령 앞에 플러그인 이름을 붙인다. 그래서 이 안내서의 명령은 모두 `/dev:setup` 처럼 `dev:` 가 붙어 있다. 서드파티 마켓플레이스는 자동 업데이트가 꺼져 있으니 새 판은 `claude plugin update dev@kit` 으로 직접 받는다.

## 모델 고르기

이렇게 친다.

```text
/dev:setup
```

[`/dev:setup`](../../skills/setup/SKILL.md) 은 쓸 수 있는 모델을 찾고, 추론 예산을 묻고, 역할(코드를 맡는 서브에이전트, 판단, 리뷰 패널)을 하나씩 보여 주고, 무엇을 원하는지 묻는다. 질문에 답하면 된다. 끝나면 `~/.claude/rules/dev-models.md` 를 쓴다. kit 의 모든 스킬이 읽는 작은 규칙 파일이다.

기본값은 `large` 예산과 같다. 코드, 글, 판단은 `opus xhigh` 로 돌고, 리뷰 패널과 swarm 워커는 `high` 로 돈다. 어떤 역할도 `xhigh` 위로 돌지 않는다. 리뷰 패널 밖에서 `fable` 은 내가 그 일에 그 모델을 말했거나, 같은 브리프로 `opus` 를 두 번 돌려 두 번 다 검사를 못 넘겼을 때만 돈다. `medium` 은 역할마다 한 단계, `small` 은 두 단계 내리고, 둘 다 토큰을 덜 쓴다.

신경 쓰는 것만 바꾸면 된다. 규칙에 줄이 없는 역할은 스킬 기본값을 쓴다. 기본값으로 돌리려면 그 역할의 줄을 지운다. `/dev:setup` 을 다시 돌리면 기본값과 다른 모델을 고른 역할은 그대로 둔다. 기본값이 바뀌어도 그 전에 쓴 규칙은 `/dev:setup` 을 다시 돌릴 때까지 옛 기본값을 붙들고 있다. 다시 돌리면 알아보는 옛 기본값을 새것으로 바꾸고, 무엇을 바꿨는지 말하고, 다른 선택은 남긴다. 알아보지 못하는 고정값을 없애려면 먼저 그 역할의 줄이나 파일을 지운다.

부모 대화의 모델을 그대로 쓰고 싶을 수도 있다. 역할을 `inherit-parent` 나 `auto` 로 두면 kit 이 서브에이전트의 `model` 을 빼서 서브에이전트가 부모 대화의 모델을 물려받는다. 두 값은 뜻이 같고, 둘 다 모델 이름이 아니다. 패널 역할의 값은 목록이고 항목 하나에 서브에이전트 하나가 뜨므로, 목록 길이가 패널 인원수다. 설정은 `swarm workers` 도 정한다. 경주가 갈래마다 다른 모델을 정하지 않는 한 모든 `/dev:swarm` 워커의 기본 모델이다.

## 검증 제안은 받아도 되고 안 받아도 된다

설정 끝에 `/dev:setup` 은 프로젝트에서 앱 동작을 증명할 방법을 찾는다. `verify-*` 스킬이나 이미 있는 하네스다. 둘 다 없으면 [`/dev:verify-setup`](../../skills/verify-setup/SKILL.md) 으로 하나 만들자고 한 번 제안한다.

받으면 `.claude/skills/verify-<앱>/` 을 쓴다. 에이전트가 사용자처럼 앱을 몰게 가르치는 프로젝트 전용 스킬이다. 넘기기 전에 그 스킬이 동작하는지 한 번 증명한다. 안 받으면 설정이 다음으로 넘어간다. `/dev:verify-setup` 은 언제든 직접 돌릴 수 있다. 자세한 것은 [검증하고 내보내기](./06-verify-and-ship.md) 에 있다.

kit 이 처음이면 받는다. 자기 일을 확인할 수 있는 에이전트는 확인이 통과할 때까지 계속 간다. 확인할 수 없는 에이전트는 결과마다 나에게 돌려주고 손으로 확인하게 한다. 이 안내서에서 가장 남는 것이 검증 스킬이다.

이어서 프로젝트에 형식 검증 스킬이 없으면 [`/dev:formal-setup`](../../skills/formal-setup/SKILL.md) 으로 하나 만들자고 한 번 제안한다. 테스트는 누군가 써 둘 생각을 한 경우만 확인한다. 형식 검증 스킬은 「작업 하나가 동시에 두 번 돌지 않는다」 같은 코드의 핵심 속성 하나를 정한 범위 안의 모든 경우에서 확인한다. 동시성, 재시도, 상태 기계, 파서가 있어서 버그가 비싸고 깨지는 경우에 테스트가 잘 닿지 않는 코드면 받는다. 아니면 거절하고, 사정이 바뀌면 나중에 돌린다. 이것도 [검증하고 내보내기](./06-verify-and-ship.md) 에서 다룬다.

설정이 끝나면 새 대화를 연다. 모델 규칙은 새 세션부터 적용된다.

## 비용 다스리기

kit 은 서브에이전트와 리뷰 패널에 토큰을 더 쓴다. 엄격함의 값이다. 덜 쓰려면 이렇게 한다.

- `/dev:setup` 을 다시 돌려 더 작은 추론 예산이나 싼 모델을 고른다. 본 대화는 강한 모델로, 코드 역할은 더 싸고 빠른 모델로 두는 것이 좋은 나눔이다.
- 역할을 `auto` 나 `inherit-parent` 로 두어 대화 자신의 모델로 돌게 한다.
- 패널 목록을 줄인다. 항목 하나가 서브에이전트 하나다.

## 첫 일 돌리기

진짜지만 작은 일을 골라 동료에게 말하듯 적는다.

```text
/dev:mode 이 명령에 --json 플래그를 더해. 텍스트 출력은 바이트 하나까지 그대로여야 해. 둘 다 검증해.
```

작업 목록을 본다. 첫 항목들은 고른 플레이북의 단계를 옮긴 것이고, 이 프롬프트라면 기능 플레이북이다.

여기서부터는 평범하게 이어 말하면 된다. kit 은 대화를 열거나, 다시 열거나, 지우거나, 압축할 때마다 mode 본문을 대화에 넣는다. 그래서 `/dev:mode` 를 붙이지 않은 메시지에도 같은 방식이 적용된다. 붙여도 해는 없다.
