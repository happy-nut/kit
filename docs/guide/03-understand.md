# 고치기 전에 코드 이해하기

이해하지 못한 코드를 고치면 미묘한 회귀가 나간다. 나에게도 에이전트에게도 똑같다. 에이전트는 보통 둘 중 하나로 실패한다. 내가 원하는 것을 잘못 읽거나, 일을 제대로 할 맥락이 없다. 첫째는 [프롬프트에 넣을 것](./02-mode.md#프롬프트에-넣을-것) 이 다룬다. 이 장은 둘째를 다룬다.

kit 에는 들어가는 길이 넷 있다. `/dev:how` 는 코드가 지금 무엇을 하는지 설명한다. `/dev:why` 는 왜 그런 모양이 됐는지 이유를 캐낸다. `/dev:why` 의 가르치기는 둘을 엮어 설명 하나로 만든다. `/dev:recall` 은 한 주제에 대한 내 최근 맥락을 다시 세운다. 넷 다 에이전트가 내가 확인할 수 있는 말로 자기 설명을 하게 만든다. 나보다 코드를 더 잘 알 수도 있는 에이전트를 이렇게 감독한다.

## 읽기 전용 조사로 시작한다

원인이 불분명하면 고침이 아니라 찾은 것을 달라고 한다.

```text
/dev:mode 백그라운드 작업이 몇 시간마다 시간 초과로 죽는 이유를 조사해. 아는 것, 쓴 데이터, 가장 그럴듯한 가설을 줘. 아직 코드는 바꾸지 마.
```

「아직 코드는 바꾸지 마」가 이 일을 [조사 플레이북](../../skills/mode/playbooks/investigation.md) 으로 보낸다. 코드를 따라가고, 동기를 묻는 질문이면 `/dev:why` 를 더하고, 출처를 단 설명을 돌려준다. 여러 안 가운데 고르는 일이면 트레이드오프 표를 단 추천을 돌려준다. 「쓴 데이터」를 물으면 에이전트가 증거와 짐작을 가른다. 찾은 것이 고침을 가리키면 고침은 새 일로 시작한다.

## `/dev:how` 로 동작 따라가기

```text
/dev:how 알림 중복은 어떻게 걸러? 구독자를 찾을 때 n+1 이 있어?
```

실제로 가진 질문을 묻는다. [`/dev:how`](../../skills/how/SKILL.md) 는 코드를 읽고, 이 하위 시스템에 나를 들이는 시니어 엔지니어의 수준으로 답한다. 실행 흐름, 핵심 타입, 뻔하지 않은 부분이다. 코드를 탐색하고 설명을 쓰는 읽기 전용 서브에이전트 하나를 띄운다.

## `/dev:why` 로 기록 캐기

```text
/dev:why 재시도 한도를 왜 5로 정했어? 그 이유가 아직 맞아?
```

[`/dev:why`](../../skills/why/SKILL.md) 는 코드가 아니라 기록에서 답한다. 그 코드를 들인 커밋과 PR 토론, 그 뒤의 변경마다의 것을 읽고, 그 자취가 얇으면 다른 출처를 본다. 답은 작성자가 쓴 말을 인용하고, 에이전트 자신의 추론은 추론이라고 표시하고, 기록이 답하지 못하는 것은 그렇다고 말한다. 「아무도 이유를 적지 않았다」도 그 자체로 답이기 때문이다.

둘은 자연스럽게 이어 붙는다. 엉망인 까닭이 기록에 있을 것 같으면 「why 먼저, 그다음 how」가 좋은 프롬프트다.

## 가르치기로 제대로 이해하기

```text
/dev:why 이 PR 이 재시도를 어떻게 바꾸는지 가르쳐 줘. 증상이 아니라 원인을 고친다는 걸 납득시켜.
```

요약으로 모자랄 때는 [`/dev:why`](../../skills/why/SKILL.md) 의 가르치기다. `/dev:how` 와 기록 조사를 돌리고(작은 변경이면 하나만), 찾은 것을 그림 한 장씩 쌓아 가는 평범한 설명으로 엮는다. 「납득시켜」라는 틀은 다시 쓸 만하다. 설명을 둘러보기가 아니라 시험해 볼 수 있는 논증으로 바꾼다.

에이전트 자신의 선택에도 쓴다.

```text
/dev:why 왜 큐가 아니라 이렇게 구현했는지 가르쳐 줘. 무엇을 내주고 무엇을 얻었고, 왜 그랬어?
```

가르치기는 나만큼 에이전트에게도 도움이 된다. 자기 일을 설명해야 하는 에이전트는 코드를 읽고 주장마다 증거를 대야 한다. 자신 있게 말하고 넘어가지 못한다.

## `/dev:recall` 로 내 맥락 다시 세우기

```text
/dev:recall 지난주 내보내기 작업 따라잡게 해 줘
```

[`/dev:recall`](../../skills/recall/SKILL.md) 은 내 최근 대화와 공유 기록(이슈, 지난 고침, 아직 터지는 오류)을 캐서 어디까지 왔고 다음은 무엇인지 브리프로 돌려준다. 내 옛 대화에는 새 에이전트에게 없는 맥락이 있다. 그러니 옛 주제로 새 일을 시작할 때는 먼저 그 맥락을 싣고, 그다음 새 입력을 넘긴다.

```text
/dev:recall 어제 하던 가상화 목록 작업 떠올려 줘. 그다음 이 버그 보고 읽어.
```

특정 대화 하나를 이어 가고 싶으면 `/dev:recall` 이 아니라 아래 세션 이어받기 플레이북이다.

## 세션 이어받기로 앞 일 넘겨받기

다른 에이전트가(또는 지난주의 내가) 브랜치를 하다 만 채로 두었을 때다.

```text
/dev:mode 이 브랜치 넘겨받아. 결정 기록을 읽고, 무엇이 끝났는지 알아내고, 거기서부터 이어 가. 끝난 일은 다시 하지 마.
```

[세션 이어받기 플레이북](../../skills/mode/playbooks/session-pickup.md) 은 앞 자취를 권위 있는 입력으로 다룬다. 브랜치 상태와 결정을 다시 세우고, 재개 지점을 이름 짓고, 모든 것을 처음부터 다시 도출하는 대신 물려받은 주장을 원래 목표에 대어 검증한다.

**함정.** 「어차피 에이전트가 코드를 읽을 것」이라며 이 장의 스킬을 건너뛰지 않는다. 따라가 본 그림 없이 고치기 시작한 에이전트는 처음 그럴듯해 보이는 자리에서 증상을 고치기 쉽다. `/dev:how` 를 먼저 하는 것이 두 번째 버그보다 싸다.
