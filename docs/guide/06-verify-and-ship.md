# 결과를 검증하고 PR 을 연다

「컴파일된다」는 증거가 아니다. [Prove It Works 원칙](../../skills/mode/principles.md#prove-it-works)은 에이전트가 성공을 보고하기 전에 실제 산출물을 확인하게 한다. 내 일은 그 「실제 산출물」을 확인할 수 있게 만드는 것이다. 이 장은 완료 조건을 말하는 법, 잰 숫자를 점검하는 법, 내 앱에 맞는 검증 스킬을 만드는 법, 테스트가 거의 닿지 않는 속성을 형식 검증하는 법, PR 을 여는 법, 그리고 PR 을 머지까지 모는 법을 다룬다.

검증은 에이전트 일 대부분에서 가장 느린 단계다. 보통 사람을 기다리는 단계이기 때문이다. 에이전트가 직접 검증할 수 있게 만들면 내가 병목이 되지 않는다. 건너뛰면 에이전트를 더 돌려도 리뷰할, 확인 안 된 일만 늘어난다.

![시제품 비행기가 실제 시험 코스를 날고, 그녀가 스톱워치로 시간을 재고, 로봇들이 그 비행을 찍으며 체크리스트를 채운다. 터미널에는 verify: pass, evidence: captured 가 떠 있다.](./images/verification.jpg)

## 완료 조건을 처음에 말한다

첫 프롬프트에 「됐다」가 무엇인지 맞는 말로 적는다.

```text
/dev:mode 이 명령에 json 출력을 더해. 텍스트 출력은 바이트 하나까지 그대로고, json 은 파싱되고, 둘 다 샘플 프로젝트에 대고 돌아야 해. 증거를 보여 줘.
```

이제 에이전트에게는 맞춰야 할 기분이 아니라 돌릴 수 있는 검사 셋이 있다. 답이 오면 정확한 명령과 출력이 붙어 있어야 한다. 검사를 돌리지 못했으면 좋은 답은 「결론 불가」라고 말한다. 증거 없이 자신만만한 답은 경고 신호다.

검사를 변경에 맞춘다.

- CLI 변경은 실제 명령을 돌린다.
- UI 변경은 돌고 있는 앱에서 바뀐 흐름을 걸어 본다. 기준과 픽셀 하나까지 맞아야 하면 [시각 동등성 플레이북](../../skills/mode/playbooks/visual-parity.md)이 눈으로 판단하지 않고 동결한 기준선과 스크린샷을 diff 한다.
- 파서나 이전 작업은 저장해 둔 입력을 다시 돌린다.
- 성능 변경은 전과 후 프로파일을 견준다.
- 저장소 변경은 쓴 값을 다시 읽는다.

증명은 내가 직접 볼 수 있는 산출물로 달라고 한다. 실패하던 테스트와 통과하는 테스트, 전과 후 영상, trace, 스크린샷이다. 수정이 이미 머지됐으면 main 에서 같은 검사를 다시 해 달라고 한다. 산출물은 그럴듯한 설명보다 낫다. 실행 전체를 다시 밟지 않고도 따져 물을 수 있기 때문이다.

다 믿지는 못하는 작은 diff 는 [`/dev:review`](../../skills/review/SKILL.md) 가 다른 곳에서 무엇을 깰 수 있는지 찾는다. 변경을 안전하게 만드는 사실 하나를 찾고, 말로 우기지 않고 코드를 돌려 그 사실을 증명한다.

## 잰 숫자는 `/dev:bench` 로 점검한다

전과 후 숫자는 실수로 틀리기 가장 쉬운 증거다. 데워진 캐시, 한쪽만 디버그 빌드, 잰 구간 안에서 한 번도 돌지 않은 일이 저마다 그럴듯한 속도 향상을 만들어 낸다. 숫자를 보고하거나 그에 따라 움직이기 전에 친다.

```text
/dev:bench PR 에 넣기 전에 export 속도 향상을 점검해
```

[`/dev:bench`](../../skills/bench/SKILL.md) 는 질문 일곱 개를 묻고, 저마다 실행에서 나온 증거를 요구한다.

1. 무엇이 숫자를 묶고 있나, 왜 두 배가 아닌가?
2. 모든 쪽이 운영처럼 튜닝돼 돌았나?
3. 결과가 디스크 대역폭이나 코어 수 같은 물리 한계를 넘나?
4. 오류가 났거나 틀린 출력을 돌려준 것이 있나?
5. 번갈아 돌린 실행에서 중앙값과 범위로 재현되나?
6. 사용자가 기다리는 경로에서 처음부터 끝까지 의미가 있나?
7. 일이 정말 잰 구간 안에서 일어났나?

판정은 빨라짐, 느려짐, 측정 가능한 차이 없음, 결론 불가 가운데 하나로, 실행 횟수, 범위, 병목과 함께 온다. 병목을 대지 못하거나 한쪽이 튜닝되지 않고 돌았으면 결론 불가라고 말한다. `/dev:mode` 는 성능 문제와 힐클라임 플레이북 안에서 이미 이 점검을 돌린다. 그러니 직접 치는 것은 그 플레이북 밖에서 무언가를 쟀을 때, 또는 남의 숫자가 너무 좋아 보일 때다. [Explain the Number 원칙](../../skills/mode/principles.md#explain-the-number)을 실제로 돌리는 모양이다.

## 프로젝트 검증 스킬을 만든다

위 UI 항목에는 진짜 요구 사항이 숨어 있다. 에이전트에게는 내 앱을 스크립트로 몰 길이 필요하다. 프로젝트에 이미 있으면 좋다. 없으면 이렇게 돌린다.

```text
/dev:verify-setup
```

[`/dev:verify-setup`](../../skills/verify-setup/SKILL.md) 은 나를 인터뷰하지 않고 저장소를 인터뷰한다. 사용자가 무엇을 만지는지, 로컬에서 앱이 어떻게 뜨는지, 무엇으로 몰 수 있는지, 어떤 증거가 동작을 증명하는지, 인스턴스 두 개가 나란히 돌 수 있는지를 알아낸다. 몰 방법은 이미 있는 장치가 사용자처럼 몰고 사용자가 보는 그대로 관찰하는지 먼저 확인하고, 아니면 브라우저 도구나 CDP, PTY, 평범한 HTTP 를 쓴다. 코드가 답할 수 없는 것만 나에게 묻는다.

결과는 `.claude/skills/verify-<앱>/` 이다. 에이전트가 읽는 지시문으로, Launch, Doctor, Drive, Evidence, Cleanup 절이 정확한 명령으로 채워져 있고, 딸린 스크립트가 있으면 Helpers 절이 붙는다. 그리고 `features/` 아래에 앱이 하는 일과 각 기능이 동작한다는 것을 증명하는 결과를 색인한 기능 지도가 있다. 스킬에는 [기능 지도 예시](../../skills/verify-setup/references/feature-map-example/)가 들어 있다. README 색인 하나와 기능마다 파일 하나이고, 파일마다 정해진 H2 넷을 쓴다. 넘기기 전에 생성기는 만든 스킬을 처음부터 끝까지 한 번 증명한다. 띄우고, Doctor 로 확인하고, 기능 하나를 몰고, 증거를 잡고, 정리한 뒤, 정리 뒤에도 증거가 남았는지 확인한다. 그 증명이 실패하면 결과를 쓰지 않는다.

그때부터 「앱에서 검증해」는 이 저장소에서 어느 에이전트든 준비 대화 없이 실행할 수 있는 단계가 된다. 증명을 특정한 모양으로 받고 싶으면 프롬프트에 이름을 댄다.

```text
/dev:mode 일괄 보관 기능을 만들어. /verify-<앱> 으로 변경을 검증하고 증거로 영상과 스크린샷을 보여 줘.
```

```text
/dev:mode /verify-<앱> 으로 이걸 재현해. main 에서 재현되면 고치고 증거로 영상을 보여 줘.
```

검증 스킬이 돌면 [`/dev:swarm`](../../skills/swarm/SKILL.md) 이 전체 검증을 기능 지도 항목마다 나눠 돌리고 결과를 모을 수 있다. 검증자 스웜은 충분히 큰 표본으로 성능 개선을 확인하거나, PR 을 내보내기 전에 앱을 퍼징해 회귀를 찾기도 한다.

검증 스킬은 한 번 쓰고 버리는 것이 아니라 기반 시설로 다룬다. 커밋해서 팀의 모든 사람과 모든 에이전트가 같은 방법으로 앱을 몰게 한다. 그다음 [지렛대를 만든다](../../skills/mode/principles.md#build-the-lever). 에이전트들이 앱을 눌러 보려고 버릴 스크립트를 계속 쓰면, 스킬이 대신 부를 작은 조종 CLI 를 만들어 달라고 한다. 에이전트가 토큰을 덜 쓰고, 실행마다 되풀이할 수 있게 된다. 에이전트가 잘 쓰는 CLI 는 이런 특징이 있다.

- 얇은 명령 여럿보다, 저마다 실제 일을 하고 서로 엮이는 명령 몇 개.
- 무언가를 망가뜨릴 수 있는 명령마다 `--dry-run` 선택지.
- 기능을 한꺼번에가 아니라 차츰 드러내는 하위 명령.
- 대신 무엇을 하라고 말하는 오류 메시지.
- 풍부한 `--help` 글.
- JSON 같은 기계가 읽는 출력.

그 김에 개발 환경 준비도 되풀이할 수 있게 만든다. 시드 데이터, 시험용 사용자, 그리고 늘 같은 방법으로 환경을 띄우는 명령 하나다.

## 검증 스킬이 사실을 말하게 유지한다

앱은 바뀌고, 기능 지도는 낡는다. 적어도 하루에 한 번 돌린다. 아무도 기억할 필요가 없게 Claude Code 원격 루틴(`/schedule`)에 걸어 두면 가장 좋다.

```text
/dev:verify-setup 검증 스킬 점검해
```

검증 스킬이 이미 있으면 [`/dev:verify-setup`](../../skills/verify-setup/SKILL.md) 은 「유지」 절로 간다. 만든 스킬을 감사한다. 먼저 기능마다 읽기 전용 소스 리더 하나를 병렬로 돌리고, 그다음 지도의 모든 기능을 실제로 모는 패스를 한 번 돈다. 결과는 셋 중 정확히 하나다. `clean` 은 모두 덮였고 내보낼 것이 없다는 뜻이다. `changed` 는 검증 스킬 자기 폴더 안에 한정한, 증명된 수정을 PR 하나로 낸다는 뜻이다. `blocked` 는 무엇이 막았는지 댄다. 제품 코드는 고치지 않는다. 실제로 몰다가 제품 회귀를 잡으면 문서를 고쳐 덮지 않고 회귀를 보고하고 그 저장소에 이슈로 남긴다.

## 형식 검증 스킬로 속성을 증명한다

검증 스킬은 내가 몬 경로를 증명한다. 어떤 버그는 아무도 몰지 않는 경로에 산다. 겹치는 재시도 두 번, 쓰는 도중 끝나는 락, 순서가 뒤바뀌어 도착하는 상태 변화다. 테스트는 그런 경우에 거의 닿지 않는다. 그런 버그가 비싼 코드에는 이렇게 돌린다.

```text
/dev:formal-setup
```

[`/dev:formal-setup`](../../skills/formal-setup/SKILL.md) 은 코드에서 대상을 고른다. 코드가 하는 약속 가운데, 깨지면 사용자가 다치고 그 깨지는 경우에 테스트가 거의 닿지 않는 것이다. 검증하기 가장 쉬운 대상이 아니라 가장 강한 대상을 고른다. 영역이나 버그를 대면 거기서 시작한다.

```text
/dev:formal-setup 작업 임대와 재시도 로직. 작업 하나가 동시에 두 번 돌면 절대 안 돼.
```

질문이 도구를 고른다. 사건이 나쁜 순서로 일어날 수 있는지는 설계의 작은 모델 위에서 도는 모델 검사기가 맞고, 어느 언어든 기본은 TLA+ 다. 코드가 모든 입력에서 맞게 도는지는 코드 위에서 도는 검증기가 맞다. 내 언어에서 도는 검증기가 없으면 에이전트가 그렇다고 말하고, 함수를 손으로 모델링하지 않고 실제 코드를 생성한 입력으로 시험한다. 모든 크기에서 성립해야 하는 속성은 증명이 필요할 수 있다. 에이전트는 어떤 도구를 왜 골랐는지 말해 준다.

속성 하나를 검증하고, 코드를 망가뜨린 변형에서 그 속성이 실패하는 것을 보여 준다. 한 번도 실패하는 걸 본 적 없는 검사는 아무것도 증명하지 않기 때문이다. 지금 코드가 이미 속성을 깨면, 코드의 말로 쓴 짧은 단계 목록으로 반례를 받는다. 속성은 처음 말한 그대로 두므로 발견은 발견으로 남는다. 내가 시키지 않으면 제품 코드는 바뀌지 않는다.

결과는 `.claude/skills/formal-<영역>/` 에 쓴 프로젝트 스킬이다. 다음 에이전트에게 변경이 검증된 코드에 닿는지, 명령 하나로 검사를 어떻게 돌리는지, 진짜 버그와 모델링 오류를 어떻게 가르는지 알려 준다. 넘기기 전에 생성기는 속성을 깨는 임시 변경 위에서 그 스킬을 한 번 따르고, 검사가 그 깨짐을 잡아야 한다. 넘길 때는 무엇을 어떤 도구와 한계로 검증했는지, 검사가 무엇을 찾았는지, 무엇을 덮지 않는지 말한다. 통과는 모델이나 한계를 덮지 시스템 전체를 덮지 않는다.

스킬은 검사마다 덮는 코드와, 검사가 그 코드와 마지막으로 맞았던 커밋도 기록한다. 스킬을 거치지 않은 머지와 리팩터링은 이제 없는 코드를 설명하면서 계속 통과하는 검사를 남길 수 있다. 그런 일 뒤에는 `/dev:formal-setup` 을 다시 부른다. 프로젝트 스킬이 있으면 「유지」 절로 가서, 코드를 보고 검증을 고치고, 다시 돌리고, 고친 검사마다 아직 실패할 수 있음을 보이고, 실패마다 검증의 어긋남인지 코드의 버그인지 말해 준다.

## 동작을 상태 차트로 보여 준다

모델의 말로 쓴 반례는 나를 납득시킨다. 그 동작을 책임지는 PM 이나 디자이너는 자기 말로 봐야 한다. 이렇게 돌린다.

```text
/dev:statechart 사용자가 오프라인에서 노트를 고칠 때 무엇을 보는지
```

[`/dev:statechart`](../../skills/statechart/SKILL.md) 는 사용자가 보는 것을 Mermaid 상태 차트로 그린다. 차트는 TLA+ 모델에서 생성되므로 그림과 검사한 모델이 어긋날 수 없다. 읽는 사람의 규칙(「오프라인인 동안에는 절대 동기화됨이 보이지 않는다」)이 불변식이 된다. 차트는 규칙을 깨는 상태마다 표시하고, 보고서는 그 상태로 가는 가장 짧은 경로를 읽는 사람의 말로 준다. 넘기기 전에 에이전트는 버그 경로마다 실제 코드에서 재현한다. 그래야 모델링 오류가 버그인 척 읽는 사람에게 가지 않는다.

## PR 을 연다

```text
/dev:mode PR 열어. 작고 순서 있는 커밋으로, 증거는 설명에.
```

[PR 열기 플레이북](../../skills/mode/playbooks/opening-a-pr.md)은 워크트리에서 일하고, 홀로 착지할 수 있는 작은 커밋으로 rebase 하고, diff 를 정리하고, 본문에 1분짜리 브리핑을 쓰고, PR 을 리뷰 준비된 상태로 연다. 브랜치를 키우는 것보다 후속 PR 을 쌓는 것이 낫다.

## Babysit 으로 PR 을 머지 준비까지 몬다

열린 PR 에는 곧바로 막힘이 쌓이기 시작한다. 검사가 실패하고, 리뷰어가 코멘트를 달고, trunk 가 움직인다. 그 뒤치다꺼리는 [Babysit 플레이북](../../skills/mode/playbooks/babysit.md)에 넘긴다.

```text
/dev:mode 이 PR 돌봐 줘. 초록으로 만들어.
```

Babysit 은 GitHub 에서는 `gh pr checks --watch` 로, Origin CLI 가 저장소를 풀면 그것으로 PR 을 지켜보며 막힘을 차례로 다룬다. 충돌, 그다음 리뷰 스레드, 그다음 CI 다. rebase 도 force-push 도 하지 않는다. 충돌이나 낡은 base 는 rebase 가 필요한 브랜치를 적어 나에게 돌려준다. 코멘트 분류는 의심하면서 한다. 사람과 봇이 진짜 지적과 잡음을 같은 목록에 올리기 때문이다. 진짜 지적은 고치고, 잡음은 스레드에 반증을 달아 닫는다. 상태만 알고 싶으면 더 작게 물으면 된다. Babysit 은 `check` 모드로 한 번 보고 루프를 시작하지 않고 답한다.

```text
/dev:mode PR 123 확인해 줘. 남은 거 있어?
```

Babysit 은 머지 준비에서 멈춘다. 모든 것이 초록이어도 머지하지 않는다. 머지는 다른 결정이기 때문이다.

## Shipping 으로 스택을 착지시킨다

초록이 안전과 같지는 않다. 착지시킬 준비가 되면 그렇게 말한다.

```text
/dev:mode 스택 착지시켜.
```

[출시 플레이북](../../skills/mode/playbooks/shipping.md)은 무엇이든 걸기 전에 PR 마다 따로 검증한다. PR 하나에 새 에이전트 하나가 동작을 실제로 돌려 증명하고, 변경을 판정하는 에이전트는 결코 그 변경을 쓴 에이전트가 아니다. 판정은 `PASS`, `PASS+NOTES`, `FAIL` 가운데 하나다. 그다음 맨 아래부터 이어진 검증 구간만, 기본은 GitHub 로, Origin CLI 가 있으면 그것으로 한 번에 PR 하나씩 착지시키고, 사슬을 끊는 첫 PR 을 보고한다. 검증 안 된 PR 위에 있는 검증된 PR 은 기다린다. 그것을 머지하면 그 빈틈이 아래로 딸려 들어오기 때문이다.
