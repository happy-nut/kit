# 내 것으로 만든다

`/dev:mode` 는 한 사람의 방식이다. 그 아래의 플레이북, 라우팅, 모델 역할은 내 방식으로도 똑같이 잘 돈다. 이 장은 내 방식을 모드에 담기, 한 세션의 교훈 거두기, 에이전트가 실수를 되풀이하지 않게 저장소 고치기, 초점이 분명한 스킬 쓰기, 스킬 변경을 믿기 전에 시험하기를 다룬다.

생각보다 작게 시작한다. 첫날부터 스킬이 많을 필요가 없고, 이 플러그인 전체도 필요 없다. 평범하게 프롬프트를 쓰고, 에이전트가 어디서 틀리는지 보고, 같은 실패가 두 번 나오면 스킬이나 검사를 더한다.

## 내 방식을 모드에 담는다

```text
/dev:reflect 나를 자동화해
```

내 방식을 설명하지 않는다. [`/dev:reflect`](../../skills/reflect/SKILL.md) 의 「내 방식 캐기」가 기록에서 읽어 낸다. 현재 작업 폴더의 최근 대화 기록에서 되풀이되는 선호를 캔다. 답의 모양, 위임, 검증, 코드, 글, 진행 방식이다. 그다음 어느 영역이 정말 나다운지 한 번 묻는다. 결과는 새 모드 스킬이 아니라 kit(또는 내 포크)의 `skills/mode/SKILL.md` 와 해당 스킬의 수정이다. 고친 글을 [`/dev:write`](../../skills/write/SKILL.md) 기준으로 다시 읽고, 워크트리에서 PR 을 연다. 다른 변경처럼 리뷰하면 된다.

습관이 바뀔 때마다 다시 돌린다.

```text
/dev:reflect 모드 갱신해. 마지막 수정 뒤로 쌓인 거 전부.
```

갱신은 `skills/mode/SKILL.md` 가 마지막으로 바뀐 뒤의 기록만 캔다. 반박되지 않은 규칙은 지키고, 새 근거가 있는 규칙은 고치고, 새 패턴에만 절을 더한다.

## 한 세션의 교훈을 거둔다

뭔가를 배운 일을 막 끝냈으면 바로 부른다.

```text
/dev:reflect 이거 너무 오래 걸렸어. 다음엔 되풀이하지 않게 배운 걸 남겨.
```

[`/dev:reflect`](../../skills/reflect/SKILL.md) 는 대화 기록을 읽고, 앞으로의 에이전트가 일을 다르게 하게 만들 교훈만 남겨 제안을 `Accepted`, `Rejected`, `Backlog` 로 나눈다. `Accepted` 의 스킬 수정은 내 승인을 기다린다. `Backlog` 는 승인 없이 이슈로 바로 등록된다. 미래의 결정을 바꿀 제안만 승인한다. 이상했던 세션 하나는 일화지 규칙이 아니다.

## 환경을 고친다

같은 실수로 에이전트를 자꾸 고치고 있다면, 고칠 곳은 다음 프롬프트가 아니라 저장소다. 얼마나 잘 버티는지로 선택지를 줄 세운다.

1. 구조나 더 나은 자료 구조로 실수를 불가능하게 만든다.
2. 타입으로, 또는 오류가 고칠 길을 이름으로 알려 주는 린트나 CI 검사로 막는다.
3. 테스트로 잡는다.
4. 문서나 에이전트 규칙으로 적는다. 에이전트가 규칙을 건너뛰어도 아무것도 실패하지 않으니 이것이 마지막이다.

사람의 리뷰는 목록에 없다. PR 마다 같은 실수를 잡아야 하는 리뷰어가 바로 이것이 고치는 문제다. [`/dev:correct`](../../skills/correct/SKILL.md) 가 그 일을 한다.

```text
/dev:correct 에이전트가 자꾸 저장소 계층을 안 거치고 데이터베이스 클라이언트를 바로 불러
```

최근 커밋, 되돌린 커밋, 리뷰 코멘트, 우회를 변명하는 주석을 읽고 실수를 군으로 묶는다. 두 번 일어난 군부터 센다. 가장 잦은 군부터 군마다 커밋 하나로, 통하는 가장 높은 층에서 고치고, 새 검사가 실제 과거 실수에서 실패함을 증명한다. 에이전트 지시 파일에는 규칙마다 그것을 강제하는 수단을 짝지은 표를 둔다. 그래서 아무것도 강제하지 않는 규칙은 되풀이로 드러난다. 답은 군마다 증거, 고른 층, 더 높은 층이 왜 안 됐는지를 적는다.

인자 없이 부르면 기록에서 군을 스스로 찾는다. `/dev:reflect` 와 `/dev:correct` 는 일을 나눈다. `/dev:reflect` 는 한 세션에서 스킬을 낫게 한다. `/dev:correct` 는 실수 군이 돌아오지 못하게 저장소를 바꾼다. 고침이 새 경계라면 `/dev:design` 과 짝지어 쓴다. [여러 일을 나란히 돌린다](./07-overnight.md#여러-일을-나란히-돌린다)에 저장소 전체에서 둘을 함께 하는 프롬프트가 있다.

## 초점이 분명한 스킬을 쓴다

담고 싶은 작업 흐름을 이미 알 때 쓴다.

```text
/dev:mode 이 저장소에서 데이터베이스 마이그레이션을 검증하는 스킬 써 줘
```

스킬 쓰기는 [스킬 쓰기·고치기 플레이북](../../skills/mode/playbooks/authoring-a-skill.md)에 맞는다. 이 플레이북은 `skill-creator` 스킬로 쓰고, frontmatter 와 링크를 검사하고, PR 열기 플레이북으로 결과를 내보낸다. 에이전트가 읽는 글은 사람이 읽는 글보다 기준이 높다. 쓸모없는 문장 하나가 미래의 어떤 에이전트가 따를 지시가 되기 때문이다. `SKILL.md` 를 손 가는 대로 쓰지 말고 플레이북이 그 기준을 지키게 둔다.

특별한 경우 둘은 따로 만드는 스킬이 있다. 앱을 몰아 동작을 증명해야 하는 스킬은 검증 스킬이니 [`/dev:verify-setup`](../../skills/verify-setup/SKILL.md) 을 쓴다. 만들기와 유지가 그 안의 두 절이다. 모델 검사기, 증명, 다른 검증 도구로 코드의 속성을 검사하는 스킬은 형식 검증 스킬이니 [`/dev:formal-setup`](../../skills/formal-setup/SKILL.md) 을 쓴다. 이것도 만들기와 유지 두 절이다. [검증하고 내보낸다](./06-verify-and-ship.md)가 둘 다 다룬다.

## 문서를 기준대로 쓴다

내보내는 글은 스킬만이 아니다. 문서, RFC, README, PR 설명, 커밋 메시지에는 이것을 쓴다.

```text
/dev:write README 바뀐 거 리뷰해 줘
```

[`/dev:write`](../../skills/write/SKILL.md) 는 겹겹의 기준을 적용한다. 목표는 피곤한 엔지니어가 한 번에 이해하는 한국어 글이다. 먼저 문서의 갈래(튜토리얼, 하우투, 참조, 설명)를 고르고, 그다음 문장 하나하나를 본다. 누가 무엇을 하는지, 한 문장 한 생각, 두 가지로 읽히는 문장 없음. AI 티(번역체, 상투어, 명사화, 긴 대시)도 걷어낸다. 나나 에이전트가 방금 쓴 것을 리뷰하는 데 쓰거나, 문서를 부탁할 때 처음부터 이름을 댄다.

## 스킬 변경을 가리고 시험한다

스킬 편집은 앞으로의 모든 세션에 영향을 주니, 실험답게 시험한다. 남의 스킬을 들일 때도 마찬가지다. 내 일에서 에이전트를 정말 낫게 하는지 확인한 뒤에 남긴다.

```text
/dev:mode 이 스킬 변경에 eval 플레이북 돌려. 두 변형에 같은 과제를 주고, 후보끼리는 모르게 해.
```

스킬이 자꾸 놓치고 무엇을 해야 하는지 안다면, 고치기와 시험을 한 일로 한다.

```text
/dev:mode 리뷰 스킬이 빠진 마이그레이션을 짚게 고치고, 그 변경을 eval 해.
```

eval 을 처음부터 같이 청하면 편집이 정직해진다. 나빴던 세션 하나에서 쓴 고침은 그 세션에 과적합되기 쉽고, 편집이 쌓이면 스킬이 표류한다. eval 이 그 표류를 내보내기 전에 잡는다.

[평가 플레이북](../../skills/mode/playbooks/eval.md)은 한 가지 실패, 관찰자 효과를 중심으로 짜였다. 평가받는 줄 아는 에이전트는 다르게 행동한다. 그래서 후보 에이전트는 정화된 디렉터리에서 자연스러워 보이는 과제를 받고, 「eval」이나 「candidate」 같은 낱말을 보지 못하고, 서로가 있다는 것도 모른다. 심판 한 명이 모든 출력을 중립 라벨로 채점하고, 사슬을 따랐는지는 후보의 주장이 아니라 실제로 읽은 파일로 채점한다.

판정을 받아들이기 전에 출력을 모두 직접 읽는다. 심판과 의견이 다르면 내 판단보다 채점 기준을 먼저 의심한다.

## 루틴을 깨우는 화면을 만든다

상황에 따라 쓰는 스킬이 하나 있다. [`/dev:bot-ui`](../../skills/bot-ui/SKILL.md) 는 버튼을 누르면 Claude Code 원격 루틴을 API 트리거로 깨우는 작은 페이지를 만든다. 예를 들어 리뷰 대기열을 넘기며 넘길 때마다 루틴이 그 항목을 처리하게 할 수 있다. 이 컴퓨터의 로컬 서버가 루틴 토큰을 들고 있어서 토큰은 브라우저에도 대화에도 가지 않는다. 페이지를 Tailscale 로 여는 법도 다룬다.

**함정:** 스킬이 말을 안 듣는다고 일 도중에 고치지 않는다. 따로 PR 로 고치고 하던 일은 계속 간다. 기능 작업에 엉켜 나간 스킬 편집은 리뷰에서 보이지 않고 평가할 수도 없다.
