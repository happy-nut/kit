# kit 안내서

kit 은 에이전트를 하나하나 지시하지 않을 때 가장 잘 돈다. 원하는 것과 됐는지 확인할 방법을 말하면 된다. `/dev:mode` 가 플레이북을 고르고, 단계에 필요한 다른 스킬을 부르고, 증거를 보여 준다. 이 안내서는 실제로 칠 법한 프롬프트로 그 습관을 가르친다.

이런 것을 배운다.

1. [kit 설정하기](./01-setup.md). 플러그인을 설치하고 모델을 고른다.
2. [`/dev:mode` 로 일 보내기](./02-mode.md). 목표를 주고 플레이북을 고르는 것을 지켜본다.
3. [코드 이해하기](./03-understand.md). 무엇이든 고치기 전에 읽기 전용 조사, 그리고 `/dev:how`, `/dev:why`, `/dev:why` 의 가르치기, `/dev:recall`.
4. [변경 설계하기](./04-design.md). 코드가 모양을 굳히기 전에 `/dev:design`, `/dev:swarm`, `/dev:review`, 시제품, 계획.
5. [변경을 짓고 다듬기](./05-build-and-clean.md). 짓는 플레이북, `/dev:tdd`, `/dev:write`, `/dev:no-comments`.
6. [검증하고 내보내기](./06-verify-and-ship.md). 실제 앱에서 동작을 증명하고, 테스트가 잘 닿지 않는 곳은 형식 검증하고, 숫자는 `/dev:bench` 로 점검한 뒤, 초점이 분명한 PR 을 열어 머지까지 몬다.
7. [자는 동안 일 돌리기](./07-overnight.md). 루프보다 신뢰가 먼저다. 밤샘 계약, 감사할 수 있는 결정 기록, 에이전트 하나를 넘어서는 여러 세션과 루틴.
8. [원칙 이름으로 방향 잡기](./08-principles.md). 일하는 도중의 에이전트 방향을 바꾸는 이름 24개.
9. [내 것으로 만들기](./09-make-it-yours.md). 나만의 모드, 되풀이되는 실수를 막는 `/dev:correct`, 스킬 변경을 시험하는 법.
10. [레시피와 함정](./10-recipes-and-pitfalls.md). 베껴 쓸 프롬프트와 피할 실수.

처음에는 차례대로 읽는다. 그 뒤로는 장마다 따로 읽어도 된다.

막히거나 어느 스킬이 맞는지 모르겠으면 질문과 함께 [`/dev:help`](../../skills/help/SKILL.md) 를 친다.

```text
/dev:help 이 브랜치를 리뷰하려면 어떤 스킬을 써야 해?
```

답을 주고, 보낼 프롬프트 하나를 건네고, 답이 나온 스킬이나 안내서 장을 링크한다. 일을 시작하지는 않는다. kit 실행은 토큰을 실제로 쓰니 준비되면 직접 프롬프트를 보낸다. 직접 칠 때만 돈다.

## 하나만 기억한다면

목표와 그것을 확인할 방법을 내 말로 준다.

```text
/dev:mode 실행 도중에 재시도가 끼면 내보내기가 같은 행을 두 번 쓴다. 먼저 재현하고, 그다음 고치고 검증해.
```

플레이북 이름을 대거나 스킬을 늘어놓을 필요가 없다. 「먼저 재현」과 확인할 수 있는 결과만 있으면 `/dev:mode` 가 길을 정한다. 버그 수정 플레이북을 고르고, 그 단계를 작업 목록에 옮기고, 단계마다 맞는 스킬을 부른다.
