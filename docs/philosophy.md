# 철학: high trust 루프

kit 이 끝내 도달하려는 이상이다. 판단이 갈리면 이 이상에 더 가까워지는 쪽을 고른다. 출처는 Lauren Tan 의 강연 「All Code Is Slop (Except Mine)」(AI Engineer, 2026-11, https://youtu.be/O_zcc6Xl12g)이다. 아래는 강연을 옮겨 정리한 것이고, 숫자는 강연자 팀의 것이다.

## 이상

에이전트에게 맡긴 일이 기본적으로 좋게 나온다. 그래서 사람은 코드를 리뷰하지 않고 검증 산출물(영상, 스크린샷, 그림, 형식 검증 결과)만 본다. 에이전트가 자기 PR 대부분을 직접 머지한다. 결국 리뷰할 것이 남지 않는다. 속도를 크게 올려도 품질은 유지되거나 좋아진다.

이 신뢰는 맹목이 아니다. 에이전트가 일하는 환경(코드베이스, 검사, 검증 장치)에 투자해서 얻는다. 에이전트를 믿는 것이 아니라 에이전트가 잘못하기 어려운 환경을 믿는다.

## 이상에 닿았는지 아는 신호

- **되돌림이 적고 안정적이다.** 강연자 팀은 한 달에 PR 11,000개를 내면서 되돌린 PR 비율이 약 0.5% 로 유지됐고, 비율은 오히려 낮아졌다.
- **교정이 장치로 들어간다.** 교정할 때마다 결정적 검사가 하나 늘고, 리뷰 때 살필 것이 하나 준다.
- **리뷰가 산출물 보기로 줄었다.** 사람이 diff 를 읽지 않고 검증 산출물로 판단한다.
- **토큰 대부분이 검증에 쓰인다.** 강연이 인용한 사례는 하루 토큰의 70% 를 검증에 썼다.
- **속도와 품질이 같이 간다.** PR 수와 배포 주기가 늘어도 성능 지표(시작, 입력, 화면 전환)가 나빠지지 않고 좋아진다.

## 거기로 가는 길: 신뢰 피라미드

투자할 곳을 강한 것부터 늘어놓은 역피라미드다. 위 두 층은 결정적이고, 아래로 갈수록 판단이 끼어든다.

1. **코드 자체.** 좋은 API, 아키텍처, 디렉터리 구조로 잘못된 길이 아예 없게 한다.
2. **결정적 검사.** 린트, 타입, 컴파일러, 테스트. 1층과 함께 에이전트가 기본값으로 옳은 일을 하게 강제한다.
3. **검증.** 런타임 검증과 형식 검증으로 버그를 찾고 불변식을 확인한다. 에이전트가 목표와 의도를 이해했는지도 여기서 드러난다.
4. **산문.** 규칙, 스킬, `AGENTS.md`. 판단이 필요한 것만, 맨 마지막에 조금.

### 코드베이스는 정원이다

- 에이전트의 출력은 입력을 따른다. 코드베이스가 가장 큰 입력이다.
- 코드는 이제 하루에 몇 개가 아니라 수백 개씩, 거의 흐름처럼 들어온다. 사람의 일은 정원 가꾸기에 가까워진다. 제약과 가드레일이 새 코드가 자라는 뼈대다.
- 우회, 안티패턴, 옛 API, 기술 부채는 「기존 패턴」처럼 보여서 다음 에이전트가 베낀다. 잡초처럼 퍼진다. 코드베이스를 깨끗하게 유지해 에이전트가 좋은 것만 베끼게 한다.

### 교정은 장치로 만든다

- 에이전트를 교정할 때마다 규칙 글을 한 줄 더하지 말고 결정적 검사로 만든다. 코드에 있는 규칙이 다시 돌릴 수 있고 믿을 수 있다.
- 더 좋은 것은 문제를 범주째 없애는 것이다. 미묘하게 써야 하는 API 는 에이전트가 잘못 쓴다(예: React 의 `useEffect`). 제품 코드에서 금지하고, 감싼 API 한 곳에서만 쓰게 한다. 그러면 리뷰에서 다시 볼 일이 없다.
- 디렉터리 구조로 맥락을 준다. 섞이면 안 되는 코드(예: Electron 의 main 과 renderer)를 최상위 폴더로 나누고, 둘 사이 import 를 의존성 분석기와 린트로 막는다.
- 린트 오류 메시지는 우회가 아니라 근본 원인을 고치라고 이름으로 알려 준다.
- 새 발생은 린트로 먼저 막고, 옛 발생은 그다음에 치운다.
- 이걸 충분히 하면 리뷰할 것이 줄고, 어느 순간 남지 않는다.

### 주석과 글은 탈출구가 된다

- 에이전트는 문서, 주석, 규칙 글에 「옳은 일을 하지 않은 변명」을 적는다. 강연의 예에서는 구조 충돌을 타이머(`setTimeout` 등)로 덮고, 그게 왜 정당한지 주석으로 적었다. 그 패턴이 퍼져 앱이 느려졌다.
- 작은 교정 하나를 절대 규칙처럼 과하게 따르기도 한다.
- 주석은 쉽게 낡고, 사람은 읽지 않고, 무엇보다 강제할 수 없다. 그래서 주석 대부분을 금지한다.

### 검증이 리뷰를 대신한다

- **런타임 검증.** 에이전트가 코드를 직접 돌리고, 사람이 쓰는 디버깅 도구(브라우저 개발자 프로토콜 등)를 쓰게 한다.
- **기능 지도.** 사용자 눈으로 본 앱의 기능 목록이다. 「왼쪽 사이드바의 그거」처럼 말해도 에이전트가 짐작하지 않게 하는 공유 어휘다.
- **재사용하는 도구.** 앱을 모는 CLI 와 드라이버를 스킬에 넣어 매번 다시 쓴다. 토큰이 줄고 그 도구 자체를 시험할 수 있다.
- **형식 검증.** 여러 기기에 걸친 사용자 흐름은 TLA+ 로 모델 검사하고, 알고리즘의 성질은 Lean 으로 증명한다. 사용자 눈으로 본 상태 차트는 영상, 스크린샷과 나란히 리뷰하기 쉽다.
- **속성 기반 UI 테스트.** 사람이 생각 못 한 순서로 눌러 본다.
- 어느 것도 은탄환이 아니다. 피라미드의 한 층이다.
- 이 도구들은 새것이 아니다. 예전에는 쓰고 유지하기 비싸서 못 썼을 뿐이다. 에이전트가 그 비용을 크게 줄였다. 시험과 검증의 황금기다.

### 공장보다 기초가 먼저다

- 안쪽 코딩 루프가 slop 을 내면, 그 루프를 자동화해도 slop 만 늘고 토큰만 더 든다.
- 그래서 자동화(소프트웨어 공장) 전에 코드베이스, 정적 분석, 런타임·형식 검증에 먼저 투자한다. 이 일은 어차피 자동화의 전제다.
- 기초가 서면 공장은 그 위에 쉽게 선다. 예: 새 판을 낼 때마다 앱 전체를 실제 사용자처럼 몰아 버그를 찾고, 버그마다 수정 PR 을 열고, 자동으로 머지한다. 코드베이스가 좋아서 PR 이 기본적으로 좋기 때문에 가능하다.
- 강연자는 이 상태에 닿는 데 여섯 달이 걸렸다.

## kit 에 박힌 자리

| 이 문서의 생각 | kit 의 장치 |
|---|---|
| 신뢰 피라미드, 공장보다 기초 | `skills/mode/playbooks/autonomous-run.md` 0단계 |
| 교정은 장치로 | `/dev:correct`, principles.md 의 Encode Lessons in Structure |
| 주석은 탈출구 | `/dev:no-comments`, `/dev:deslop` |
| 런타임 검증과 기능 지도 | `/dev:verify-setup` |
| 형식 검증과 상태 차트 | `/dev:formal-setup`, `/dev:statechart` |
| 검증 산출물로 리뷰 | `/dev:control-ui`, `/dev:control-cli`, principles.md 의 Prove It Works |
| 이상과 현재의 갭 찾기 | `/dev:idea` |

새 스킬이나 규칙을 더할 때는 이 표의 어느 칸을 채우는지 먼저 말한다. 어느 칸에도 들지 않으면 이 이상에 기여하는지부터 따진다.
