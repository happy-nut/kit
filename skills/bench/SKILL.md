# 측정 점검

성능 숫자를 낼 때 쓴다. PR 의 전과 후, 회귀 주장, 힐클라임 장치, 라이브러리나 설정 선택. 질문마다 코드에 대한 짐작이 아니라 실행에서 나온 증거로 답한다.

사용자가 빠른 대략치를 원했으면 한 번 돌리면 된다. 그래도 4번과 7번은 확인하고, 한 번 돌린 것이라고 말한다. 그 실행이 이상해 보이지 않으면 나머지는 건너뛴다. 선택지 사이의 선택은 대략치가 될 수 없다.

## 돌리기 전에

- 내보낼 주장을 내보낼 말 그대로 먼저 적는다(「60k 행 데이터셋에서 export 가 p50 기준 30% 빠르다」). 질문들은 이 문장을 시험한다.
- 측정 스크립트를 읽는다. 무엇을 재고, 무엇을 세고, 무엇을 무시하는지 적어 둔다.
- 부하는 `uptime`, 코어 수는 Linux 면 `nproc`, macOS 면 `sysctl -n hw.ncpu`(성능 코어만은 `sysctl -n hw.perflevel0.physicalcpu`)로 본다. 기계가 바쁘면 무엇이 돌고 있는지 찾는다. 멈출 수 없으면 양쪽을 번갈아 돌려 같은 잡음을 보게 하고, 보고에 그렇게 적는다.
- macOS 노트북이면 전원 연결 여부와 저전력 모드(`pmset -g`), 발열에 따른 클럭 저하를 확인한다. 양쪽이 같은 조건이어야 한다.

## 질문

1. **왜 두 배가 아닌가?** 병목의 이름을 댄다. 프로파일은 보고하지 않을 별도 실행에서 한다. 프로파일러와 추적기는 일을 느리게 만든다. 쓸 것:
   - 프로세스별 CPU: Linux `top`, `pidstat`. macOS `top -o cpu`, `ps -o pid,%cpu,rss,command -p <pid>`.
   - 런타임 프로파일러: `node --cpu-prof`, `py-spy`(macOS 는 sudo 필요), Linux `perf`. macOS 는 Instruments 의 Time Profiler(`xcrun xctrace record --template 'Time Profiler' --launch -- <명령>`) 또는 `sample <pid> 10`.
   - I/O 대기: Linux `iostat`, `pidstat -d`. macOS `iostat`, `sudo fs_usage -f filesys <pid>`.
   - 시스템 호출 횟수: Linux `strace -c`. macOS `sudo dtruss -c <명령>`. SIP 가 켜져 있으면 dtruss 가 막히거나 시스템 바이너리를 추적하지 못한다. 그때는 Instruments 의 System Call Trace 템플릿을 쓴다.
   - 자원 합계: macOS `/usr/bin/time -l <명령>` 은 최대 RSS, 페이지 폴트, 문맥 전환, 블록 입출력을 준다. Linux 는 `/usr/bin/time -v`.

   찾은 뜨거운 곳을 소스 위치로 이어 붙인다. 부하 생성기도 지켜본다. 그것이 먼저 포화되면 부하 생성기를 잰 것이다. 변경이 숫자를 움직이지 못했으면 병목이 그 이유를 설명한다. 변경이 쓸모없다고 하기 전에 병목부터 찾는다.
2. **튜닝했나?** 모든 쪽을 운영처럼 돌린다. 릴리스 빌드, 운영 플래그와 환경 변수, 배치와 트랜잭션 설정, 연결 풀, 운영이 보는 만큼 데워지거나 식은 캐시, 같은 버전과 데이터. 한쪽이 기본값으로 돌면 구현이 아니라 설정을 비교한 것이다. 병목이 설정이면(행마다 커밋, 디버그 빌드, 빠진 인덱스) 그쪽은 튜닝되지 않은 것이다. 튜닝하고 다시 잰 뒤에 승자를 고른다. 튜닝할 수 없으면 그 실행으로 승자를 고르지 않는다. 사용자가 무엇을 들일지 고르는 중이면 「오늘 실린 그대로의 코드」로 주장을 좁혀도 이 문제가 풀리지 않는다. 그들은 오늘의 설정이 아니라 그 선택지를 들이기 때문이다.
3. **한계를 넘었나?** 산수를 한다. 초당 바이트를 디스크와 네트워크 대역폭과, 초당 작업 수 곱하기 작업당 비용을 코어 수와, 아낀 시간을 바뀐 부분이 원래 걸리던 시간과 견준다. 실행의 10% 를 차지하는 부분을 없애면 실행은 많아야 약 11% 빨라진다. 한계를 넘은 결과는 일이 아닌 다른 것을 잰 것이다. 캐시, 아무것도 안 하는 경로, 버그.
4. **오류가 났나?** 실패와 성공이 아닌 응답의 개수를 세고, 출력이 있기만 한 게 아니라 맞는지 확인한다. 거부는 흔히 빠르고, 타임아웃과 재시도는 느리다. 스크립트가 오류를 세지 않으면 세게 고친다.
5. **재현되나?** 각 쪽을 최소 5번, 번갈아(A, B, A, B 순으로) 돌려 데워짐, 지연 초기화, 캐시, 흔들림이 어느 쪽에도 유리하지 않게 한다. 중앙값과 범위를 보고한다. 실행 간 편차보다 작은 차이는 측정 가능한 차이가 없는 것이다. 박빙이면 순위합 검정이나 장치 자체의 통계를 쓴다.
6. **의미가 있나?** 마이크로 결과 옆에, 사용자가 실제로 기다리는 end-to-end 경로를 현실적인 데이터 크기와 동시성으로 재고, 마이크로 결과를 전체 중 비중으로 보고한다. 요청의 1% 를 차지하는 도우미는 아무리 빨라져도 요청을 많아야 1% 빠르게 한다.
7. **일이 정말 일어났나?** 일이 잰 구간 안에서 실제로 돌았는지 확인한다. 요청이 서버에 닿았는지, 행이 쓰였는지, 바이트를 읽었는지, 코드가 결과를 썼는지. 게으른 코드(아무도 돌지 않는 제너레이터, 아무도 await 하지 않는 promise, JIT 가 버릴 수 있는 결과)와 타임아웃은 일어나지 않은 일에 숫자를 만들어 낸다.

## 보고

- 판정을 먼저 쓴다. 빨라짐, 느려짐, 측정 가능한 차이 없음, 결론 불가.
- 숫자는 단위, 실행 횟수, 범위, 병목과 함께 쓴다. 예: 「p50 41 ms → 33 ms, 쪽마다 7번 중앙값, 바꾼 뒤 범위 32~35 ms, 단일 코어 JSON 파싱이 병목」.
- 측정에 걸린 시간과 든 비용(기계, API 호출, 토큰)도 같이 쓴다.
- 차이를 주장하는데 병목을 대지 못하거나, 한쪽이 튜닝되지 않았거나, 4번과 7번을 확인하지 못했으면 판정은 결론 불가다. 무엇이 빠졌는지 적는다.
- PR 본문에는 대표 숫자 하나만 둔다. 실행 기록, 범위, 병목 증거는 저장소의 노트 파일이나 `/tmp/bench-<slug>/` 에 두고 링크하거나 경로를 적는다.
