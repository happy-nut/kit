# 설계

코드를 쓰기 전에 변경이 닿는 시스템을 모두 따라가 보고, 모양(타입, 시그니처, 모듈 경계)을 서로 다르게 둘 이상 그려 하나를 고른 뒤, 그 스케치를 계약 삼아 구현한다. 설계가 크거나 의견이 갈리면 혼자 그리지 말고 아래 「경쟁 절차」로 여러 모델에게 그리게 한다. 설계가 아닌 산출물(글, 코드 조각, 스크립트)을 여러 후보로 만들어 고를 때는 경쟁 절차만 쓴다.

## 설계 흐름

세션의 작업 목록 도구(데스크톱 앱이면 update_plan, 아니면 TodoWrite)에 Ground, Sketch, Implement 를 한 줄씩 연다. 경쟁 절차만 쓸 때는 Frame, Fan out, Cross-judge, Pick, Graft, Verify 를 연다.

1. **Ground.** 새 코드가 닿는 시스템마다 실제로 따라가 구조를 짧게 설명하는 글을 쓴다. 파일 이름을 대는 것은 따라간 것이 아니다. 설계가 소유권이나 계층을 다시 정하면 기존 모양에 `/dev:why` 를 돌려 그 이유를 짐작이 아니라 제약으로 삼는다. 붙일 주변 시스템이 없는 순수 신규 작업만 건너뛴다.
2. **Sketch.** 모양 전체가 다른 후보를 둘 이상 그린다. 첫 안이 충분해 보여도 그렇다(`../mode/principles.md` 의 Exhaust the Design Space). 몸통은 `not implemented`, 까다로운 로직은 의사코드로 둔다. 호출자의 사용 예를 먼저 쓰고 타입은 거기서 끌어낸다. 다음 기여자는 연 파일만 보고 가장 가까운 예를 베끼는 에이전트라고 가정하고, 아래를 가장 잘 지키는 후보를 고른다.
   - 상태마다 주인이 하나다. 둘 이상이 쓰거나 저마다 사본을 가지면 한쪽만 고친 에이전트 때문에 규칙이 갈라진다.
   - 한 일에 길이 하나다. 길이 둘이면 둘 다 호출자가 늘어난다.
   - 호출자가 알아야 할 것이 가장 적다. 작은 공개 면 뒤에 많은 것을 숨긴다. 내부는 밖에서 import 할 수 없게 하고, 전송 타입은 경계 안에서 도메인 타입으로 바꾼다.
   - 같은 목록을 두 곳에서 손으로 맞추지 않는다. 하나에서 끌어내거나, 어긋나면 빌드가 깨지게 한다.
3. **Implement.** 고른 스케치가 계약이다. 사람 확인을 기다리지 않고 바로 채운다. 부르는 사람이 「구현 전에 보여 줘」처럼 분명히 말했을 때만 멈춘다. 사람이 모양에 이의를 내면 1단계의 증거로 다루고 다시 그린다. 스케치에 없던 매개변수가 필요하면 조용히 흡수하지 말고 스케치가 틀렸는지, 요구를 놓쳤는지, 구현이 지나친지 따진다.

같은 모양의 우회가 서로 관계없는 곳에 되풀이되면 덧대지 말고 스케치를 버린다(`../mode/principles.md` 의 Redesign From First Principles). 신호는 특수 분기가 계속 늘어남, `any`·캐스트 같은 탈출구, 공유하지 않는다던 상태에 필요해진 락, 내부 규칙을 알아야 쓸 수 있는 추상화다. 한두 번은 신호가 아니다. 데이터가 복잡한 것은 설계가 복잡한 것과 다르다. 버릴 때는 지은 것을 따라가고, 새 제약이 첫날부터 있던 것처럼, 옛 스케치보다 작게 다시 그려 2단계로 돌아간다(`../mode/principles.md` 의 Subtract Before You Add).

산출물은 스케치와 짧은 설명 글이다. 스케치는 작은 변경이면 타입·시그니처 파일 하나, 큰 작업이면 모듈 지도와 타입 정의다. 설명 글에는 문제, 사용 예, 고른 모양, 버린 대안마다 진 이유 한 줄, 받아들인 맞바꿈, 경쟁 절차를 돌렸으면 그 결과 노트를 담는다. 둘 다 저장소 안 작업 브랜치에 둔다. 설명 글을 저장소에 남기면 안 되는 성격이면 `/tmp/design-<slug>/rationale.md` 에 두고 경로를 보고한다.

# 경쟁 절차

같은 과제에 후보 N개를 병렬로 만들게 하고, 하나를 기반으로 고른 뒤, 진 후보의 가장 좋은 부분을 기반에 접붙인다.

## 1. Frame

모든 후보가 같은 프롬프트를 받는다. 그래서 프롬프트가 계약이다.

1. 각 후보가 만들 산출물을 적는다.
2. 채점 기준을 정한다. 이 과제에서 성공이 무엇인지 채점할 수 있는 구체 기준 3~6개. 4단계에서 고르는 쪽이 쓰는 도구다. 후보에게는 과제만 보여 주고 기준은 보여 주지 않는다.
3. 러너를 고른다. `~/.claude/rules/dev-models.md` 의 `design runners` 줄이 있으면 그 항목마다 하나씩이고(`/dev:mode` 의 「서브에이전트」 절), 없으면 `fable high`, `opus high`, 부모 모델(`model` 을 뺀다) 하나씩이다. 설계 방향이 여럿이면 러너를 늘린다. 판단보다 생성량이 관건인 일이면 같은 모델을 N번 쓴다. `Agent` 가 어떤 모델을 거부하면 그 자리를 남은 모델 중 하나로 돌리고 그렇게 말한다. 러너가 둘보다 적어지면 남은 모델로 채워 둘 이상을 만든다.
4. 후보마다 출력 위치를 따로 준다(`../mode/principles.md` 의 Separate Before Serializing Shared State). 기본은 `Agent` 의 `isolation: "worktree"` 로 각자 git worktree 를 받는 것이다. worktree 를 쓸 수 없으면 `/tmp/design-<slug>/candidate-<n>/` 을 쓴다.

## 2. Fan out

N개를 한 메시지에서 모두 띄운다. 각 호출은 `subagent_type: "dev:worker"`, `model`(3번에서 고른 것), `isolation: "worktree"`, `run_in_background: true`.

브리프마다 과제, 공유 grounding 의 경로, 자기 출력 위치, 그리고 「산출물과 함께, 고려했다가 버린 대안과 그 이유를 짧은 근거 글로 내라」를 담는다. 설계 스케치면 1단계 Ground 글의 경로와 「`/dev:design` 의 설계 흐름 2단계 기준으로 스케치하고 설명 글을 내라. 네 모델이 낼 수 있는 가장 좋은 설계를 내고, 다른 러너를 의식해 무난한 중간으로 모이지 마라」를 넣는다. worktree 에 쓴 러너에게는 끝날 때 작업을 커밋하고 브랜치 이름을 보고하게 한다.

결과를 내지 못한 후보가 있으면 N-1 개로 진행하고 탈락을 기록한다.

## 3. Cross-judge

모든 후보가 끝난 뒤에 심사자 하나를 띄운다. 후보가 아직 쓰는 중에는 띄우지 않는다.

- 모델: `~/.claude/rules/dev-models.md` 의 `design cross-judge pool` 줄(기본 `opus high`, 부모 모델)에서 목록 순서대로, 부모와 다른 계열의 첫 항목을 쓴다. `fable` 은 `opus` 와 같은 계열로 친다. 부모 모델 항목은 심사하지 않는다. 맞는 항목이 없으면 심사를 건너뛰고 그렇게 말한다.
- 형식: `subagent_type: "Explore"`, `run_in_background: true`, 브리프에 「파일을 고치지 마라」. 끝난 뒤 `git status` 로 아무것도 바뀌지 않았는지 확인한다.
- 심사자는 채점 기준과 후보들(경로 이름표)을 받아 기준마다 점수를 매기고, 근거와 함께 기반 하나를 추천한다.
- 심사는 4단계의 내 읽기와 병렬로 돈다.

모든 모델이 같은 회사(Anthropic) 것이라 심사의 독립성에는 한계가 있다. 비슷한 훈련에서 오는 같은 맹점을 러너와 심사자가 함께 가질 수 있다. 이 한계를 결과 노트에 그대로 적는다. 심사자가 돌지 못하면 혼자 고르고 그렇게 적는다.

## 4. Pick

고르기 전에 모든 후보를 끝까지 읽는다. 전체 인상이 아니라 기준마다 하나씩 채점하고, 심사자가 돌았으면 그 결과와 견준다. 기반이 일치하면 선택이 확인된 것이다. 갈리면 한쪽이 편향됐거나 기준이 모호했다는 뜻이다. 결정 전에 두 근거를 모두 읽는다.

다음 유지보수자가 불변식을 깨지 않고 가장 쉽게 넓힐 수 있는 기반을 고른다. 두 후보가 비슷하면 경계가 더 깨끗하거나 API 가 더 작은 쪽을 고른다(`../mode/principles.md` 의 Laziness Protocol).

## 5. Graft

진 후보를 하나씩 다시 훑어 기반에 옮길 만한 것을 찾는다. 보통 후보마다 한두 가지이고, 대부분이 아니다. 접붙이기는 손으로 녹여 넣어 결과가 한 머릿속 모델로 일관되게 한다(`../mode/principles.md` 의 Redesign From First Principles). 기계적으로 붙여 넣지 않는다.

후보들이 한 모양으로 모이면 강한 합의다. 그렇게 적고 그 모양을 내보낸다. 접붙일 것이 없다. 후보들이 크게 갈리면 Frame 이 덜 정해졌던 것이다. 갈린 것을 평균 내지 말고 다시 틀을 잡아 다시 돈다.

## 6. Verify

합성된 산출물을 다른 결과물처럼 검증한다(`../mode/principles.md` 의 Prove It Works). 검증에서 경쟁이 놓친 문제가 나오면 둘 중 하나다. Frame 이 틀렸거나(다시 틀을 잡고 다시 돈다), 어느 후보가 잡았는데 접붙이기를 놓쳤거나(5단계로 돌아간다). 덮고 넘어가지 않는다.

끝나면 러너들이 만든 worktree 와 브랜치 가운데 쓰지 않는 것은 지운다.

## 경쟁 결과 노트

합성된 산출물 하나와 함께 짧은 노트를 낸다.

- 기반과 고른 이유
- 심사자의 판정, 또는 심사를 건너뛴 사실과 이유
- 모든 모델이 같은 회사라 심사 독립성에 한계가 있다는 한 줄
- 접붙인 것마다 출처 후보
- 버린 것과 이유
- 수렴 또는 탈락
- 검증 결과
