# 설계

코드를 쓰기 전에 변경이 닿는 시스템을 모두 따라간다. 그다음 서로 다른 모양(타입, 시그니처, 모듈 경계)을 둘 그리고, 상태마다 주인이 하나이고 한 일에 길이 하나이며 호출자가 알아야 할 것이 가장 적은 쪽을 고른다. 우회가 되풀이되면 덧대지 말고 다시 설계한다.

설계가 크거나 의견이 갈리면 혼자 그리지 말고 아래 「경쟁 절차」를 돌린다.

# 경쟁 절차

같은 과제에 후보 N개를 병렬로 띄우고, 기반 하나를 고른 뒤, 진 후보의 가장 좋은 부분을 기반에 접붙인다.

무엇이든 띄우기 전에 세션의 작업 목록 도구(데스크톱 앱이면 update_plan, 아니면 TodoWrite)에 단계마다 한 줄(Frame, Fan out, Cross-judge, Pick, Graft, Verify)을 연다.

## 1. Frame

모든 후보가 같은 프롬프트를 받는다. 그래서 프롬프트가 계약이다.

1. 각 후보가 만들 산출물을 적는다.
2. 채점 기준을 정한다. 이 과제에서 성공이 무엇인지 채점할 수 있는 구체 기준 3~6개다. 4단계에서 고르는 쪽이 쓰는 도구다. 후보는 과제만 본다.
3. 러너를 `~/.claude/rules/dev-models.md` 의 `design runners` 줄에서 고른다. 기본은 `fable high`, `opus high`, 부모 모델이다. `auto` 나 `inherit-parent` 항목은 부모 모델이므로 `model` 을 빼고 `general-purpose` 로 띄운다. `Agent` 가 어떤 모델을 거부하면 같은 계열의 가장 가까운 값을 쓰거나 그 자리를 빼되, 러너를 둘 이상 남기고 그렇게 말한다. 계열은 `fable` 과 나머지 Claude 모델(`opus`, `sonnet`, `haiku`)로 나눈다. 설계 방향이 여럿이면 더 띄운다. 판단보다 생성량이 관건인 일이면 한 모델을 되풀이한다. 서브에이전트마다 추론 수준은 `../mode/SKILL.md` 의 「서브에이전트」 절대로 고른다.
4. 후보마다 출력 위치를 따로 준다(`../mode/principles.md` 의 Separate Before Serializing Shared State). 되도록 `isolation: "worktree"` 로 git worktree 를 주고, 아니면 `/tmp/design-<slug>/candidate-<n>/` 을 준다.

## 2. Fan out

N개를 한 메시지에서 모두 `run_in_background: true` 로 띄운다. 브리프마다 과제, 공유 grounding 의 경로, 자기 출력 경로, 그리고 산출물과 함께 고려한 대안과 버린 것을 밝힌 짧은 근거 글을 내라는 지시를 담는다.

결과를 내지 못한 후보가 있으면 N-1 개로 진행하고 탈락을 적는다.

## 3. Cross-judge

2단계 후보가 모두 끝난 뒤 `~/.claude/rules/dev-models.md` 의 `design cross-judge pool` 줄에서 심사자 하나를 띄운다. 기본은 `opus high`, 부모 모델이다. 형식은 `subagent_type: "Explore"` 에 브리프의 「파일을 고치지 마라」이고, 끝난 뒤 `git status` 로 확인한다. 심사자는 부모와 다른 계열 모델이다. 계열은 1단계 3번대로 나누고, 다른 계열의 첫 항목을 쓴다. `auto` 나 `inherit-parent` 항목은 부모 모델이다. 부모 모델을 모르면 첫 실제 모델을 쓰고 계열 검사를 하지 못했다고 말한다. `Agent` 가 어떤 모델을 거부하면 같은 계열의 가장 가까운 값, 그다음 다른 계열의 다음 항목을 쓰고, 그것도 없으면 심사를 건너뛴다. 어느 쪽이든 그렇게 말한다. 내가 4단계에서 읽는 동안 심사자는 후보마다(경로 이름표로) 채점 기준 하나하나에 점수를 매기고 기반을 추천한다.

## 4. Pick

고르기 전에 모든 후보를 끝까지 읽는다. 전체 인상이 아니라 기준마다 하나씩 채점하고, 3단계에서 심사자가 돌았으면 그 결과와 견준다. 기반이 일치하면 선택이 확인된 것이다. 갈리면 한쪽이 편향됐거나 기준이 모호했다는 뜻이다. 결정 전에 두 근거를 모두 읽는다.

다음 유지보수자가 불변식을 깨지 않고 가장 쉽게 넓힐 수 있는 기반을 고른다. 둘이 비슷하면 경계가 더 깨끗하거나 API 가 더 작은 쪽을 고른다(`../mode/principles.md` 의 Laziness Protocol).

## 5. Graft

진 후보를 하나씩 한 번 더 훑어 기반에 옮길 만한 것을 찾는다. 보통 후보마다 한두 가지이고, 대부분이 아니다. 접붙일 것은 손으로 녹여 넣어 결과가 한 머릿속 모델로 일관되게 한다(`../mode/principles.md` 의 Redesign From First Principles). 기계적으로 붙여 넣지 않는다.

후보들이 한 모양으로 모이면 강한 합의다. 그렇게 적고 그 모양을 내보낸다. 접붙일 것이 없다. 후보들이 크게 갈리면 1단계가 덜 정해졌던 것이다. 갈린 것을 평균 내지 말고 다시 틀을 잡아 다시 돈다.

## 6. Verify

합성된 산출물을 다른 결과물처럼 검증한다(`../mode/principles.md` 의 Prove It Works). 검증에서 경쟁이 놓친 문제가 나오면 둘 중 하나다. 1단계가 틀렸거나(다시 틀을 잡고 다시 돈다), 어느 후보가 잡았는데 접붙이기를 놓쳤다(5단계로 돌아간다). 덮고 넘어가지 않는다.

## 산출물

합성된 산출물 하나와 짧은 결과 노트를 낸다. 노트에는 기반과 고른 이유, 심사자의 판정 또는 3단계에서 심사를 건너뛴 사실, 접붙인 것마다 출처 후보, 버린 것과 이유, 수렴이나 탈락, 검증 결과를 적는다.
