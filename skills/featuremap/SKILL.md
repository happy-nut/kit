# 기능 지도 그래프

사용자와 에이전트가 같은 이름으로 기능을 부르게 하는 그래프 한 장을 만든다. 그래프의 뼈대는 코드에서 매번 다시 뽑는다. 그래서 손으로 쓴 지도가 낡아도 그래프는 코드와 같다.

결과물은 오프라인으로 열리는 파일 하나다. 첫 화면은 왼쪽에서 오른쪽으로 흐르는 나무다. 왼쪽 끝이 앱(뿌리), 그다음이 진입점 원천(단축키, CLI 인자, HTTP 라우트, 공개 함수), 그다음이 화면·범위, 오른쪽 끝이 끝점이다. 가지마다 −/+ 로 접고 편다. 자동 검증이 없는 가지와 끝점은 꺼진 것처럼 흐리게(회색, 점선) 그리지만 누르면 똑같이 열린다. 노드를 누르면 뿌리부터 그 노드까지의 길과 그 아래가 밝아지고, 패널(휴대폰은 아래 시트)에 이름과 복사 단추, 나눔(자식과 합), 검증 판정과 근거가 뜬다. 처음 열 때 노드가 열 순서로 들어오고 선이 그려지며, 고른 길에는 흐름이 돈다(움직임 줄이기 설정이면 멈춘다). 휴대폰에서는 화면 너비에 맞춰 열린다.

## 낱말

이 스킬과 HTML 은 이 낱말만 쓴다.

| 낱말 | 뜻 |
|---|---|
| 진입점 | 사용자나 호출자가 앱에 들어오는 문 하나. 단축키, 메뉴 항목, 라우트, CLI 인자, 공개 함수 |
| 원천 | 진입점이 정의된 코드 자리 하나(단축키 표 파일, 인자 파서, 라우터). 진입점을 세는 정규식과 함께 적는다 |
| 가지 | 나무의 안쪽 노드. 원천, 화면, 범위 |
| 끝점 | 나무의 잎. 진입점 하나. 이름은 코드의 식별자 그대로다(`compareTip`, `--staged`, `GET /api/need`) |
| MECE | 모든 가지에서 자식들의 끝점 합이 그 가지의 끝점 수와 같고, 같은 끝점이 두 번 나오지 않고, 원천마다 코드에서 센 수와 잎 수가 같다 |
| 자동 검증 / 방법만 / 검증 없음 | 그 끝점의 키를 적은 하위 기능을 스크립트·시험이 돌린다 / 손으로 모는 방법만 있다 / 그런 하위 기능이 없다 |
| README 빈칸 | 기능 지도 README 의 `## Not mapped yet` 절에 사람이 적어 둔 아직 안 그린 곳 |

## 무엇이 MECE 를 보장하나

그래프는 끝점마다 `path`(원천에서 끝점까지의 가지 이름들)를 하나씩 받아 나무로 쌓는다. 끝점 하나가 길 하나에만 있으니 나무는 만들 때부터 나눔이다. 스크립트는 그래도 그릴 때마다 다시 잰다.

- **빠짐(CE).** 원천마다 코드 파일에서 그 정규식이 맞는 수를 새로 세고, 그 원천의 잎 수와 다르면 「누락」. 길이 없는 잎, 원천이 없는 잎도 빠짐이다.
- **겹침(ME).** 같은 이름의 잎이 둘이면 「중복 잎」, 같은 가지에 같은 키를 가진 잎이 둘이면 「같은 자리에 같은 진입점」. 코드가 같은 진입점을 두 번 적는 원천(같은 플래그를 두 줄에서 읽는 파서)은 `distinct: true` 로 이름을 한 번만 센다.
- **재귀.** 뿌리부터 모든 가지에서 자식 합 = 부모, 빈 가지 0, 같은 이름 가지 0 을 확인하고, 뿌리 합이 잎 수와 같은지 본다. 확인한 가지 수를 HTML 머리에 적는다.

하나라도 어긋나면 스크립트는 문제를 찍고 HTML 을 쓰지 않는다(종료 코드 1). 고칠 곳은 진입점을 뽑는 스크립트(그래프를 그리는 장치)다. 기능 지도 파일은 고치지 않는다. 고친 뒤 다시 그려 다시 잰다.

## 끝점의 검증 덧칠

기능 지도의 `Sub-features` 글머리(또는 그 하위 기능 ID 가 있는 `Driving` 줄)에 끝점의 키가 낱말째 적혀 있으면 그 하위 기능의 판정을 끝점에 덧칠한다. 여러 하위 기능이 적었으면 가장 좋은 판정을 쓴다. 덧칠은 나눔이 아니라서 MECE 와 상관없다.

하위 기능의 판정은 이렇다.

| 판정 | 조건 |
|---|---|
| 자동 검증 | 기능 지도 폴더 밖의 파일이 그 ID 를 가리킨다. `.md`·`.txt` 가 아닌 파일이면 어느 줄이든, `.md` 면 실행 명령(`node`, `npm`, `pytest`, `./x.sh` 등)이 있는 줄만. 또는 근거 파일의 `verified_by` 가 짚은 시험이 실제로 있다 |
| 방법만 | 그 기능 파일의 `Driving it with …` 절에 ID 가 나온다 |
| 없음 | 둘 다 아니다 |

키를 비교할 때 앞부분만 겹치는 것(`⌘E` 와 `⌘Enter`)은 세지 않고, 두 글자 이하 영숫자 키는 백틱 안에 있을 때만 센다.

## 순서

1. **기능 지도를 찾는다.** `<저장소>/.claude/skills/verify-*/features/` 다. 없으면 `/dev:verify-setup` 으로 먼저 만든다. 지도가 없어도 나무는 그릴 수 있지만 끝점이 모두 「검증 없음」 이 된다.
2. **진입점을 뽑는 스크립트를 쓴다.** 손으로 고르지 않는다. 코드의 원천을 읽는 짧은 스크립트를 scratch 폴더에 남기고, 그 출력을 `surfaces.json` 으로 쓴다. 원천은 앱 종류마다 다르다.
   - 화면 앱: 단축키 표, 메뉴 정의, 라우터, 화면 탭 목록.
   - 백엔드: HTTP 라우트 등록(`HandleFunc`, `app.get`, `@router.post`, OpenAPI 명세), RPC·gRPC 서비스 정의, CLI 하위 명령, 예약 작업(cron), 큐 소비자, 웹훅.
   - 라이브러리: 바깥에 내보내는 공개 API(`index.ts` 의 export, `__all__`, `lib.rs` 의 `pub`).
   ```json
   {"app": "kakapo",
    "sources": [{"name": "단축키", "file": "src/shortcuts.ts", "pattern": "^\\s*\\{ id: \""},
                {"name": "CLI 인자", "file": "src/cli-args.ts", "pattern": "readOption\\(args, \"(--[\\w-]+)\"\\)", "distinct": true}],
    "entries": [{"id": "compareTip", "source": "단축키", "path": ["단축키", "어디서나"], "match": ["⌥T"], "where": "src/shortcuts.ts:16", "label": "⌥T"}]}
   ```
   - `pattern` 은 그 원천에서 진입점 하나마다 한 번 맞는 정규식이다. 뽑는 코드와 다른 식으로 세야 뽑기에서 빠진 것이 드러난다(뽑는 쪽은 줄 전체를 풀고, 세는 쪽은 줄머리만 본다).
   - `path` 는 코드가 이미 가진 범위를 따른다. 단축키 표의 `where`, 라우트의 첫 경로 조각, 명령의 상위 명령. 같은 키가 범위마다 다른 일을 하면 범위가 갈라 준다.
   - `id` 는 코드 식별자 그대로 쓴다. 그 이름이 사용자와 에이전트가 끝점을 부르는 말이다.
3. **근거 파일을 쓴다(선택).** 백엔드·라이브러리 시험은 하위 기능 ID 를 담지 않는 일이 많다. 그 하위 기능을 실제로 검사하는 시험을 읽어 찾았으면 scratch 의 근거 파일에 단다. 스크립트는 그 파일에 그 이름이 있을 때만 「자동 검증」으로 치고, 없으면 「근거를 못 찾음」 을 `naming_problems` 로 센다.
   ```json
   {"NEED-2": {"verified_by": ["need_revive_test.go::TestNeedRevive"]}}
   ```
4. **그린다.**
   ```bash
   python3 <이 스킬>/scripts/featuremap.py <저장소>/.claude/skills/verify-<앱>/features --repo <저장소> --surfaces <scratch>/surfaces.json --names <scratch>/names.json --out <scratch>/<앱>-featuremap.html
   ```
   표준 출력 첫 줄은 요약 JSON 이다(`entries`, `sources`, `nodes_checked`, `mece`). `mece` 가 false 면 이어지는 문제 줄을 보고 2의 스크립트를 고쳐 다시 그린다. 「누락」 이면 뽑기 정규식이 놓친 줄을 찾고, 「중복」·「같은 자리」 면 같은 진입점을 두 번 뽑은 곳을 찾는다. 숫자를 맞추려고 `pattern` 을 뽑는 쪽에 맞춰 고치지 않는다. HTML 은 저장소에 커밋하지 않는다.
5. **띄워 본다.** 브라우저로 연다(파일 경로로 안 열리면 그 폴더를 `python3 -m http.server`). 처음 열 때 움직임, 나무 전체(축소), 가지 하나를 누른 패널(나눔과 합), 흐린 끝점 누르기, 가지 접기, 검색, 휴대폰 너비와 아래 시트, 어두운 화면을 하나씩 찍는다. 머리의 「MECE ✓ 가지 n · 잎 m = 코드 …」 가 요약 JSON 과 같은지 본다.
6. **이상한 숫자를 판다.** 자동 검증 끝점 몇 개를 골라 덧칠한 하위 기능의 근거 줄이 정말 그 진입점을 돌리는지 본다. 틀린 판정을 찾으면 스크립트를 고치고 `--self-test` 에 그 경우를 더한다.

## 보고

- HTML 파일을 사용자에게 보낸다(파일 보내기 도구가 있으면 그것으로).
- 첫 줄: 「MECE ✓ 가지 n · 잎 m = 코드 <원천별 수>」 와 자동 검증된 끝점 a/m.
- 끝점을 부를 때는 코드 식별자(`compareTip`)로, 하위 기능은 `CMP-3 branch tip` 처럼 지도의 ID 와 이름으로 부른다.
- 다음에 할 일은 검증을 늘리는 쪽으로 쓴다. 흐린 끝점이 많은 가지부터, 그 키를 몰 하위 기능과 시험을 붙인다.
- 이 스킬은 앱 코드와 기능 지도 파일을 고치지 않는다. 고치는 것은 진입점을 뽑는 스크립트(scratch)와, 틀린 판정을 낸 이 스킬의 스크립트다.
