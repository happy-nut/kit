# devkit 안내

사용자의 질문에 답하고, 그대로 보낼 수 있는 프롬프트 하나와 답이 나온 파일을 준다. 안내 질문이면 일을 시작하지 않는다. 사용자는 방법을 물었고, devkit 실행은 토큰을 실제로 쓰니 프롬프트를 보내는 건 사용자에게 맡긴다.

「devkit 으로 이 버그 고쳐」처럼 일을 시키는 말은 안내 질문이 아니다. `/dev:mode` 를 읽고 그대로 일한다. 그리고 다음부터는 일마다 `/dev:mode` 로 시작하면 된다고 한 번 말한다.

이 파일은 질문을 답이 있는 스킬·파일로 보내는 지도다. 자세한 내용은 그 파일이 가진다. 인용하기 전에 보내는 파일을 읽고, 이 지도와 다르면 그 파일을 믿는다. 파일 위치는 이 스킬 폴더의 두 단계 위(플러그인 폴더) 기준 경로로 준다. 사용자가 포크를 쓰면 그 저장소 경로로 준다.

## 무엇이 필요한지

메시지와 대화에서 필요를 짐작한다. 「PR 리뷰는 어느 스킬?」처럼 상황을 말했으면 바로 그 절로 간다. 그래도 모르겠으면 `AskUserQuestion` 으로 한 번 묻고, 고른 절만 답한다.

- 설치와 설정
- `/dev:mode` 로 일 시작하기
- 상황에 맞는 스킬 고르기
- 잘못 돈 실행 바로잡기
- devkit 을 내 것으로

답을 바꾸는 상태를 본다. 답이 달라질 때만 말한다.

- `~/.claude/rules/dev-models.md` 이 없으면 `/dev:setup` 을 아직 안 돌린 것이다. 모든 역할이 기본 모델을 쓴다.
- 프로젝트에 `.claude/skills/verify-*` 스킬이나 앱을 모는 다른 하네스가 없으면 에이전트가 앱을 정해진 방법으로 몰 수 없다. 질문이 「변경이 동작하는지 증명」이면 `/dev:verify-setup` 을 말한다.
- 프로젝트에 형식 검증 스킬(`.claude/skills/formal-*`)이 없으면 테스트가 닿는 곳 너머로 검사되는 속성이 없다. 질문이 경쟁 상태·불변식처럼 테스트가 드물게 닿는 경우면 `/dev:formal-setup` 을 말한다. 있는데 그 스킬이 마지막으로 맞춘 커밋 뒤로 다루는 코드가 바뀌었고 질문이 그 코드에 닿으면, `/dev:formal-setup` 의 「유지」 절로 다시 맞추라고 말한다.

설정 파일이 없고 그게 중요하면, 지금 설정할지 한 번 묻는다. 중요한 경우는 사용자가 처음이거나, 질문이 설정·비용이거나, 답이 어느 모델이 도는지에 달렸을 때다. 대화마다 한 번만 묻는다. 필요도 불분명하면 두 질문을 한 `AskUserQuestion` 에 같이 묻는다. 선택지는 둘이다.

- 지금: 칠 명령 `/dev:setup` 을 주고 질문에도 답한다.
- 나중에: 질문에 답하고, `/dev:setup` 을 돌리기 전까지는 모든 역할이 기본 모델이라고 한 줄 더한다.

## 설치와 설정

1. 설치는 README 의 「설치」 절 명령 두 줄이다(`claude plugin marketplace add …`, `claude plugin install dev@kit`). 새 판은 `claude plugin update dev@kit`. 서드파티 마켓플레이스는 자동 업데이트가 꺼져 있다.
2. `/dev:setup` 을 돌린다. 역할별 모델과 추론 예산을 `~/.claude/rules/dev-models.md` 에 쓴다. 다음 `/dev:mode` 실행부터 적용된다. 끝에 검증 스킬과 형식 검증 스킬을 한 번씩 제안한다(프로젝트에 이미 있으면 안 한다).
3. 진짜 일 하나를 `/dev:mode` 와 목표, 통과·실패가 갈리는 확인 조건으로 시작한다.

설치만으로는 스킬이 움직이지 않는다. 모든 devkit 스킬은 사용자가 부를 때만 뜬다(`disable-model-invocation: true`).

첫 프롬프트를 같이 다듬자고 제안한다. `references/prompting.md` 를 따른다.

비용이 걱정이면 토큰이 어디로 가는지와 덜 쓰는 법을 말한다. devkit 은 서브에이전트와 리뷰·설계 패널에 토큰을 더 쓴다. `/dev:setup` 을 다시 돌려 모델을 낮추거나(`아끼기`, 또는 역할별로 `sonnet`·`haiku`) 패널 목록을 줄인다. 패널 항목 하나가 서브에이전트 하나다. `/dev:mode` 는 엄격함이 필요한 일에만 쓴다. 검증에 쓰는 토큰은 줄이지 않는 게 devkit 의 원칙이라는 것도 같이 말한다.

## `/dev:mode` 로 일 시작하기

`/dev:mode` 는 일을 플레이북에 맞추고, 플레이북 단계를 작업 목록에 그대로 옮기고, 단계가 필요로 할 때 다른 스킬을 부른다. 좋은 프롬프트는 목표와 「됐다」를 어떻게 알지를 적는다. 스킬 목록은 적지 않는다. 손으로 쓴 순서는 플레이북이 지킬 단계를 빠뜨리거나 뒤섞기 쉽다. 프롬프트를 같이 다듬기 전에 `references/prompting.md` 를 읽는다.

모드는 켜 두는 스위치가 아니다. `/dev:mode` 는 그 메시지에 붙고, 대화가 길어지면 흐려진다. **작업마다 `/dev:mode` 로 시작한다.** 대화 중간에 주제를 바꿀 때는 「새 작업」이라고 말해야 모드가 새 플레이북을 고른다. 그 전까지 후속 메시지는 진행 중인 플레이북의 다음 단계로 다뤄진다.

`/dev:mode` 는 플레이북 단계에서 띄우는 서브에이전트에 이미 `dev:worker` 를 쓴다. 직접 띄우는 서브에이전트도 같은 방식으로 일하게 하려면 `subagent_type: "dev:worker"` 로 띄우고 브리프에 `skills/mode/SKILL.md` 의 절대 경로를 넣는다.

어디서 멈추는지도 필요하면 말한다. 되돌릴 수 있는 일과 바깥 행동(팀 채팅, 티켓 갱신, 평가 시작)은 묻지 않고 하고, 되돌릴 수 없는 쓰기(공유 브랜치 force-push, 배포, 데이터 삭제, 손님에게 가는 메시지)는 언제나 멈춘다. 정본은 `/dev:mode` 의 「자율」 절이다.

## 질문으로 고르기

기본 답은 `/dev:mode` 다. 단계가 필요로 하면 나머지 대부분을 알아서 부른다. 플레이북이 주는 것보다 더 많이, 또는 덜 원할 때 스킬을 직접 댄다. 권하기 전에 그 스킬을 읽고, 예시 프롬프트 하나를 준다.

| 이런 걸 원하면 | 쓸 것 |
|---|---|
| 무엇을 풀지부터 모르겠다. 원하는 모습은 있는데 진짜 문제가 무엇인지 | `/dev:idea <원하는 모습>` |
| 사소하지 않은 일을 제대로 | `/dev:mode <할 일>` |
| 시작 전에 에이전트가 목표와 문제를 제대로 이해했는지 확인 | `/dev:mode` 에 「먼저 문제를 네 말로 다시 적어」. 첫 메시지에 목표 재진술이 나온다 |
| 보내기 전에 프롬프트를 더 날카롭게 | `/dev:mode` 에 「이 요청을 목표·완료 판정·보여 줄 증거·이미 아는 것·진짜 제약으로 다시 세워 줘. 일은 하지 마」 (`/dev:mode` 의 「이해 먼저」) |
| 코드가 지금 어떻게 도는지, 새 코드를 어디 둘지 | `/dev:how` |
| 왜 이렇게 생겼는지, 이 숫자는 어디서 왔는지 | `/dev:why` |
| 바뀐 것이나 하위 시스템을 쉬운 말로 배우기 | `/dev:why` (「how 와 엮어 가르치기」 절) |
| 최근 내 작업을 주제별로 따라잡기 | `/dev:recall` |
| 이 대화에서 내 마지막 메시지 뒤로 바뀐 것, 내가 결정할 것만 | `/dev:catchup` |
| 같은 따라잡기를 자막 달린 짧은 슬라이드 영상으로 | `/dev:catchup-video` |
| 작은 diff 가 diff 밖에서 무엇을 깰 수 있는지 | `/dev:review` (「파급 범위」 절) |
| 함수 경계를 넘는 코드 전에 타입·모듈 모양 정하기 | `/dev:design` |
| 같은 브리프로 여러 시도를 받아 가장 나은 것으로 합치기 | `/dev:design` |
| 조각마다 병렬 검사, 또는 워커 경주 | `/dev:swarm` |
| 여러 모델이 diff 를 깨 보는 리뷰 | `/dev:review` |
| 싼 로컬 테스트가 있는 버그를 테스트 먼저 | `/dev:tdd` |
| `.ts`·`.tsx` 작업에 TypeScript 규칙 | `/dev:ts` |
| 리뷰 전에 주석 걷어내기(쓰지 않은 리뷰어가 심사) | `/dev:no-comments` |
| 문서·README·RFC·PR 설명·커밋 메시지·보고를 한국어 기준대로, AI 티 걷기 | `/dev:write` |
| 방금 답을 쉬운 말로 다시 | 그냥 「쉬운 말로 다시 해 줘」. 스킬이 필요 없다 |
| 에이전트가 앱을 정해진 방법으로 몰아 동작을 증명하게 | `/dev:verify-setup` |
| 검증 스킬과 기능 지도를 앱에 다시 맞추기 | `/dev:verify-setup` (「유지」 절) |
| 기능 지도와 그 커버리지를 HTML 한 장으로 보기 | `/dev:featuremap` |
| 테스트가 드물게 닿는 경쟁 상태·불변식을 형식 검증 | `/dev:formal-setup` |
| 코드가 바뀐 뒤 형식 검증을 다시 맞추고, 실패가 어긋남인지 버그인지 가리기 | `/dev:formal-setup` (「유지」 절) |
| 사용자가 보는 흐름을 TLA+ 로 검사한 상태 차트로, 규칙을 깨는 상태까지의 가장 짧은 길과 함께 | `/dev:statechart` |
| 성능 숫자를 보고하거나 믿기 전에 점검 | `/dev:bench` |
| 크거나 여러 곳을 가로지르는 일, 자리를 비운 뒤 믿어야 하는 일 | `/dev:mode` (맞춤 플레이북 절로 간다) |
| 긴 실행 중 결정 기록, 나중에 검토 | `/dev:log` |
| 막을 낱말·역할별 모델 정하기 | `/dev:setup` |
| 내 작업 습관을 devkit 에 녹이기 | `/dev:reflect` |
| 끝난 일에서 배운 것을 스킬 수정으로 | `/dev:reflect` |
| 이 저장소에서 에이전트가 같은 실수를 되풀이하지 않게 | `/dev:correct` |
| 채널에 올라온 이슈 보고 하나를 분류해 원래 스레드에 판정 답글 하나 남기기(원격 루틴으로도) | `/dev:triage` |
| 분류된 버그를 앱에서 재현하고 작은 초안 수정 PR 까지(원격 루틴으로도) | `/dev:repro-fix` |
| 누르면 Claude Code 원격 루틴을 깨우는 버튼 페이지 | `/dev:bot-ui` |
| devkit 길 찾기 | `/dev:help` |

이 폴더 옆 스킬 폴더 중 표에 없는 것이 있으면 그 frontmatter 를 읽고 description 으로 안내한다.

헷갈리는 짝:

- `/dev:idea` 는 무엇을 풀지(문제)를 정하고 멈춘다. `/dev:mode` 는 정해진 일을 푼다. `/dev:idea` 보고 끝의 프롬프트로 `/dev:mode` 를 부른다.
- `/dev:how` 는 코드가 무엇을 하는지, `/dev:why` 는 왜 그런지 설명한다. 쉬운 말로 가르쳐 달라면 `/dev:why` 가 둘을 엮는다.
- `/dev:design` 은 모든 러너에게 같은 브리프를 주고 좋은 점을 합친다. `/dev:swarm` 은 일을 조각이나 경주로 나눠 보고서 하나로 돌려준다.
- `/dev:design` 은 설계를 정하면 바로 구현한다. 구현 전에 설계를 보고 싶으면 「구현 전에 보여 줘」를 붙인다.
- `/dev:review` 의 적대 리뷰는 diff 를 본다. 파급 범위 절은 diff 밖의 깨짐을 찾고, 변경을 안전하게 만드는 사실 하나를 증명한다. 둘 다 고치지 않는다.
- `/dev:recall` 은 최근 여러 대화에서 맥락을 다시 세운다. `/dev:catchup` 은 이 대화의 마지막 메시지 뒤만 다룬다. 특정 대화나 브랜치 하나를 이어받는 건 이어받기 플레이북이다.
- `/dev:mode` 의 맞춤 플레이북은 엄격한 실행 하나를 설계한다. 오케스트레이션 플레이북은 여러 날, 많은 PR 에 걸친 프로그램을 돌린다. 자율 실행 플레이북은 일 하나를 완료 조건까지 몬다.

devkit 에 없는 것:

- `/simplify`, `/loop`, `/code-review` 는 Claude Code 기본 스킬이다. devkit 은 필요하면 이것들을 쓴다.
- 오케스트레이션 스킬은 따로 없다. 오케스트레이션은 `/dev:mode` 의 플레이북이다.

## 플레이북과 원칙

플레이북은 `/dev:mode` 안의 단계 목록이라 슬래시 명령이 없다. `/dev:mode` 에 일을 설명하면 하나를 고른다. 이런 말은 바로 하나를 부른다.

| 말 | 플레이북 |
|---|---|
| 「이 PR 돌봐」, 「초록으로 만들어」, 「PR 123 확인해」, 「남은 거 있어?」 | PR 돌보기 `babysit.md`. 머지 준비까지. 머지·착지·출시를 말해야 머지한다 |
| 「스택 내보내」, 「머지해」 | 내보내기 `shipping.md` |
| 「이 브랜치 이어받아」 | 이어받기 `session-pickup.md` |
| 「안전하게 멈춰」 | 안전하게 멈추기 `pause-safely.md` |
| 「이 큐 끝까지 오토파일럿」 | 오토파일럿 `autopilot-full.md` |
| 「오토파일럿, 머지는 하지 마」 | 오토파일럿 스택 `autopilot-stack.md` |
| 「평가 플레이북으로 돌려」 | 평가 `eval.md` |
| 「여러 날 걸리는 프로그램으로 돌려」 | 오케스트레이션 `orchestrate.md` |
| 「끝날 때까지 돌려」, 「자고 올게」 | 자율 실행 `autonomous-run.md` |
| 「계획만 세워」 | 여러 단계·여러 PR 계획 `multi-phase-plan.md`. 계획을 쓰고 구현하지 않는다 |
| 「몇 가지 안으로 시제품 만들어 비교」 | 프로토타입 `prototype.md` |

플레이북 목록과 언제 쓰는지의 정본은 `../mode/SKILL.md` 의 「플레이북」 절이다. 파일은 `../mode/playbooks/` 에 있다(조사, 버그 수정, 성능, 힐클라임, 런타임 포렌식, 트레이스 포렌식, 기능, 리팩터링, 프로토타입, 화면 일치, 스킬 작성, 평가, PR 돌보기, 내보내기, 자율 실행, 오토파일럿, 오토파일럿 스택, 이어받기, 안전하게 멈추기, 여러 단계 계획, 오케스트레이션, 워크트리 정리, PR 열기).

devkit 에는 계획 전용 스킬이 없다. Claude Code 의 계획 모드와 같이 써도 된다. 여러 단계나 쌓인 PR 에 걸친 일은 `/dev:mode` 에 계획을 달라고 하면 여러 단계 계획 플레이북이 계획만 쓴다. 설계 질문은 프로토타입 플레이북이나 `/dev:design` 이 코드로 먼저 정한다.

원칙은 `../mode/principles.md` 한 파일에 있다. `/dev:mode` 가 읽고 답에서 이름을 댄다. 사용자는 원칙을 부르지 않고 이름으로 방향을 튼다. 「Prove It Works 로 다시 봐. 진짜 출력을 보여 줘」, 「Fix Root Causes」, 「Laziness Protocol」. 목록과 언제 쓰는지는 `../mode/SKILL.md` 의 「원칙」 절이다.

## 잘못 돈 실행 바로잡기

| 증상 | 할 일 |
|---|---|
| 몇 턴 뒤 모드가 안 먹는다 | 모드는 그 메시지에만 붙는다. 작업마다 `/dev:mode` 로 다시 시작한다 |
| 질문이 지난 일의 다음 단계로 처리됐다 | 「새 작업」이라고 말하거나, 이 턴은 모드가 필요 없다고 말한다 |
| 모델을 바꿨는데 그대로다 | `~/.claude/rules/dev-models.md` 은 새 세션을 열 때 읽힌다. 새 세션에서 `/dev:mode` 로 시작한다. |
| 머지·배포를 안 하고 멈춘다 | 정상이다. babysit 은 머지 준비에서 멈추고, 배포는 되돌릴 수 없어 언제나 멈춘다. 그 말을 해야 한다 |
| 비용이 예상보다 크다 | 「설치와 설정」의 비용 문단 |
| 스킬이 알아서 안 뜬다 | 모든 devkit 스킬은 사용자가 치거나 `/dev:mode` 가 부를 때만 뜬다. `/dev:mode` 도 모든 스킬을 돌리지는 않는다 |
| 병렬 에이전트가 서로 덮어썼다 | 에이전트마다 자기 워크트리(`isolation: "worktree"`)를 준다 |
| 밤새 돌았는데 끝난 게 없다 | 통과·실패가 갈리는 확인 조건이 필요하다. 시간은 조건이 아니다. `/loop` 나 자율 실행 플레이북에 그 술어를 준다 |
| 빌드가 초록이라고 성공이라 한다 | 진짜 명령 출력, 화면 흐름 스크린샷, 저장된 값, 측정을 달라고 한다. Prove It Works 원칙이다 |
| 같은 실수를 또 한다 | 대화로 지적하면 `/dev:mode` 가 `/dev:correct` 로 장치를 넣는다. 모드 밖이면 `/dev:correct <지적>` |

흐르는 실행을 한 줄로 돌리는 말은 `references/prompting.md`, 따라 쓸 프롬프트는 `references/recipes.md` 에 있다.

## devkit 을 내 것으로

- `/dev:reflect` 가 세션의 교훈과 되풀이되는 교정을 devkit 저장소(포크)나 그 프로젝트 `AGENTS.md` 수정으로 바꿔 PR 로 올린다. 사용자가 승인한 것만.
- `/dev:correct` 는 지금 저장소의 실수를 구조·검사·훅으로 막는다. devkit 이 아니라 그 저장소를 고친다.
- `/dev:mode 이 작업 흐름으로 스킬을 써 줘` 는 스킬 작성 플레이북을 돈다. 평가 플레이북이 스킬 변경을 가린 채 시험한다.
- 이상하게 구는 스킬은 기능 작업 안에서가 아니라 따로 고친다(`/dev:reflect`).
- 포크를 공개해도 개인 이름이 새지 않게 `/dev:setup` 으로 `private_words` 를 채운다. devkit 을 고칠 때 `scripts/check.py` 가 막는다.

## 답하기

답을 먼저 쓴다. 예시 프롬프트는 많아야 하나, 코드 블록으로. 맞는 게 있으면 `references/recipes.md` 에서 고쳐 쓰고, 답이 나온 파일 경로를 붙인다. 사용자가 전체 지도를 달라고 하지 않았으면 짧게.
