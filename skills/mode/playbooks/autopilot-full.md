# 오토파일럿 (머지까지)

**판정을 소유하고 PR 은 소유하지 않는다. 담당 하나가 PR 하나를 만들기부터 머지까지 나르고, 코드를 쓰지 않은 너의 스웜이 착지할 코드를 증명하기 전에는 아무것도 머지하지 않는다.**

판정은 패치 하나를 덮고, 초록 CI 는 head 하나를 덮는다. 4단계는 전체 스웜을 한 번 돌리고, 큰 변경일 때만 다시 돌린다. `playbooks/shipping.md` 의 patch-id 규칙이 레인 결과를 이어 줄 수 있고, 새 head 마다 자기 초록 CI 가 필요하다.

1. **운영자의 관문이 먼저다.** 권한은 대기열 항목만 덮는다. 그래서 운영자가 자기 것이라고 한 항목과 대기열 밖 PR 은 머지 준비에서 멈춘다. 계획을 말해 달라는 요청은 시작 신호가 아니다.
2. **PR 마다 담당 하나를 띄우고, 대신할 에이전트가 찾을 수 있는 곳에 작업을 둔다.** PR 도구는 프로그램에 한 번 정한다. 기본은 GitHub CLI(`gh`)다. `command -v origin` 이 성공하고 Origin 이 저장소를 풀면 모든 PR 작업에 `origin pr` 을 쓴다. 아니면 `gh` 에 머물고 그렇게 물러났다고 기록한다. Graphite(`gt`)를 요구하지 않는다. 담당은 저마다 `Agent`(`subagent_type: "dev:worker"`, `isolation: "worktree"`)다. 담당은 만들고, `playbooks/opening-a-pr.md` 대로 PR 을 열고, 실제 산출물에서 변경을 증명하고, `playbooks/babysit.md` 대로 초록까지 babysit 하고, 4·5단계가 통과시키면 머지한다. 그 플레이북이 rebase 를 보고하라고 하는 곳에서 담당은 자기 브랜치를 직접 rebase 하고 `git push --force-with-lease` 로 올린다.

   PR 은 일찍 열어 CI 와 봇이 작업과 나란히 돌게 한다. 코드는 slop 걷어내기(`/dev:deslop`)와 `/dev:no-comments` 를 거친 뒤에야 준비된 것이다. 그래야 전체 스웜이 끝난 코드에서 돈다. 그다음 지금 trunk 에 rebase 하고, 자기 증명 전에 코드 준비 head 를 보고한다. 그래야 검증이 패치가 착지할 base 에서 돈다. 이후 head 도 모두 보고하고, 자기 증명·CI·babysit 이 끝나면 머지 준비를 보고한다. 고치는 회차는 그 base 에 머문다. trunk 가 충돌하거나, CI 를 깨거나, 같은 파일을 바꾸는 알려진 동시 변경을 들일 때만 rebase 한다. rebase 마다 CI 가 다시 돌기 때문이다. 코드 준비 push 전과, 검증자가 필요한 이후 push 전에, 건드린 경로에 대한 저장소 검사를 커밋된 head 에서 돌린다.

   작업 환경이 죽는다고 가정한다. 시작하자마자 push 하고, 루트 에이전트의 기록 저장소(루트가 브리프에 준 git 밖 경로)에 `/dev:log` 대로 결정 기록을 시작하고, 끝난 단위마다 push 한 뒤 다음을 시작한다. 서브에이전트를 띄우는 쪽은 그 id, 상태, 같은 종류의 지난 실행에서 잰 「이 시간이 지나면 막힌 것」을 그 저장소에 적는다. 부모가 죽어도 루트가 살펴볼 수 있게 하기 위해서다. force-push 는 자기 브랜치에만, 마지막으로 push 했거나 넘겨받은 SHA 에 묶은 `--force-with-lease` 로 한다. 자기가 하지 않은 push 를 보면 멈추고 루트에 보고한다.
3. **담당들을 trunk 에서 병렬로 돌린다. 쌓지 않는다.** 그래야 PR 마다 따로 착지한다.
4. **스웜 검증은 한 번 한다.** 전체 스웜은 코드 준비 head 에서 한 번 돈다. 다른 전체 스웜은 새 동작, 재설계, 큰 새 diff 일 때만 돈다. rebase, 머지 충돌 해결, 작은 수정은 새 head 에서 검증자 하나를 받고, 문구만 바뀐 변경은 아무것도 받지 않는다. `/dev:swarm` 대로 코드 준비 SHA 에서 독립 검증자들을 펼친다. 검증자는 관문을 다시 돌리고, 핵심 동작을 실제 표면에서 그 조작 스킬(`/dev:control-ui` 나 `/dev:control-cli` 같은 것)이나 이름 댄 드라이버로 직접 증명하고, diff 를 감사한다. 실사용 레인 없이, 또는 머지 준비 보고의 영수증을 감사하기 전에는 판정이 깨끗하지 않다. 어떤 레인도 확인하지 않은 주장을 믿지 않기 때문이다.

   PR 을 막는 것은 보여 줄 수 있는 문제뿐이다. head 에서 실패하는 실행이나, PR 이 틀리게 만든 문서 줄이다. PR 의 base(trunk 든 스택에서 아래 PR 이든)가 이미 가진 문제는, PR 이 그것을 베끼거나 새로 닿지 않는 한 막지 않는다. 사용자가 겪을 버그, 실패한 관문, 틀린 출시 문서만 막고 나머지는 모두 후속으로 간다.
5. **담당은 네가 검증하고 착지할 trunk 에서 시험한 것만 머지한다.** 초록 CI 만으로는 결코 머지를 허락하지 않는다. 스웜 레인이 시작된 뒤 머지 준비는 지금 trunk 에 rebase 하고, 새 head 를 보고하고, 초록 CI 를 기다린다.

   머지 직전에 trunk 를 fetch 하고 그 변경이 패치에 영향을 줄 수 있는지 묻는다. trunk 가 움직일 때마다 rebase 하면 끝나지 않기 때문이다. 착지할 코드가 시험된 적이 없으면 rebase 하고 CI 를 기다린다. 충돌, 양쪽이 바꾼 파일, PR 에 도는 체크를 바꾸는 변경이 그렇다. 양쪽이 바꾼 lockfile 은 머지 결과에서 frozen install 이 통과하고 PR 이 바꾼 패키지가 head 에서와 같이 풀리면 rebase 가 필요 없다. 그 install 이 착지할 lockfile 을 시험하기 때문이다. install 이 실패하면 rebase 로 고쳐야 한다. trunk 가 패치의 호출자나 패치가 기대는 것(부르는 코드, 의존성 버전 같은 것)을 바꿨으면 머지 결과에서 패치의 체크를 돌리고 통과하면 머지한다. 아니면 머지한다. 머지 준비 뒤 trunk 때문에 세 번째 rebase 를 해야 하면 멈추고 루트에 보고한다. 루트가 부딪치는 작업의 순서를 정한다.
6. **루트 층을 돌린다.** 관문을 느슨하게 하는 것(예산 올리기, 허용 목록 항목 같은 것)은 검증자의 증명과 너의 새 연서가 필요하다. 초록을 원하는 쪽이 담당이기 때문이다. 승인까지 덮는 권한 아래에서는 그 연서가 승인이고, 담당의 기록은 레인이 확인할 수 있게 너의 연서를 가리킨다. 끄거나 실패를 무시하게 한 체크는 늘 되돌린다. 모든 경우를 지키지 못하게 되기 때문이다. forge 가 강제하는 승인은 주지도 우회하지도 않는다. 어떤 연서도 그것을 덮지 못한다.

   운영자가 시작을 말하면 맡긴 일이 남지 않을 때까지 감사하도록 `/loop 1h` 를 건다. 긴 실행은 표류하고 에이전트는 조용히 멈추기 때문이다. 매 틱은 trunk 에서 이 플레이북을 다시 읽고 표류를 고친다. 보고 안 된 head, 기록 안 된 에이전트 같은 표류는 그 담당이 기록하게 한다. 표류는 기록의 빈틈이지 멈춤이 아니기 때문이다. 매 틱은 잎 레인까지 모든 에이전트를 살피고 부수 효과로 판단한다. 상태 글과 요약은 막힌 자식을 가릴 수 있기 때문이다. 오류가 나거나, 턴을 시작하지 못하거나, 「막힌 것」 시간이 지나도록 새것이 없으면 막힌 것이다. 첫 틱까지 push 도 기록 줄도 없는 담당도 막힌 것이다. 너나 운영자를 기다리는 에이전트는 막힌 것이 아니니 답해 준다. 막힌 에이전트는 그 멈춤이 처리되기를 기다리지 말고 바로 갈아 끼운다. 운영자에게 바뀐 것이 있는 틱은 `/dev:catchup` 대로 운영자를 따라잡게 하고 끝내고, 바뀐 것이 없는 틱은 조용히 있는다.
7. **운영자가 멈추라고 하면 바로 물러난다.** 보류는 모든 담당에게 「쓰기 0」 지시로 간다. 각 담당은 어디까지 왔는지 보고하고, 운영자가 풀 때까지 브리프를 쥐고 있는다.

**답:** `/dev:catchup` 대로 운영자를 따라잡게 한다. PR 마다 상태와 판정, 무엇이 머지됐는지, 연서와 그 이유, 열린 운영자 관문, 미뤄 둔 후속을 다루고, 각 PR 과 기록의 링크를 붙인다.
