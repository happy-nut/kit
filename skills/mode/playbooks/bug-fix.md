# 버그 수정

**이 일을 소유한다. 계획하고, 리뷰하고, 검증한다.** 원인 조사와 수정은 서브에이전트에 맡기고 리드는 놓지 않는다. 서브에이전트마다 mode 「서브에이전트」 절대로 일에 맞는 추론 수준을 고른다.

과학적으로 한다. 내보내는 모든 줄은 런타임 증거로 이어진다. 「도움이 될지도」 싶은 이중 안전장치는 가설이지 수정이 아니다. 내보내지 않는다. 증거가 가설을 반박하면 그 가설 때문에 넣은 것을 되돌린다. 증거가 정당화하는 가장 작은 변경만 내보내고 그 이상은 내보내지 않는다.

1. 맞는 표면에서 조종 스킬(`/dev:control-ui` 나 `/dev:control-cli`, mode 「꼭 지킬 것」)로 직접 재현한다. 디버그나 계측 절차가 사용자에게 재현을 부탁하라고 해도 직접 한다. 사용자에게 부탁하는 것은 조종 수단이 대상에 닿지 못하는 구체적 이유를 밝혔고, 닿는 데까지 몰아 본 뒤뿐이다. 바로 재현되지 않으면 계기를 합성하거나, 조건을 조이거나, 터질 때까지 계측한다.
2. 원인을 이분 탐색한다. 후보 가설을 세우고 하나가 남을 때까지 지운다. 가설의 씨앗은 영향받는 하위 시스템의 추적과 회귀 이력을 보는 `/dev:why` 다. 회차마다 남은 문제 공간을 가장 많이 자르는 분할을 골라 런타임 증거를 얻고 지운다. 프로그램 상태가 불분명하면 계측이나 로그를 넣고 코드가 도는 동안 읽는다. 짐작하지 않는다. 길거나 끈질긴 추적은 Claude Code `/loop` 스킬로 몬다. 3단계의 `/dev:design` 이나 `/dev:review` 팬아웃 전에 살아남은 *메커니즘*을 런타임 증거로 확정한다.
3. 수정을 계획한다. 함수 경계를 넘으면 먼저 `/dev:design`. 구현은 범위를 구체적으로 정해 `bug-fix` 역할 모델(mode 「서브에이전트」 절)의 서브에이전트에 맡긴다.
4. 같은 표면에서 검증한다. 원래 재현이 이제 통과한다. 「판단 불가」나 다른 표면은 통과가 아니다. 그렇게 표시한다. 단위 테스트는 분기 동작을 보여 줄 뿐 버그가 없다는 증거가 아니다.
5. 실패하는 재현이 수정보다 먼저 git 이력에 들어가게 커밋을 나눈다. 버그에 값싼 로컬 테스트 경로가 있으면 `/dev:tdd` 의 실패 테스트 먼저 순서를 본다. 테스트가 비싸거나, 통합 위주이거나, 모양이 불분명하면 건너뛴다.
   principles.md 의 Sequence Work into Verifiable Units 의 정석이다. 실패 테스트가 먼저, 수정이 그 위다.
6. `playbooks/opening-a-pr.md` 를 돌린다.

**답:** 무엇이 깨졌나, 근본 원인, 수정, 검증 방법. 실패하던 재현 출력과 통과하는 재현 출력을 그대로 붙인다.
