# 기능

**설계를 소유한다. 계획하고, 리뷰하고, 검증한다.** 구현은 맡긴다. 리드는 놓지 않는다.

1. 영향받는 하위 시스템을 추적한다.
2. `/dev:design` 으로 모양을 정한다.
3. 처리량 점검을 작업 목록 항목 네 개로 쓴다. 정말 해당하지 않는 항목(파일 하나, 팬아웃 없음)도 지우지 않고 `n/a: <이유>` 로 남긴다.
   - **먼저 막는 단계.** 관문은 팬아웃 전에 돈다.
   - **독립 작업 줄기.** 겹치지 않는 파일, 서비스, 레이어는 병렬로 간다. 같은 곳에 쓰는 일은 직렬로 간다.
   - **공유 가변 상태.** 기본은 대상을 쪼갠다(principles.md 의 Separate Before Serializing Shared State). 진짜 불변식이 있을 때만 직렬화한다.
   - **가장 작은 안전한 분해.** 워커 하나가 최선이면 이유를 적는다.
4. 코드 작성은 `feature, refactoring` 역할 모델(기본 `opus xhigh`)의 서브에이전트에 구체 범위로 맡긴다. 범위에는 파일 경로, 이름 붙인 데이터 모양과 그 조직 구조(principles.md 의 Model the Domain), 성공 기준을 넣는다. 조직 구조는 흩어진 boolean 대신 상태 기계, 분기 대신 표나 레지스트리, 반복되는 모양 가정 대신 타입 모델이고, 서브에이전트가 로직을 쓰기 전에 정한다. 서브에이전트마다 일에 맞는 수준을 `/dev:mode` 「서브에이전트」 절대로 고른다. 구현 모양이 여럿 가능하면(오류 처리, 추상화 층, 테스트 구조) `/dev:design` 의 겨루기로 맡겨, 러너들이 대안을 드러내고 교차 심사가 고른 것을 지키게 한다. 필수다. 「이유 적고 생략」은 없고, Laziness Protocol 도 이것을 넘지 못한다(얻는 것은 줄 수 절약이 아니라 리뷰 분리다). 서브에이전트를 띄울 수 없는 에이전트는 같은 리뷰 분리를 지키며 diff 를 직접 소유하는 것으로 채운다. 중첩 에이전트를 기다리며 「대기 중」으로 답하지 않는다. 편집은 외과적으로 한다. 상류에서 파생된 파일은 원본에 다시 맞춰 본다. 공유 프리미티브를 개선하면 모든 소비자에 옮기고 각각 검증한다. 커밋은 자주 한다.
5. 같은 표면에서 검증한다. 「판단 불가」나 다른 표면의 결과는 통과가 아니다. 그렇게 표시한다.
6. 작고 순서 있는 커밋으로 rebase 한다. 후속은 위에 쌓는다.
   principles.md 의 Sequence Work into Verifiable Units 대로 작은 단위마다 만들고, 검증하고, 커밋한 뒤 다음으로 간다.
7. 설계에 이견이 있으면 내보내기 전에 `/dev:review` 를 돌린다.
8. `opening-a-pr.md` 를 따른다.

코드가 엮인 일(기능 하나, 마이그레이션 하나)은 처리량 점검을 품은 owner 하나에게 준다. 그 owner 가 먼저 막는 단계 뒤에 안에서 팬아웃한다. 부모 수준 팬아웃은 독립 산출물을 내는 조각(감사, 하위 시스템을 가로지르는 조사, 경쟁 실험)에 쓴다. phase 경계마다 처리량 점검을 다시 쓴다. 끼어들기를 이어 붙이지 말고 새 owner 를 띄운다.

**답:** 만든 것, 고른 것과 그 이유, 처리량 점검, 열린 결정. 설계 대안은 표로.
