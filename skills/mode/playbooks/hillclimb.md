# 힐클라임

**지표와 실험의 정직함을 소유한다. 감독하고 리뷰한다. 시도는 맡긴다.** 측정할 수 있는 것 하나를 목표까지 꾸준히, 되풀이해 끌어올리는 일이다. 한 번 고치는 일은 `playbooks/bug-fix.md` 나 `playbooks/perf-issue.md` 다. 이것은 루프다.

핵심 규율은 변경 하나, 측정 하나, 남기거나 되돌리기다. 시험하지 않은 변경을 쌓지 않고, 코드를 읽고 이겼다고 하지 않는다(principles.md 의 Prove It Works).

1. 지표를 고르기 전에 워크로드와 구조를 파악한다. 대상을 추적하고, 결과를 움직일 수 있는 현실적 워크로드 차원(데이터 크기, 이력, 상태, 동시성)을 이름 짓고, 사용자의 불만을 재현하는 케이스를 고른다. 재현하는 케이스가 없으면 힐클라임 말고 재현부터 고친다. 그다음 지표 하나, 더 나은 쪽으로 치는 방향, 확인할 수 있는 정지 조건을 정한다. 정지 조건은 목표와 최소 시도 횟수를 짝지어 운 좋은 초반 승리로 실행이 끝나지 않게 한다(예시 「기준선보다 50% 이상 좋아지고 10회 이상 반복」이 이 모양이다). 사용자가 숫자를 주면 그것을 쓰고, 아니면 합의한다.
2. 측정 하네스를 만들고, 민감도를 증명하고, 동결한다(principles.md 의 Build the Lever). 대비되는 현실 워크로드를 돌려 목표 케이스가 증상을 재현하고 쉬운 케이스가 예상대로 갈리는지 확인한다. 하네스가 둘을 구분하지 못하면 워크로드나 지표를 고친다. 동결 전에 `/dev:bench` 로 하네스를 검토하고, 하네스가 오류 수와 한 일의 양을 찍게 한다. 동결 뒤에는 되풀이할 수 있는 명령 하나가 잡음을 넘을 만큼 표본을 뽑아 지표를 낸다(한 번 실행이 아니라 N 회 중앙값). 어떤 변경보다 먼저 기준선 지표와 회귀 관문(계속 통과해야 할 테스트)의 초록 실행을 기록한다.
3. `/dev:log` 로 결정 기록을 연다. `decision.tsv` 에 시도마다 한 줄. 열은 id, hypothesis, change, before, after, delta, tests, verdict(kept 또는 reverted), note. 매 시도 전에 읽는다. 저장소 트리 밖에 둔다(gitignore).
4. 가설마다 1단계의 구조 모델에 근거를 두어, 「뭔가 메모이즈해 본다」가 아니라 구체 메커니즘(「첫 그리기를 막으니 X 를 부팅 경로 밖으로 미룬다」)을 이름 짓게 한다. 성능 지표면 성능 문제 플레이북(`playbooks/perf-issue.md`) 2단계의 성능 주문 순서로 가설을 줄 세운다. 그 순서만 빌리고 그 단계의 정지 규칙은 빌리지 않는다.
5. 회차마다 가설 하나로 돈다.
   - 범위를 좁게 정해 `hillclimb` 역할 모델(mode 「서브에이전트」 절)의 서브에이전트에 변경을 맡긴다. 서브에이전트마다 mode 「서브에이전트」 절대로 일에 맞는 추론 수준을 고른다. 직접 치지 말고 감독하고 diff 를 리뷰한다(principles.md 의 Guard the Context Window). 독립 가설이 여럿 살아 있으면 저마다 자기 워크트리(`isolation: "worktree"`)를 가진 병렬 서브에이전트로 펼친다(principles.md 의 Separate Before Serializing Shared State).
   - 동결한 하네스로 전후를 재고, 회귀 관문을 돌린다.
   - 지표가 잡음을 넘어 움직이고 관문이 초록일 때만 받아들인다. 아니면 변경을 통째로 되돌린다. 「도움이 될지도」 싶은 손질은 남기지 않는다.
   - 받아들인 수정마다 커밋 하나. 바꾼 파일만 스테이징한다(`git add <files>`, `-A` 는 쓰지 않는다). 남기든 되돌리든 기록 한 줄을 남긴다.
   회차마다 다음 회차가 시작되기 전에 검사로 끝낸다(principles.md 의 Sequence Work into Verifiable Units). 사람 없이 돌면 자율 실행 플레이북(`playbooks/autonomous-run.md`)의 깨우기 장치만 빌리고 그 정지 규칙은 빌리지 않는다.
6. 첫 정체를 넘는다. 멈추거나 거절이 여러 번 이어지면, 다 올랐다고 결론짓기 전에 범주를 바꾸거나, 아깝게 진 것들을 묶거나, 소스를 다시 읽거나, 더 과감한 것을 시도한다. 정확성과 단순성이 숫자보다 앞선다. 동작을 깨는 승리는 되돌리고, 숫자를 지키는 단순화는 남긴다(principles.md 의 Laziness Protocol).
7. 정지 조건을 채우거나, 남은 아이디어가 사소해 비용만큼 값하지 않을 때 멈춘다. 조건을 채우려고 조건을 느슨하게 하지 않고, 시도 안 한 값싼 가설이 남았으면 그만두지 않는다. 막히면 헛돌지 말고 드러낸다.
8. 받아들인 커밋을 들어간 순서대로 쌓아 `playbooks/opening-a-pr.md` 를 돌린다.

**답:** 지표와 목표, 기준선에서 최종까지와 그 퍼센트 차이, 돈 회차 수(남김 대 되돌림), 받아들인 수정 하나에 한 줄씩, `decision.tsv` 경로, 더 간다면 다음에 해 볼 가장 좋은 아이디어.
