# 여러 단계·여러 PR 계획

**언제.** phase 여러 개나 쌓인 PR 여러 개에 걸친 일을 계획한다.

**소유.** 계획을 소유하고 코드는 소유하지 않는다. 계획은 담당이 칸마다 실행하고 사용자가 증거로 감사하는 체크리스트다. 계획이 산출물이다. 구현하지 않는다.

## 단계

1. 파일 한두 개에 접근이 뻔한 변경이면 계획을 건너뛴다.
   그렇다고 말하고 멈춘다.
2. 쓰기 전에 열린 질문을 `prototype.md` 로 정한다.
   어떤 실행으로도 정할 수 없는 제품·취향 결정만 사용자에게 `AskUserQuestion` 으로 묻고, 답을 기다리는 동안 나머지를 쓴다(principles.md 의 Never Block on the Human).
3. 계획 파일을 쓴다.
   사용자가 경로를 말하지 않으면 저장소 밖 `~/.claude/plans/<slug>.md` 에 쓴다. 맨 앞에 무엇이 바뀌는지, 착지 순서대로 PR id, 의존 그래프를 둔다. 의존 그래프는 어느 PR 이 독립이라 trunk 에서 따는지, 어느 PR 이 무엇을 기다리는지, PR 마다 건드려도 되는 파일을 적는다. 실행 플레이북도 적는다. 실행이 머지까지 해도 되면 `autopilot-full.md`, 사용자가 PR 을 착지시키면 `autopilot-stack.md`. 그다음 PR 하나에 절 하나. PR 하나는 자기 증거를 가진 변경 하나다(principles.md 의 Sequence Work into Verifiable Units). 절마다 의존, 고칠 파일, 만들 변경 하나, 보이는 결과, 검증을 체크 칸으로 둔다. `/dev:write` 로 쓴다.
4. 검증 칸을 채운다.
   테스트만으로는 검증이 아니다. PR 은 단위·실사용·성능 칸이 모두 체크돼야 검증된 것이다(principles.md 의 Prove It Works). 실사용 칸마다 그 표면의 조종 수단(웹은 브라우저 도구, CLI 는 터미널, `/dev:verify-setup` 으로 만든 검증 스킬이 있으면 그것)으로 실제 표면을 모는 구체 시나리오와 통과 조건을 적는다. 성능 칸은 지표, 측정, 먼저 잰 trunk 기준선, 실패하는 숫자를 적는다. 상호작용을 바꾸는 PR 은 머지 전에 사용자의 리뷰를 기다린다.
5. 넘긴다.
   계획 경로를 올리고 멈춘다. 실행은 사용자가 시작을 분명히 말한 뒤에, 계획이 적은 실행 플레이북으로 한다.

## 답변에 넣을 것

- 계획 경로.
- PR id 와 의존 관계, 리뷰 관문 대상 묶음.
- 증명되지 않은 채 남은 것.
