# 오케스트레이션

**언제.** 코디네이터 대화 하나가 맡은 상시 프로그램을 돌린다. 여러 날 걸리고, 쌓인 PR 이 많고, 서브에이전트가 수십에서 수백이고, 사람 턴은 적다. 술어 하나까지 모는 일 하나는 `autonomous-run.md` 다. 맞춤 흐름이 필요한 야심 찬 실행 하나는 `/dev:mode` 의 「맞춤 플레이북」이다. 에이전트 하나가 세션 예산 안에 끝낼 일은 프로그램이 아니다.

**소유.** 프로그램을 돌리고 코드는 돌리지 않는다. 일마다 어느 에이전트가 할지 정하고, 각자 만든 것을 확인한다.

자기 도구로 돌린다. 워커는 `Agent` 로 띄운다. 프로그램 상태는 저장소 밖 노트 파일 하나 `~/.claude/devkit/programs/<프로그램>/notes.md` 에 둔다. 같은 폴더에 산출물(스크린샷, 실측 표, 워커 보고)을 모은다. 워크트리를 지우거나 브랜치를 바꿔도 남고 커밋에 섞이지 않게 하기 위해서다. 노트에는 목표, PR 마다 소유자 agent id·브랜치·마지막 head SHA·판정, 띄운 워커 전부와 그 상태, 사용자 결정 대기 목록을 적는다. PR 마다 `gh pr checks <pr> --watch` 를 Bash `run_in_background: true` 로 걸어 CI 가 끝나면 깨어나게 한다. 별도 스크립트를 부르지 않고, 폴링 루프를 돌리지 않고, 에이전트끼리 메시지나 상태를 대신 전하지 않는다.

## 토폴로지

- **PR 하나에 소유자 하나.** 소유자만 그 브랜치에 쓰고, 만들기부터 머지까지 PR 을 나른다. push, rebase, base 바꾸기도 소유자만 한다. base PR 을 닫거나 base 를 바꾸면 그 위 PR 이 모두 고아가 되니, 소유자는 그것을 코디네이터가 시킬 때만 한다. 코디네이터는 코드를 쓰지도 고치지도 않는다. 충돌 난 머지, 연쇄 rebase, 수정은 소유자에게 간다.
- **독립 일마다 새 워커.** 킥오프에 필요한 것을 전부 넣는다. 기대는 앞 단계 보고는 줄이지 않고 통째로 붙인다. 워커는 형제를 보지 못한다. 워커는 `Agent`(`subagent_type: "dev:worker"`, `isolation: "worktree"`, `run_in_background: true`)다. 원격 실행을 쓸 수 있으면 `isolation: "remote"` 로 띄운다. 단, 이 머신이 필요한 일은 `"worktree"` 로 둔다. 이 머신에서 브라우저 도구나 터미널로 실제 표면을 확인하는 일, 로컬 대화 기록, 시뮬레이터, 이 머신에만 있는 인증이 그렇다. 모델은 일에 맞게 `/dev:mode` 의 「서브에이전트」 절대로 고른다.
- **하위 코디네이터는 한 영역에 병렬 워커가 많을 때만.** 하위 코디네이터가 그 영역의 워커와 킥오프를 소유하고, 날 워커 보고가 아니라 묶은 보고 하나를 올린다. 층은 셋에서 멈춘다. 코디네이터, 하위 코디네이터, 워커. 코디네이터 하나당 동시에 도는 워커는 10개 안팎으로 둔다. 묶음 전체를 기다리지 말고 하나가 끝날 때마다 다음 하나를 띄운다.
- **새 일이 워커가 쌓은 상태를 필요로 할 때 fork 한다.** 그 체크아웃, 커밋 안 한 변경, 돌고 있는 프로세스 같은 것이다. 이때만 그 워커를 이어 쓴다. 메시지(`SendMessage`)는 같은 일의 후속에만 보낸다. 확인하려고 보내지 않는다. 메시지가 쉬던 에이전트를 다시 돌리기 때문이다.
- **PR 마다 작성자가 아닌 검증자를 붙인다.** 검증자는 작성자와 다른 `model` 이다(`opus`, `fable`, `sonnet` 중 작성자가 쓰지 않은 것). 모두 같은 회사 모델이라 시각의 다양성이 약하다는 것을 판정과 보고에 적는다. 소유자는 지금 head 에서 그 검증자가 통과시켰을 때만 머지한다.
- **한 단위로 먼저 시작한다.** 하나를 킥오프, 소유자, 검증자, 머지까지 끝까지 돌린 뒤에 펼친다. 킥오프에 흠이 있어도 에이전트 쉰 개가 아니라 하나만 잃는다. 거의 같은 값싼 단위들이면 첫 단위가 그 시험이다.

## 감독

- **킥오프마다 일이 끝났다는 증거를 적는다.** 명령과 기대 출력, 브라우저·터미널로 하는 실제 표면 확인, 산출물 같은 것이다. 목표, 써도 되는 경로와 쓰면 안 되는 경로, 하면 안 되는 행동도 적는다. 증거를 적을 수 없으면 그 단위는 아직 범위가 정해지지 않은 것이다.
- **워커 요약만 보지 말고 diff 나 산출물을 읽는다.** 초록 CI 는 판정의 입력이지 판정이 아니다. 동작을 바꾸는 일은 타입 검사로는 모자란다. 판정은 head SHA 하나를 덮는다. 새 push 는 새 판정이 필요하다. 하위 코디네이터의 워커가 도는 동안 그 킥오프 몇 개를 표본으로 읽고, 하나가 실패하면 하위 코디네이터의 지시를 고친다.
- **범위를 벗어나거나 시킨 것보다 커진 일은 돌려보낸다.** 프로그램을 막는 수정만 남기고 나머지는 후속으로 노트에 둔다.
- **PR 을 보고하기 전에 라이브 상태를 본다.** 워커의 마지막 보고가 아니라 `gh pr view` 와 `gh pr checks` 로 본다. 띄운 워커 하나하나를 끝남, 교체됨, 다른 워커 범위로 흡수됨 중 하나로 노트에 정리한다.
- **멈추거나 맴도는 워커는 세우거나 바꾼다.** 상태 글이 아니라 push 와 PR 활동으로 판단한다. 재시도는 원인별로 한다. 컨텍스트나 메모리 한계면 범위를 줄여서, 연결이 끊겼으면 같은 킥오프로, 도구 오류면 다른 모델로. 재시도 2번 뒤에도 안 되면 그 단위를 버리고 그것을 빼고 다시 계획한다. 세운 워커가 늦게 돌아오면 그 결과를 PR 의 지금 상태와 대조하고, 그 워커만 찾은 것은 새 워커에게 넘긴다.
- **사용자에게는 진짜 결정이나 막힘만 묻는다.** 되돌릴 수 없는 행동, 어떤 실험으로도 정할 수 없는 제품·취향 결정, 다시 계획해도 남은 막다른 길 같은 것이다. rebase 절차, 재시도, 불안정한 CI, 리뷰 분류, 「계속할까요」는 사용자에게 가지 않는다.

## 답변에 넣을 것

- 목표 대비 무엇이 착지했는지.
- PR 마다 라이브 상태와 판정, 링크.
- 무엇을 버렸고 왜.
- 사용자 결정을 기다리는 것.
