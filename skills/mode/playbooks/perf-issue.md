# 성능 문제

**측정 이야기를 소유한다. 계획하고, 리뷰하고, 숫자를 검증한다.** 모든 수정을 측정에 묶는다. 측정 대신 소스를 읽지 않는다.

1. 맞는 조종 스킬(`/dev:control-ui` 나 `/dev:control-cli`)로 기준선 trace 를 잡는다. 기준선과 이후의 모든 숫자는 `/dev:bench` 로 검토한다.
2. 코드를 추적해 가설의 근거를 잡는다. 먼저 돌려 보지 않고 성능 한계를 주장하지 않는다.
   성능 주문을 싼 것부터 순서대로 시도한다.
   1. 하지 마라. 결과를 아무것도 안 쓰는 일은 싸게 만들지 말고 멈춘다.
   2. 하되, 두 번 하지 마라.
   3. 덜 해라.
   4. 나중에 해라.
   5. 안 볼 때 해라.
   6. 동시에 해라.
   7. 싸게 해라.

   앞의 주문이 목표에 닿으면 멈춘다.
3. trace 를 근거로 수정을 계획한다. 함수 경계를 넘으면 먼저 `/dev:design`. 구현은 `perf-issue` 역할 모델(mode 「서브에이전트」 절)의 서브에이전트에 맡긴다. 서브에이전트마다 mode 「서브에이전트」 절대로 일에 맞는 추론 수준을 고른다. diff 를 리뷰한다. 수정 뒤 trace 를 잡는다.
   principles.md 의 Sequence Work into Verifiable Units 를 적용해, 시도 하나를 검증한 뒤 다음 시도로 간다.
4. 산출물을 파싱해 비교한다(JSON 을 sqlite 로, diff). 「판단 불가」나 다른 표면은 통과가 아니다. 그렇게 표시한다.
5. PR 에 측정을 인용한다.
6. `playbooks/opening-a-pr.md` 를 돌린다.

한 번의 수정이 아니라 지표를 꾸준히 끌어올리는 일이면 힐클라임 플레이북(`playbooks/hillclimb.md`)을 쓴다.

**답:** 기준선 숫자, 수정 뒤 숫자, 차이, 산출물 경로.
