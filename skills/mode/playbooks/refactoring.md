# 리팩터링

**계약을 소유한다. 구조는 바뀌고 동작은 바뀌지 않는다.** 동작을 더하는 `feature.md`, 동작을 고치는 `bug-fix.md` 와 다르다.

정리하다 빠진 기능이나 진짜 버그를 찾으면 따로 떼어 내고, 구조 변경을 고정한 계약 위에서 먼저 내보낸다. 재설계도 할 수 있지만 재설계라고 이름 붙여 `feature.md` 로 보낸다. 크거나 여러 곳을 가로지르는 구조 작업은 `/dev:mode` 의 「맞춤 플레이북」 절로 간다. 이 플레이북은 작거나 중간 크기 변경용이다.

1. 동작 계약부터 고정한다. 영향받는 하위 시스템을 추적해 계약을 알아내고, 구조를 하나라도 옮기기 전에 지금 동작을 잡는 특성 테스트, 스냅샷, 등가 하네스를 쓴다. 그 영역에 테스트가 없으면 구조를 건드리기 전에 고정부터 쓴다. 타입 검사와 린트는 고정이 아니다.
2. 코드에 빠진 구조를 이름 짓는다(principles.md 의 Model the Domain). 모양이 이미 분명하고 국소적이면 지루한 코드는 그대로 둔다. 새 모양은 분기나 잘못된 상태를 지워야 한다. 간접층을 더하면 안 된다.
3. 목표 모양을 이름 짓는다. 오늘 새로 만든다면 모듈 배치, 타입, 호출 그래프가 어떠해야 하는지 적는다(principles.md 의 Foundational Thinking, Redesign from First Principles). 목표가 함수 경계를 넘으면 옮기기 전에 `/dev:design` 으로 모양을 정한다.
4. 더하기 전에 뺀다. 새 모양을 들이기 전에 죽은 코드를 지우고, 호출자가 하나뿐인 래퍼를 접고, 중복 검증기를 빼고, 고아 참조를 없앤다(principles.md 의 Subtract Before You Add). 목표 모양에 닿는 가장 작은 변경을 내보낸다(principles.md 의 Laziness Protocol). 「도움이 될지도」 싶은 추측성 정리는 되돌린다.
5. 동작을 보존하는 작은 걸음으로 옮긴다. 걸음마다 고정이 초록이어야 한다. API 모양을 바꾸면 모든 호출자를 옮기고 옛 API 를 같은 물결에서 지운다(principles.md 의 Migrate Callers Then Delete Legacy APIs). 호환 shim 도, 옛길과 새길을 나란히 두는 것도 없다. 이름 바꾸기는 실제 파일에서 하나하나 확인한다. 이름 바꾸기는 문자열, 산문, 역참조에서 조용히 빠진다. 기계적 편집은 `feature, refactoring` 역할 모델(기본 `opus xhigh`)의 서브에이전트에 구체 범위(파일 경로, 옮기는 이름, 지킬 동작)로 맡긴다. 서브에이전트마다 일에 맞는 수준을 `/dev:mode` 「서브에이전트」 절대로 고른다.
6. 실제 산출물에서 동작이 그대로임을 증명한다. 「컴파일된다」는 증명이 아니다(principles.md 의 Prove It Works). 큰 변경은 등가 검사를 돌린다. 옛 출력과 새 출력을 diff 하는 스크립트, 기록한 기준선을 새 코드에 재생하기, 또는 맞는 표면에서 `/dev:control-ui` 나 `/dev:control-cli` 로 스모크 실행.
7. 남길 가치가 있는지 확인한다. 성공 기준은 읽는 사람의 부담이 줄었는가다(principles.md 의 Minimize Reader Load). diff 가 어디서도 읽는 부담을 줄이지 못하면 되돌린다.
8. 작고 순서 있는 커밋으로 rebase 한다. 빼는 커밋, 그다음 모양 바꾸기, 그다음 후속 정리. principles.md 의 Sequence Work into Verifiable Units 대로 동작을 보존하는 조각마다 초록을 지킨 뒤 다음으로 간다. `opening-a-pr.md` 를 따른다.

**답:** 바뀐 구조, 기준으로 삼은 고정, 등가 증명, 읽는 부담의 변화, 내보낸 것과 되돌린 것. 새 동작은 없다.
