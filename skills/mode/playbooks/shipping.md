# 출시

**언제.** `babysit.md` 다음 절반. 초록 스택을 PR 마다 따로 검증하고, 아래에서부터 이어지는 검증된 구간만 `gh` 로 착지시킨다.

**소유.** 무엇이 착지하는지를 소유한다. PR 마다 따로 검증하고, 뿌리에서부터 검증된 구간만 착지시키고, 그동안 스택에서 손을 뗀다. 초록은 안전이 아니다. PR 마다 따로 판정하기 전에는 아무것도 auto-merge 를 걸지 않는다.

## 단계

1. 착지 전에 PR 마다 따로 검증한다.
   PR 도구는 `opening-a-pr.md` 6단계대로 `gh` 가 기본이고 `gt` 를 요구하지 않는다. PR 하나에 검증자 하나. 검증자는 `Agent`(`subagent_type: "dev:worker"`, `model: "sonnet"`, `isolation: "worktree"`, `run_in_background: true`)로 띄운다. 검증자는 사용자가 쓰듯 그 표면을 몰아 본다. 웹은 브라우저 도구(Claude in Chrome, 내장 브라우저, playwright), CLI 는 터미널, 앱마다 검증 스킬이 있으면 그것(`/dev:verify-setup` 으로 만든 것). 부모와 head 를 비교하고 `PASS`, `PASS+NOTES`, `FAIL` 중 하나를 그 PR 에 남긴다(`gh pr comment <pr> --body-file <file>`). 화면 변경이면 기능마다 스크린샷을 같이 남긴다. 코드를 쓰지 않은 에이전트의 판정만 센다. 작성자는 만들려던 것을 확인하기 때문이다. 초록 CI 와 승인한 봇 리뷰는 판정이 아니다. 둘 다 사용자처럼 변경을 돌려 보지 않는다.
2. 맨 아래에서 이어지는 검증된 구간만 착지시킨다.
   가장 아래 머지 안 된 PR 에서 위로 걸어가다 `PASS` 나 `PASS+NOTES` 가 없는 첫 PR 에서 멈춘다. 그 아래 PR 들이 구간이고 맨 위가 천장이다. 검증 안 된 PR 위의 검증된 PR 은 기다린다. 아래 코드 없이 착지할 수 없기 때문이다. 브랜치가 그 코드를 품지도 필요로 하지도 않는 PR 은 trunk 로 옮겨 따로 착지할 수 있다. 다만 새 판정이 먼저다. 옛 판정은 그 코드를 아래 깔고 돌았고 trunk 에는 그 코드가 없다.
3. 판정이 아직 코드를 설명하는지 다시 확인한다.
   판정은 패치 하나를 덮는다. 사슬 rebase 는 위의 PR 을 모두 새 SHA 로 옮기면서 어떤 체크도 깨뜨리지 않는다. 옛 판정을 믿기 전에 판정 SHA 와 지금 head 의 `git patch-id` 를 비교한다. 패치가 테스트, 문서, lint 설정에서만 다르면, 그 레인이 돌린 것이 두 SHA 에서 잡음 말고는 똑같이 빌드될 때 레인 결과가 유지된다. 잡음은 판정 SHA 를 두 번 빌드해도 나는 차이이거나 박혀 들어간 커밋 SHA 다. 잡음은 종류마다 파일과 함께 보고해 읽는 사람이 판단을 확인할 수 있게 한다. 변경 자체는 옛 판정이 본 적이 없으니 새 체크와 리뷰를 받는다. 빌드 산출물이 없는 레인(dev 서버 등)은 이것을 보여 줄 수 없으니 다시 돌리고, 그 밖에 바뀐 것도 다시 검증한다.
4. 아래에서 위로 한 번에 하나씩 착지시킨다.
   늘 구간의 가장 아래 머지 안 된 PR 을 `gh pr merge <pr> --squash` 로 머지한다. base 가 아직 부모 브랜치인 PR 은 trunk 가 아니라 그 브랜치로 머지된다. 결과는 `gh pr view <pr> --json state,mergedAt,baseRefName` 로 다시 읽는다. merge queue 가 줄만 세웠을 때도 머지 명령은 성공이라고 할 수 있고, auto-merge 요청은 머지가 아니다. 착지한 PR 은 merged 이고 base 가 부모 브랜치가 아니라 trunk 다. `--auto` 는 판정이 지금 head 를 덮는 PR 에만 건다. 준비되는 head 가 무엇이든 착지시키기 때문이다. 머지가 착지하면 base 가 머지된 브랜치였던 PR 을 trunk 로 돌리고(`gh pr edit <pr> --base <trunk>`), 그 패치를 머지 결과 위로 옮기고, `--force-with-lease` 로 push 한다. 판정은 커밋이 아니라 패치를 덮으니 3단계의 patch-id 규칙이 판정이 살아남는지 정한다. 체크가 통과하고 판정이 살아남으면 머지한다.
5. 착지하는 동안 스택을 건드리지 않는다.
   4단계의 다음 PR 옮기기가 브랜치나 base 를 바꾸는 유일한 일이다. 머지는 그 순간 브랜치와 base 가 품은 것을 판정과 상관없이 착지시키기 때문이다. 구간은 `gh pr view <pr> --json state,mergedAt,baseRefName` 와 `gh pr checks <pr> --watch` 로 지켜본다. `--watch` 를 Bash `run_in_background: true` 로 걸고, 끝날 때마다 다시 읽고, 긴 기다림은 `/loop` 스킬이나 ScheduleWakeup 으로 깨운다. 천장이 merged 로 읽힐 때까지 간다. 부모가 머지되면서 base 가 trunk 로 옮겨지는 것은 예상된 일이지 고칠 손상이 아니다. 머지가 멈추면 무엇이든 바꾸기 전에 왜인지 알아낸다.
6. 천장에서 멈춘다.
   구간을 늘리려면 새 판정이 필요하니 1단계부터 새로 돈다.
7. 배포까지 시켰으면 배포 뒤 상태를 확인한다.
   배포는 되돌릴 수 없는 쓰기라 시키지 않았으면 언제나 멈춘다(`/dev:mode` 의 「자율」). 시켰으면 저장소의 배포 절차대로 올리고, 실제 서비스(화면이면 띄워서 스크린샷, 서버면 상태·로그)를 보고 끝낸다.

## 답변에 넣을 것

- 검증된 구간과 천장.
- PR 마다 판정과 그 판정을 낸 에이전트.
- 무엇이 착지했고 어떻게 확인했는지(`gh pr view` 결과).
- 다음 빈틈에 무엇이 필요한지.
