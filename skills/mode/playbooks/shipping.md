# 출시

**무엇이 착지하는지를 소유한다. PR 마다 따로 검증하고, 뿌리에서부터 검증된 구간만 착지시키고, 그다음 스택에서 손을 뗀다.**

1. **PR 도구를 정하고, 착지 전에 PR 마다 따로 검증한다.** 기본은 GitHub CLI(`gh`)다. `command -v origin` 이 성공하고 Origin 이 저장소를 풀면 모든 PR 작업에 `origin pr` 을 쓴다. 아니면 `gh` 에 머물고 그렇게 물러났다고 기록한다. Graphite(`gt`)를 요구하지 않는다. PR 하나에 검증자 하나다. 검증자는 저마다 `Agent`(`subagent_type: "dev:worker"`, `isolation: "worktree"`, 모델은 `/dev:mode` 「서브에이전트」 절의 검증 역할)다. 검증자는 맞는 조작 스킬(`/dev:control-ui` 나 `/dev:control-cli` 같은 것)로 사용자가 쓰듯 변경을 돌려 보고, 부모와 head 를 비교하고, 그 PR 에 `PASS`, `PASS+NOTES`, `FAIL` 중 하나를 남긴다. 코드를 쓰지 않은 에이전트의 판정만 센다. 작성자는 만들려던 것을 확인하기 때문이다. 초록 CI 와 승인한 봇 리뷰는 판정이 아니다. 둘 다 사용자처럼 변경을 돌려 보지 않는다.
2. **맨 아래에 뿌리를 둔 이어진 검증 구간만 착지시킨다.** 가장 아래 머지 안 된 PR 에서 위로 걸어가다 `PASS` 나 `PASS+NOTES` 가 없는 첫 PR 에서 멈춘다. 그 아래 PR 들이 구간이고 맨 위가 천장이다. 검증 안 된 PR 위의 검증된 PR 은 기다린다. 아래 코드 없이 착지할 수 없기 때문이다. 브랜치가 그 코드를 품지도 필요로 하지도 않는 PR 은 trunk 로 옮겨 따로 착지할 수 있다. 다만 새 판정이 먼저다. 옛 판정은 그 코드를 아래 깔고 돌았고 trunk 에는 그 코드가 없다.
3. **판정이 아직 코드를 설명하는지 다시 확인한다.** 판정은 패치 하나를 덮는다. 사슬 rebase 는 그 위의 PR 을 모두 새 SHA 로 옮기면서 어떤 체크도 깨뜨리지 않는다. 옛 판정을 믿기 전에 판정 SHA 와 지금 head 의 `git patch-id` 를 비교한다. 패치가 테스트, 문서, lint 설정에서만 다르면, 레인이 돌린 것이 두 SHA 에서 잡음 말고는 똑같이 빌드될 때 그 레인 결과가 유지된다. 잡음은 판정 SHA 를 두 번 빌드해도 나는 차이이거나 박혀 들어간 커밋 SHA 다. 잡음은 종류마다 그 파일과 함께 보고해 읽는 사람이 판단을 확인할 수 있게 한다. 변경 자체는 여전히 새 체크와 리뷰를 받는다. 옛 판정이 그것을 본 적이 없기 때문이다. 빌드 산출물이 없는 레인(dev 서버 같은 것)은 이것을 보일 수 없으니 다시 돌리고, 그 밖에 바뀐 것도 다시 검증한다.
4. **아래에서 위로 한 번에 하나씩 착지시킨다.** 늘 구간의 가장 아래 머지 안 된 PR 을 `origin pr merge <pr>` 나 `gh pr merge <pr> --squash` 로 머지한다. Origin 에서는 그냥 쓴 명령이 이름 댄 PR 아래의 PR 도 모두 머지한다. GitHub 에서는 base 가 아직 부모 브랜치인 PR 이 trunk 가 아니라 그 브랜치로 머지된다. 결과는 PR 을 다시 읽어 본다(`origin pr view <pr>` 나 `gh pr view <pr> --json state,mergedAt,baseRefName`). merge queue 가 PR 을 줄에 세우기만 했을 때도 머지 명령은 성공이라고 할 수 있고, auto-merge 요청은 머지가 아니다. 착지한 PR 은 merged 로 읽히고 base 가 부모 브랜치가 아니라 trunk 다. `--auto`(Origin merge-when-ready 나 GitHub auto-merge)는 판정이 지금 head 를 덮는 PR 에만 건다. 준비되는 head 가 무엇이든 착지시키기 때문이다. 머지가 착지하면 base 가 머지된 브랜치였던 PR 을 trunk 로 돌리고(`origin pr edit <pr> --base <trunk>` 나 `gh pr edit <pr> --base <trunk>`), 그 패치를 머지 결과 위로 옮기고, `--force-with-lease` 로 push 한다. 판정은 커밋이 아니라 패치를 덮으니 판정이 살아남는지는 3단계의 patch-id 규칙이 정한다. 체크가 통과하고 판정이 살아남으면 머지한다.
5. **착지하는 동안 스택을 건드리지 않는다.** 4단계의 다음 PR 옮기기가 브랜치나 base 를 바꾸는 유일한 일이다. 머지는 그 순간 브랜치와 base 가 품은 것을 판정이 있든 없든 착지시키기 때문이다. GitHub 에서는 지금 PR 을 `gh pr checks <pr> --watch` 가 돌아올 때마다 `gh pr view <pr> --json state,mergedAt,baseRefName` 로 다시 읽고, 구간의 PR 을 아래에서 위로 하나씩 넘기며 천장이 merged 로 읽힐 때까지 `/loop` 아래에서 지켜본다. Origin 에서는 `origin pr checks <pr> --watch` 가 돌아올 때마다 `origin pr view <pr> --checks` 로 지금 PR 을 다시 읽고, 천장이 merged 로 읽힐 때까지 간다. 부모가 머지되면서 base 가 trunk 로 옮겨지는 것은 예상된 일이지 고칠 손상이 아니다. 머지가 멈추면 무엇이든 바꾸기 전에 왜인지 알아낸다.
6. **천장에서 멈춘다.** 구간을 늘리려면 새 판정이 필요하니 1단계부터 새로 돈다.

**답:** 검증된 구간과 그 천장, PR 마다 판정과 그것을 낸 에이전트, 무엇이 착지했고 어떻게 확인했는지, 다음 빈틈에 무엇이 필요한지.
