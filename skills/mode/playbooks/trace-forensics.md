# 트레이스 포렌식

**산출물에서 나온 진단을 소유한다.**

살아 있는 프로세스를 계측하는 런타임 포렌식(`playbooks/runtime-forensics.md`)과 다르다. 여기서는 잡은 산출물이 이미 있다. 산출물은 고정된 데이터다. 읽고, 다시 돌리지 않는다. 도구는 일반적인 것을 쓴다. cpuprofile 과 `.json.gz` 는 DevTools 나 trace 파서, spindump 는 텍스트 편집기, 힙 스냅샷은 쓰는 힙 도구.

1. 형식을 알아내고 맞는 도구로 연다. 큰 산출물은 서브에이전트에서 파싱하고(principles.md 의 Guard the Context Window) 줄인 결과는 본 스레드에 둔다. 서브에이전트마다 mode 「서브에이전트」 절대로 일에 맞는 추론 수준을 고른다.
2. 날 산출물을 쿼리할 수 있는 모양으로 바꾼다. trace 나 힙 스냅샷을 sqlite 로 덤프한다. 샘플, 프레임, 노드 하나에 한 행. 읽기 전에 쿼리할 수 있는 모양에 닿는다.
3. 원인으로 좁힌다. 시간을 가장 많이 쥔 프레임을 쿼리하고 콜 트리를 따라 뜨거운 경로로 간다. 누수면 새는 객체에서 GC 루트까지 보유 사슬을 따라간다. spindump 면 CPU 에 붙었거나 막힌 스레드와 그 대기 사유를 찾는다.
4. 소스로 귀속한다. 산출물 자체의 심볼로 뜨거운 프레임을 파일, 심볼, 줄에 매핑한다. 소스 매핑이 없는 프레임은 아직 진단이 아니다. 심볼을 풀거나, 산출물에 심볼이 없다고 분명히 말한다.
5. 짝이 되는 산출물이 있으면 전후 산출물을 diff 해 확인한다. 없으면 그 결과를 확정 원인이 아니라 산출물이 뒷받침하는 가장 강한 가설로 표시한다.
6. 근거를 단 진단을 돌려준다. 요청이 없으면 수정하지 않는다. 원인이 나오면 `playbooks/bug-fix.md` 나 `playbooks/perf-issue.md` 로 넘긴다. 처리량 점검은 한 줄로 둔다. `처리량 점검: n/a, 읽기 전용 포렌식`.

**답:** 산출물과 형식, 줄인 결과, 소스 위치, 산출물 경로, 짝 산출물로 확인했는지.
