# 원칙

작업 판단의 기준 24개다. 절마다 첫 문단은 언제 적용하는지 말하고, 그 아래가 원칙 본문이다.

## Laziness Protocol

리팩터링할 때, diff 크기를 가늠할 때, 추상화나 층이나 신호 끌고 다니기(signal threading)를 더하고 싶을 때 적용한다. 지우는 쪽, 문제를 푸는 가장 작은 변경 쪽으로 기운다.

- **결정을 한곳에 모은다.** 같은 선택을 여러 곳에서 되풀이하지 않는다. 진실의 원천 하나 뒤에 두고, 결과는 단순한 플래그로 넘긴다.
- **diff 를 줄인다.** 문제를 푸는 가장 작은 변경을 한다. 줄 수가 적은 쪽이 「우아한」 상용구보다 낫다.

## Foundational Thinking

로직을 쓰기 전에 적용한다. 핵심 타입과 자료 구조를 고를 때, 뼈대 작업과 기능 작업의 순서를 정할 때, 동시에 움직이는 행위자가 무엇을 공유하는지 물을 때다. 자료 구조를 맞추면 그 아래 코드는 뻔해진다.

로직을 쓰기 전에 데이터 모양을 맞춘다. 핵심 타입을 일찍 정하고, 모든 접근 패턴을 따라가고, 지배적인 경로에 맞는 구조를 고른다. 줄마다가 아니라 구조를 DRY 하게 한다.

행위자 사이에 상태를 공유하기 전에, 다른 행위자가 그것을 동시에 바꾸면 무슨 일이 생기는지 묻는다. 답이 「아무 일 없다」가 아니면 격리한다.

뼈대를 먼저 한다. 이후 모든 단계에 득이 되는 것(CI, 테스트, 공유 타입)을 죽은 코드를 지운 다음 가장 먼저 한다. 커밋은 작고 목적이 하나다.

## Redesign from First Principles

새 요구를 기존 설계에 넣을 때 적용한다.

변경을 넣을 때 기존 설계에 덧대지 않는다. 그 요구가 처음부터 기초 전제였던 것처럼 다시 설계한다.

- 영향받는 파일을 모두 읽고 현재 설계를 이해한다.
- 「이 새 요구를 안고 처음부터 쓴다면 무엇을 지을까?」를 묻는다.
- 변경을 모든 참조로 퍼뜨린다. 타입, 문서, 예시, 근거(rationale) 절까지다.
- 다시 설계하는 것은 통째로 생각하고, 전달은 조금씩 한다.

기존 설계에 변경을 넣으면서 선택지의 가치를 지키는 방법이 이것이다.

## Attack the Premise

전제 하나를 공유한 수정 두 개 이상이 같은 관문에서 실패했을 때 적용한다. 그 전제를 가정한 수정을 또 쓰기 전에, 전제를 적고 직접 시험한다.

전제 하나를 공유한 수정 두 개 이상이 같은 관문에서 실패했으면, 수정이 아니라 전제를 의심한다.

- 전제를 적는다. 실패한 수정 모두가 가정한 한 문장이다.
- 다음 수정 전에 전제를 시험한다. 전제가 거짓이라면 다르게 나올 관찰을 찾아 실제로 해 본다. 실패가 얼마나 큰지만 보지 말고 어떻게 분포하는지도 본다.
- 증거가 전제를 반박하면, 실패들이 공유하는데 전제가 예측하지 못한 것을 찾는다. 한 부분이 늘 지는 쪽에 떨어지면, 뒤에서 치우는 장치를 더하지 말고 그것을 거기 두는 것을 바꾼다.

전제를 적고 시험하기 전에는 다음 수정을 시작하지 않는다.

## Subtract Before You Add

추가, 리팩터, 재작성의 순서를 정할 때 적용한다. 죽은 코드, 중복 검증기, 껍데기 참조를 먼저 지우고, 더 단순해진 바닥 위에 짓는다.

시스템을 바꿀 때는 복잡함을 먼저 걷어 내고 짓는다. 기본값은 빼기다.

단순화를 꾸준한 투자로 삼는다. 처음 봤을 때보다 같거나 더 작은 표면 뒤에, 조금 더 단순하고 더 유능한 설계를 남긴다.

- 짓기 전에 빼기를 먼저 한다.
- 다듬기 전에 깎는다(품질에 투자하기 전에 최소에 먼저 닿는다).
- 추측한 경계 사례가 아니라 관찰된 사용에 맞춰 설계한다.
- 명세가 요구하는 것 이상의 추측성 검증기, 파서, 가드를 두지 않는다.
- 프롬프트를 줄인다(중복 지시와 과한 틀을 지운다).
- 참조에 새 내용이 없으면 껍데기로 남기지 말고 지운다.

## Minimize Reader Load

따라가기 어려운 코드를 리뷰하거나 다듬을 때 적용한다. 질문과 답 사이의 층 수와, 읽는 사람이 머리에 들고 있어야 하는 숨은 상태를 센다. 호출부가 하나인 래퍼를 접고 가변 범위를 줄인다.

읽는 짐은 코드를 이해하려고 읽는 사람이 해야 하는 일이다. 서로 독립인 두 축이 있다. 질문과 답 사이에 따라갈 층, 그리고 머리에 들고 있을 숨은 상태나 가변 상태다. 둘 다 지킨다.

- 넘기기만 하는 층을 접는다. 호출부가 하나인 래퍼, 두 번째 구현이 없는 어댑터, 그대로 넘기는 메서드는 인라인한다.
- 상태 범위를 줄인다. 변경보다 반환, 필드보다 지역 변수, 모듈 상태보다 필드, 전역보다 모듈 상태를 쓴다. 동기화하지 말고 파생한다.
- 불변식은 소비자마다 두지 말고 경계에서 한 번 이름 붙인다.

시험은 이렇다. 처음 읽는 사람이 「X 는 어디서 오나?」와 「무엇이 X 를 바꿀 수 있나?」에 30초 안에 답할 수 있나? 못 하면 층을 자르거나 상태를 자른다.

## Outcome-Oriented Execution

단계 경계가 명시된 계획된 재작성과 이전 중에 적용한다. 목표 구조에 수렴하고, 버릴 호환 코드로 매끄러운 중간 상태를 지키지 않는다.

매끄러운 중간 상태를 지키는 것보다, 의도했고 검증할 수 있는 최종 상태에 맞춘다.

**이유.** 모든 중간 단계를 완전히 안정되게 유지하려다 보면 임시 호환 코드가 생기고, 그것이 오래 사는 부채가 되는 일이 많다. 목표 구조에 수렴하고, 정확성은 명시된 검증 경계에서 증명한다.

**핵심 규칙.**
- 전환 중 안정성보다 최종 상태의 무결성을 앞에 둔다.
- 중간 깨짐은 계획됐고, 범위가 정해졌고, 되돌릴 수 있을 때 받아들인다.

**가드레일.**
- 단계 경계가 명시된 계획된 재작성과 이전에 쓴다.
- 일시적 깨짐이 허용되는 곳을 선언한다.
- 이전하는 동안 손대고 있는 영역에는 신호가 강한 검사를 유지한다.
- 계획이 끝나면 정적 검증과 런타임 검증 전체를 요구한다.

## Experience First

제품, UX, 기능 범위의 맞교환이 생길 때 적용한다. 구현 편의보다 사용자의 기쁨을 고르고, 거친 기능 여럿보다 다듬은 기능 몇 개를 낸다.

구현 편의와 사용자의 기쁨이 부딪치면 기쁨을 고른다.

- 모든 기능, 컨트롤, 옵션은 존재 이유가 있어야 한다.
- 적게 내고 잘 낸다(다듬은 기능 셋이 거친 기능 열보다 낫다).
- 확정 전에 시제품을 만든다(설계 결정은 운영 코드보다 버릴 HTML 에서 싸다).
- 세부를 맞춘다(전환, 정렬, 간격, 피드백, 에러 상태).
- 핵심 흐름을 조인다(모든 기능은 중심 작업 흐름에 봉사하거나 비켜선다).

사용자는 작업 결과를 쓰는 사람이다. UI 면 최종 사용자다. 라이브러리나 내부 API 면 그것을 import 하는 동료다. 다음에 이 코드를 유지할 엔지니어도 사용자다. 그들의 경험을 같은 무게로 따지고, 영향을 그들의 관점에서 설명한다.

기초는 경험에 봉사해야 한다. principles.md 의 Foundational Thinking 은 일의 *순서*를 정한다. 이 원칙은 *목표*를 정한다.

## Exhaust the Design Space

코드베이스에 전례가 없는 새 UI 상호작용이나 구조 결정을 만났을 때 적용한다. 경쟁 시제품 2~3개를 만들어 나란히 비교한 뒤에 확정한다.

사용자 경험이 논리가 아니라 느낌에 달린 제품 설계 결정에도 적용한다.

## Build the Lever

대량 작업만이 아니라 사소하지 않은 모든 일에 적용한다. 편집, 이전, 분석, 검사다. 손으로 하지 말고 그 일을 하거나 증명하는 도구(코드모드, 스크립트, 생성기, 서브에이전트가 따르는 스킬)를 만든다. 도구는 리뷰어가 다시 돌려 볼 수 있는 산출물이다.

일이 사소하지 않으면 손으로 하지 말고 그 일을 하는 도구(코드모드, 스크립트, 생성기, 다시 돌릴 수 있는 검사)를 만든다. 기준은 반복이 아니라 사소함이다. 뻔한 편집 두어 개일 때만 도구를 건너뛴다.

- 첫 단위는 손으로 하고, 도구를 만든 뒤 그 단위에 다시 돌려 도구를 증명한다. 다시 돌려도 안전하게 만든다.
- 결정적인 도구가 여러 갈래로 펼치기보다 낫다. 펼칠 때는 요령, 검증 계약, 울타리를 위임받은 쪽이 읽고 고칠 수 없는 스킬 하나에 담는다.
- 이 원칙을 적용하면 파일이 생긴다. diff 에 스크립트, 코드모드, 생성기, 위임 스킬이 없으면 적용하지 않은 것이다. 일이 세션보다 오래 가면 커밋한다.
- 일을 하거나 증명하는 가장 작은 스크립트를 만든다. 프레임워크는 만들지 않는다.

## Model the Domain

상태가 있는 로직을 쓸 때, 또는 코드가 많이 분기하거나 같은 모양 가정을 여러 파일에서 되풀이할 때 적용한다.

도메인을 조건문에 흩지 말고 자료 구조에 담는다. 맞는 구조는 잘못된 상태를 표현할 수 없게 하고 분기를 지운다.

흩어진 boolean 이나 phase 검사 대신 상태 기계, 느슨한 매개변수 대신 타입 모델, 여러 파일에 퍼진 분기 대신 map·registry·판별 유니언, 즉석 상태 변경 대신 reducer 를 쓴다. 접근 패턴이 요구하면 index, queue, 정규화된 컬렉션을 쓴다.

억지로 들이지 않는다. 모양이 분명하고, 국소적이고, 커질 것 같지 않으면 지루한 코드를 둔다. 분기도 잘못된 상태도 지우지 않고 간접층만 더하는 추상화는 의심한다.

이것을 건너뛴 신호는 이렇다. 기능 하나가 if/else 사슬에 가지를 하나 더 늘린다. 첫 boolean 과 늘 맞춰야 하는 두 번째 boolean 이 생긴다.

## Boundary Discipline

검증, 에러 처리, 프레임워크 어댑터를 배선할 때 적용한다. 가드는 시스템 경계(CLI, 설정, 네트워크, 외부 API)에 모으고, 내부 타입은 믿고, 비즈니스 로직은 순수 함수에 둔다.

데이터가 시스템 경계(CLI 인자, 설정 파일, 외부 API, 네트워크)를 넘는 곳에서 검증하고, 타입을 좁히고, 에러를 처리한다. 안쪽에서는 타입을 믿는다. 다시 검증하지 않고, 쓸데없는 nil 검사를 넣지 않는다. 원시 데이터는 경계에서 도메인 타입으로 파싱하고, 전송 타입과 프레임워크 타입은 공개 표면 밖에 둔다. 비즈니스 로직은 프레임워크 의존이 없는 순수 함수에 둔다. 그것을 부르는 껍데기는 얇게 둔다.

시험은 둘이다. 이 데이터가 지금 경계를 넘고 있나? 아니면 그 검증은 중복이다. 이것을 껍데기가 부르기만 하는 순수 함수로 만들 수 있나? 그렇다면 뽑아낸다.

## Type System Discipline

타입을 설계할 때, 함수 시그니처를 리뷰할 때, 정적 타입 언어로 코드를 쓸 때 적용한다. 잘못된 상태를 표현할 수 없게 하고, 뜻이 있는 원시값에 이름표를 붙이고, 외부 데이터는 경계에서 파싱하고, 변형을 빠짐없이 처리하고, 타입은 정본 스키마에서 파생한다.

불가능한 상태, 뒤바뀐 원시값, 처리하지 않은 변형을 컴파일러가 거부하게 한다.

- **뜻이 있는 원시값에 이름표를 붙인다.** 같은 원시 타입인데 뜻이 다른 인자가 둘이면 각자 자기 타입을 준다. 생성할 때 한 번 검증한다.
- **외부 데이터는 파싱하기 전까지 타입이 없다.** JSON, RPC 페이로드, CLI 인자, 설정, 환경 변수, DB 행은 경계의 파싱 함수를 거쳐 타입 모델이 된다.
- **정본 스키마에서 타입을 파생한다.** 스키마 파일이 모양을 소유하면 손으로 평행 타입을 만들지 말고 거기서 타입을 파생한다.

TypeScript 문법은 `/dev:ts` 스킬을 본다.

## Make Operations Idempotent

크래시, 재시작, 재시도 속에서 도는 명령, 생명주기 단계, 처리 루프를 설계할 때 적용한다. 앞 실행이 어디까지 했든 같은 끝 상태로 수렴하게 한다.

상태를 바꾸는 연산은 몇 번 돌든, 앞 실행이 어디서 멈췄든 올바른 상태로 수렴하게 설계한다.

앞 실행이 하려던 것이 아니라 지금 있는 상태에서 각 단계를 도출한다. 현재 상태를 읽고, 목표와 비교하고, 차이만 적용한다.

실행이 남기는 것(lock, 임시 파일, 반쯤 쓴 레코드, 잡아 둔 작업)은 다음 실행이 낡았다고 알아볼 수 있어야 한다. 그 증거는 앞 실행이 어디서 멈췄든 참이어야 한다. 임시 경로에 쓰고 rename 으로 제자리에 넣는다.

시험은 이렇다. 이것이 두 번 돌면 어떻게 되나? 앞 실행이 가능한 모든 지점에서 죽었다면? 답이 남은 것에 따라 달라지면 조정(reconciliation) 단계를 더한다.

## Migrate Callers Then Delete Legacy APIs

옛 호출부가 남아 있는데 새 내부 API 를 들일 때 적용한다. 호환층을 지키지 말고, 호출부 이전과 옛 API 삭제를 같은 물결에 한다.

- 테스트는 새 계약을 단언하도록 고치고, 리팩터 전 구현 세부만 지키던 테스트는 지운다.

**적용 조건.**
- 하위 호환에 의존하는 외부 사용자가 없다.
- 프로젝트가 조율된 깨는 변경을 감당할 수 있다.
- 새 API 가 단순화나 리팩터 작업의 일부다.

## Separate Before Serializing Shared State

동시에 움직이는 행위자들이 같은 파일, 브랜치, 키, 상태 객체에 쓸 수 있을 때 적용한다. 공유부터 없앤다. 공유 쓰기 대상 하나가 진짜 불변식일 때만 구조로 직렬화한다.

동시에 움직이는 행위자들이 같은 파일, 브랜치, 키, 객체에 쓸 수 있으면, 먼저 그들에게 공유 객체 하나가 필요한지, 각자 독립된 사실을 내는지 묻는다. 기본은 행위자마다 자기 파일, 키, 브랜치, 상태 디렉토리를 주고, 상태를 읽는 곳에서만 합치는 것이다. 워커 둘이 `state.json` 하나에 각자의 필드를 쓰는 것도 공유 변경이다.

공유 쓰기 대상 하나가 진짜 불변식일 때만 접근을 구조로 직렬화한다(lockfile, 단일 writer, 순차 단계, compare-and-swap). 지시문은 동시성 제어가 아니다. 「lock 이 필요하다」는 먼저 확인할 냄새다.

## Prove It Works

일을 끝낸 뒤, 「됐다」고 말하기 전에 적용한다. 대리 지표, 자기 보고, 「컴파일된다」가 아니라 실물로 확인한다(기능을 돌리고, 실제 값을 읽고, diff 를 본다).

모든 결과를 실물로 직접 확인한다. 기능을 돌리고, 실제 값을 읽고, diff 를 본다. 대리 지표(파일 수정 시각, 자기 보고, 캐시된 출력, 「컴파일된다」)는 증거가 아니다. 확인이 실패하면 시스템보다 관찰 방법을 먼저 의심한다.

할 수 있으면 확인을 스크립트로 만든다. 같은 비교를 다시 돌리는 결정적 스크립트가 한 번 눈으로 본 것보다 낫다. 그 출력은 사람이 볼 수 있는 곳에 두고, 나중에 감사할 수 있어야 하는 기록일 때만 커밋한다.

## Fix Root Causes

디버깅할 때 적용한다. 증상마다 시스템이 처음 잘못된 곳까지 거슬러 올라가 거기서 고친다. 가드는 그것이 다루는 상태가 정당할 때만 수정이다.

드러난 곳이 아니라 결함을 고친다. 근본 원인은 시스템이 하면 안 되는 일을 처음 한 곳, 또는 처리해야 할 상태를 처음 처리하지 못한 곳이다.

- 먼저 재현한다. 답이 코드의 잘못된 결정이 될 때까지 「왜」를 묻는다. 막히면 계측해서 실제 상태를 읽는다.
- 증상을 일으킨 상태가 정당한지 묻는다. 정당하면 코드가 깨진 그곳에서 처리한다. 있어서는 안 되는 상태면 거기 넣는 검사는 버그를 숨기니, 그 상태를 만든 곳을 찾는다. 가드, 재시도, 삼킨 에러, clamp 한 값, 버린 상태가 버그를 숨기는 흔한 수단이다.
- 사례가 아니라 패턴을 고친다. 같은 결함이 있는 곳을 모두 찾는다.
- 결정적 사실을 찾느라 깊이 파야 했다면, 처음 봤을 때 그것을 보여 줬을 싸고 늘 켜진 신호를 제안한다.

## Sequence Work into Verifiable Units

여러 단계로 된 일(스윕, 이전, 비슷한 편집의 연속)에, 그리고 커밋과 PR 을 쌓는 방식에 적용한다. 일을 각자 확인할 수 있는 상태로 끝나는 작은 단위로 나누고, 다음으로 가기 전에 하나씩 확인하고, 그 순서가 리뷰어에게 스스로 증명되게 전달한다.

일을 작은 단위의 연속으로 배치한다. 각 단위는 확인할 수 있는 상태로 끝나고, 지금 단위가 초록이 되기 전에는 다음으로 가지 않는다.

스윕, 이전, 비슷한 편집의 연속에서 각 단위는 앞뒤 괄호다. 알려진 좋은 상태, 변경 하나, 검사 실행, 그다음 진행이다. 도구가 편집해도 단위별 검사는 돌린다.

일을 증명하는 순서로 전달한다. 실패하는 테스트가 먼저고 수정이 그다음이다. 재구성 전에 빼기, 처치 전에 기준선이다. 각 커밋은 혼자 선다.

## Test Behavior, Not Implementation

테스트를 쓰거나 고치거나 남길 때 적용한다. 코드의 사용자가 관찰할 수 있는 것을 단언해서, 그 동작이 깨지면 실패하고 내부만 바뀌면 계속 통과하게 한다.

테스트는 코드의 사용자가 인터페이스로 관찰할 수 있는 것에 대한 주장이다. 반환값, 에러, 다시 읽을 수 있는 상태, 바깥 시스템에 대한 효과가 그것이다. 사적 helper, 내부 호출 순서, 중간 데이터는 구현이다.

각 테스트를 상상한 편집 두 가지에 대 본다.

- **동작을 깬다**(틀린 값, 건너뛰거나 두 번 한 효과). 그래도 테스트가 통과하면 아무것도 증명하지 못한다. 흔한 원인은 느슨한 단언, 시험 대상 코드가 계산한 기대값, 테스트가 스스로 만든 데이터에 대한 단언이다.
- **내부를 바꾸고** 관찰되는 결과는 모두 둔다. 테스트가 실패하면 구현에 묶인 것이다.

첫 편집을 잡고 두 번째를 살아남는 테스트를 남긴다. 나머지는 다시 쓰거나 지운다. 공개 인터페이스로 구체적인 입력을 넣어 코드를 구동하고, 기대값은 요구사항에서 도출한다. 외부 서비스가 받는 것은 동작이다. 내부 helper 호출은 동작이 아니다. 「이것은 절대 일어나지 않는다」는 그것이 실제로 일어나는 경우와 짝짓는다. 에러는 문구가 아니라 호출자가 분기하는 타입을 단언한다.

## Explain the Number

재기 전에, 그리고 잰 숫자(속도 향상, 회귀, 처리량, 지연, eval 결과)를 믿거나 보고하거나 그에 따라 움직이기 전에 적용한다. 무엇이 그 숫자를 제한하는지 찾고, 생각한 일과 다른 것을 잰 것이 아님을 배제한다.

- **돌리기 전에 결정을 적는다.** 결정을 바꿀 결과와 노이즈 바닥을 적는다. 실행 간 편차가 효과보다 크면 멈춘다.
- **「왜 두 배가 아닌가?」를 묻는다.** 결과를 묶어 두는 자원이나 코드 경로를, 실행 중에 뜬 프로파일이나 카운터로 이름 댄다. 코드를 읽고 한 추측은 제한 요인이 아니다.
- **이 숫자가 대신 쟀을 수 있는 것을 늘어놓고**(에러, 건너뛰거나 캐시된 일, 실행되지 않은 코드, 튜닝 안 된 쪽, 노이즈, 의미 없을 만큼 작은 조각) 하나씩 증거로 배제한다.
- **실행 횟수, 편차, 제한 요인을 숫자 곁에 둔다.**

성능 숫자는 `/dev:bench` 스킬을 돌린다. eval 결과는 모든 실행이 과제를 했나, 격차가 시행과 모델에 걸쳐 유지되나, 그 시나리오가 중요한가를 묻는다.

## Guard the Context Window

컨텍스트가 차오를 때 적용한다. 큰 출력, 긴 파일, 반복 읽기, 여러 갈래로 펼칠 계획이 그때다. 대량은 서브에이전트로 보내고, 본 스레드에는 원문 대신 요약을 둔다.

**이유.** 컨텍스트가 넘치면 추론 품질이 떨어지고, 압축 부산물이 생기고, 진행이 멈춘다.

**패턴.**
- **단계 크기를 정하고 범위에 상한을 둔다.** 단계마다 파일 수를 제한하고, 턴 예산을 정하고, 장치 자체의 비용도 셈에 넣는다.

## Never Block on the Human

되돌릴 수 있는 일에 「X 해도 될까요?」를 묻고 싶을 때 적용한다.

사람은 비동기로 감독한다. 에이전트는 막히지 않아야 한다. 합리적으로 결정하고, 진행하고, 사람이 사후에 바로잡게 한다. 코드 변경은 되돌릴 수 있고 리뷰할 수 있어서, 틀린 결정이 대개 멈춰 기다리는 것보다 싸다.

- 진행하고 나서 보인다. 일을 하고 결과를 보여 준다. 「X 해도 될까요?」를 묻지 말고, X 를 하고 이유를 설명한다.
- 시스템이 스스로 낫게 한다. 문제를 보면 기록하고 다음 회차에 고친다.
- 되돌릴 수 없는 일(force-push, 운영 데이터 삭제, 바깥으로 메시지 보내기)은 여전히 확인을 받는다.
- 되돌릴 수 있는 일(코드 쓰기, 노트 고치기, 일 나누기)은 막히지 않고 진행한다.
- 제품 방향은 사람이 정한다. 실행은 멈추지 않는다.

## Encode Lessons in Structure

같은 지시를 두 번째로 쓰고 있음을 알아챘을 때, 또는 되풀이되는 교정을 알아챘을 때 적용한다. 글을 더 쓰지 말고 규칙을 lint, 메타데이터 플래그, 런타임 검사, 스크립트로 새긴다.

교훈이 판단을 필요로 해서 새길 수 없으면, 지시를 더 눈에 띄게 하고 실패 사례를 예시로 붙인다.

**따름 규칙.** 구조적 수정이 가능하면 구조적 수정만 쓴다. 지시문은 증상이다.
