# Recall

일을 시작하거나 다시 잡기 전에 사용자의 최근 작업 맥락을 다시 세우고, 지금 어디까지 왔고 다음에 무엇을 할지 짧은 캡슐로 돌려준다.

짧게, 주제 안에서만 한다. 범위 안 줄기에 필요한 것만 읽고 멈춘다.

맥락은 두 기록에 있다. 내 대화 기록에는 내가 한 일과 정한 것이 있다. 공유 기록에는 같은 코드 주변에서 다른 이름으로 일어난 일이 있다. 사용자가 계속 보고하는 증상, 나갔다가 되돌려진 수정, 운영에서 아직 터지는 오류다. 공유 기록은 소스 관리, 이슈 트래커, 채팅·이슈 채널, 긴 문서, 오류 추적에 있다. 버그 꼬리가 긴 기능은 이야기 대부분이 거기 있다. 대화 기록만으로 다시 세우지 않는다.

## 대화 기록 위치

`~/.claude/projects/<경로>/<세션>.jsonl`. `<경로>` 는 현재 작업 폴더의 절대 경로에서 `/` 와 `.` 을 `-` 로 바꾼 것이다(`/Users/me/repos/app` → `-Users-me-repos-app`). 한 줄이 한 이벤트다. 사람이 쓴 메시지는 `type == "user"` 이고 `.message.content` 가 문자열이거나 `text` 블록이 든 배열인 줄이다. `tool_result` 만 든 `user` 줄은 도구 결과다. 서브에이전트 기록은 `<세션>/subagents/*.jsonl` 에 있다. 현재 작업 폴더의 것만 읽는다. 다른 프로젝트 폴더는 사용자가 시키지 않으면 열지 않는다.

```bash
d=~/.claude/projects/$(pwd | sed 's#[/.]#-#g')
ls -t "$d"/*.jsonl | head -20
```

워크트리에서 일하는 중이면 워크트리 경로가 따로 폴더를 갖는다. 사용자가 「이 저장소 작업」을 물으면 메인 체크아웃 경로와 그 워크트리 경로(`<저장소>/.claude/worktrees/*`)까지가 같은 작업 폴더다.

## 절차

1. 분류하고 보낸다. 지난 대화 하나를 이어 가는 일이면 이 스킬이 아니라 /dev:mode 의 이어받기 플레이북(`../mode/playbooks/session-pickup.md`)이다. 습관을 오래 남을 규칙으로 바꾸는 일은 /dev:reflect 다. 사람이 읽을 업무 요약은 다른 일이다. recall 은 행동하기 전에 최근 여러 대화의 작업 맥락을 싣는 일이다. 사용자가 이미 상태 캡슐(경로, 브랜치, 변경)을 줬으면 그것을 쓰고 캐기를 건너뛴다.
2. 찾기 전에 범위를 고정한다. 기간(「최근」은 실제 범위다. 기본은 최근 7일), 이름이 있으면 주제, 작업 폴더(기본은 현재 것)를 정한다. 범위를 한 줄로 되말한다. 「전부」를 몰래 「최근 N개」로 바꾸지 않는다.
3. 대화 기록을 나눠 캔다. `Agent` 를 `model: "sonnet"` 으로 여럿 병렬로 띄우고 기록 묶음을 하나씩 맡긴다. 모든 서브에이전트에 이렇게 지시한다. 후보는 파일 이름(UUID) 순이 아니라 실제 수정 시각(`ls -t`) 순으로 고른다. 주제로 먼저 grep 하고, 걸린 대화의 관련 부분만 읽는다. 현재 대화와 잡음(서브에이전트, 평가, 시험 대화)은 건너뛴다. 파일을 고치지 않는다. 대화마다 같은 틀로 한 덩어리씩 돌려준다: 주제, 사용자의 목표, 결정, 열린 줄기, 고생과 교정, 산출물(PR, 이슈, 브랜치). 덩어리마다 세션 UUID 를 단다. 대화가 한두 개면 나누지 말고 직접 찾는다. 원문은 서브에이전트에 두고 본 스레드는 결과만 받는다.
4. 공유 기록을 훑는다. 주제가 기능·파일·하위 시스템·영역·버그를 가리키면 판단하지 말고 늘 한다. 「내 X 작업」도 빠지지 않는다. 출처마다 조사 서브에이전트(`general-purpose`, `model: "sonnet"`)를 하나씩 띄운다. MCP 를 써야 하므로 `Explore` 가 아니라 `general-purpose` 이고, 브리프에 「파일을 고치지 마라」를 적는다. 물음은 「지금 상태는? 시도했지만 버티지 못한 것은? 사용자가 아직 보고하는 것은?」이다. 3단계와 병렬로 돌린다. 결과가 없는 것도 결과다. 쓸 수 없는 MCP 는 건너뛰고 건너뛰었다고 말한다. 돌아온 것을 브리프에 넣는다. 이름 붙은 대상이 없는 순수 활동 회상(「이번 주에 뭐 했지」)만 이 단계를 건너뛴다. 그때는 내 기록과 현재 상태가 답의 전부다.
5. 현재 상태와 맞춰 본다. 캐기와 훑기에서 나온 PR, 브랜치, 이슈를 `git` 과 `gh` 로 확인한다. 답이 에이전트가 실제로 한 일(실행한 도구, 읽은 파일, 만난 오류)에 걸려 있으면 요약본이 아니라 그 기록 전체를 읽는다.
6. 아래 형식으로 브리프를 쓴다. 줄기별로 묶는다. 이름 붙은 주제 안에서만 쓴다.

## 출력 형식

캡슐, 줄기 상태, 문제, 다음 수 순서다. 더 깊은 내용은 아래에 두거나 자른다.

- **캡슐.** 5줄 이하. 이 일이 무엇이고 전체적으로 어디까지 왔나.
- **줄기.** 한 줄씩. 맨 앞에 상태 표시를 정확히 하나 붙인다: `[merged #N]`, `[open PR #N]`, `[in flight <브랜치>]`, `[verified, uncommitted]`, `[reverted #N]`, `[planned, not started]`. 표시가 없는 줄기는 아직 안 끝났다는 뜻이니 표시를 단다.
- **문제.** 5개 이하, 되풀이되는 것만. 사용자가 계속 보고하는 증상과 나갔다가 되돌려진 수정을 넣어, 다음 시도가 지난 시도가 실패한 자리에서 시작하게 한다.
- **다음 수.** 가장 쓸모 있는 다음 행동 하나, 구체적으로.

옆 기능이나 옆 이슈는 이 일을 막을 때만 넣는다. 캡슐과 줄기가 한 화면을 넘으면 줄기를 자르기 전에 세부를 자른다. 같은 대상은 한 줄로 합쳐 최종 상태와 변화만 쓴다(「A: 500 → 1000」). 글은 /dev:write 기준으로 쓴다. 대화에서 나온 것은 세션 UUID 로, 공유 기록에서 나온 것은 출처(PR 번호, 이슈 번호, 채팅 링크, 오류 추적 이슈)로 단다. 공개되는 곳에 쓰기 전에 사적인 맥락을 지운다.
