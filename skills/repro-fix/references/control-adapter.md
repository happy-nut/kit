# 제어 어댑터 약속

이 흐름은 모든 앱을 어떻게 띄우고 모는지 모른다. 대상 앱을 위해 이 약속을 채우는 제어 스킬 하나가 있어야 한다. devkit 에서는 `/dev:verify-setup` 이 만든 프로젝트 검증 스킬 `<저장소>/.claude/skills/verify-<앱>/` 이 그 스킬이다.

설정의 `control.skill_name` 에 그 스킬 이름(`verify-<앱>`)을 둔다.

설정의 `control.feature_map_path` 에 채운 사용자 시점 기능 지도(`.claude/skills/verify-<앱>/features/`)를 둔다. 재현에 필요한 칸은 [`feature-map.md`](feature-map.md) 가 정한다. 예시를 고치지 말고 그 검증 스킬의 기능 파일에 채운다.

스킬, 기능 지도, 필요한 능력 중 하나라도 없거나, 애매하거나, 덜 채워졌으면 재현과 수정은 닫힌 쪽으로 실패한다. 빠진 능력은 `/dev:verify-maintain` 으로 그 스킬에 더한다. 이 흐름이 실행 중에 검증 스킬을 고치지 않는다.

## 검증 스킬 절과의 대응

| 이 약속 | `verify-<앱>` 의 절 |
|---|---|
| 띄우기 | Launch, Doctor |
| UI 몰기, 지도 기능과 상태 몰기 | Drive, `features/` |
| 상태 보기 | Doctor(읽기 전용), Evidence 의 교차 확인 |
| 스크린샷, 녹화 | Evidence |
| 정리 | Cleanup |
| 부르는 법이 보이는 스크립트 | Helpers |

검증 스킬이 녹화를 다루지 않으면 녹화 능력이 빠진 것이다. 스크린샷 여러 장으로 대신하지 않는다.

## 필요한 능력

### 띄우기

요청한 앱 리비전을 요청한 시험 환경에서 시작한다.

입력:

- 저장소와 리비전
- 빌드나 시작 방식
- 작업 공간, 계정, 픽스처, 기능 상태 요구
- 산출물 폴더
- 채운 기능 지도 경로

돌려줄 것:

- 세션 식별자
- 맞는 앱과 환경임을 어떻게 확인했나
- 안정된 앱 표지
- 뒤 호출에 필요한 실행 중 프로세스나 대상 정보
- 빠진 능력

비슷한 창, 셸, 운영 인스턴스와 대상 앱을 구별해야 한다.

### UI 몰기

실제 사용자 행동을 한다.

- 누르기
- 입력
- 키 누르기
- 스크롤
- 끌기
- 크기 바꾸기
- 앱 컨트롤로 이동

역할, 라벨, 안정된 선택자를 먼저 쓴다. 좌표는 새 스크린샷을 찍은 뒤에만 쓴다.

행동마다 그 행동과 관찰한 상태 변화를 돌려준다.

증상을 만들려고 내부 상태를 바꾸거나, 숨은 앱 메서드를 부르거나, 저장소에 직접 쓰거나, DOM 을 주입하지 않는다.

### 지도 기능과 상태 몰기

앱을 몰기 전에 맞는 기능 파일을 읽는다.

어댑터는 이것을 할 수 있어야 한다.

- 지도의 모든 기능으로 사용자에게 보이는 경로를 따라 간다.
- 그 기능에 적힌 어댑터 동작 이름을 부른다.
- 해당하면 기본, hover, focus-visible, active, disabled, loading, empty, error, selected, open, expanded, 기능 고유 상태를 다룬다.
- 안전한 픽스처 데이터, 권한, 플래그, 서비스 응답, 지원되는 시험 컨트롤로 상태를 갖춘다.
- 두 번째 독립 재현 시도를 위해 기능을 되돌린다.
- 기능 지도가 정한 스크린샷, 영상, 읽기 전용 교차 확인을 잡는다.

역할, 접근 가능한 이름, ARIA 관계, 안정된 컴포넌트 표지, 목적을 이름에 담은 data 속성을 쓴다. 생성된 CSS 나 StyleX 같은 CSS-in-JS 클래스, 동적 해시, 자식 순번, 깨지기 쉬운 DOM 위치는 절대 쓰지 않는다.

전제를 갖추는 것은 보고된 증상을 주입해도 된다는 허락이 아니다. 재현 자체는 여전히 실제 사용자 조작에서 나와야 한다.

### 상태 보기

UI 가 보여 주는 것을 확인하려고 상태를 읽는다.

예:

- 접근성 트리
- DOM 이나 뷰 계층
- 프로세스 상태
- 로컬 로그
- 네트워크 요청 상태
- 앱이 내보이는 디버그 상태

보기는 읽기 전용이다. 질의가 상태를 바꾸면 그것은 「UI 몰기」에 속하고 실제 사용자 행동을 나타내야 한다.

### 스크린샷

현재 앱 상태를 요청한 경로에 찍는다.

돌려줄 것:

- 파일 경로
- 찍은 시각
- 앱 표지나 창 제목
- 무엇이 보여야 하는지 짧은 설명

맞는 앱을 시험 중임을 증명할 만큼 앱 테두리가 보여야 한다.

### 녹화

재현 경로 전체를 감싸 화면 녹화를 시작하고 멈춘다.

돌려줄 것:

- 파일 경로
- 시작과 멈춘 시각
- 잡은 창이나 영역
- 소리나 민감한 겹침 화면을 뺐는지

녹화는 준비나 로딩 화면만이 아니라 증상을 가르는 최종 상태를 보여야 한다.

### 정리

어댑터가 만든 프로세스와 세션을 멈춘다.

버려도 되는 것을 지운다.

- 브라우저나 앱 프로필
- 임시 작업 공간
- 어댑터가 만든 시험 계정이나 픽스처
- 디버그 포트와 터널
- 보존 기간이 지난 캡처

무엇을 멈췄고, 지웠고, 남겼고, 사람에게 맡겼는지 돌려준다.

정리는 사용자 작업을 지우지 않는다. 프로세스 이름으로 죽이지 말고 자기가 띄운 것만 멈춘다.

## 어댑터 동작

어댑터는 이렇게 해야 한다.

- 재현을 시작하기 전에 능력을 보고한다.
- 지도의 어느 기능을 몰 수 있고 어느 것이 막혔는지 보고한다.
- 기준 빌드와 고친 빌드에 같은 환경 입력을 쓴다.
- 시작 실패를 실패로 드러낸다.
- 재시도에 상한을 둔다.
- 비밀을 로그와 산출물 밖에 둔다.
- 캡처를 저장소 밖에 둔다.
- 두 재현 시도 사이에 새 상태나 되돌린 상태를 준다.
- 사용자가 안전한 시험 동작을 명시적으로 설정하지 않았으면 운영 환경을 바꾸지 않는다.

## 실행 자리

원격 루틴은 화면 없는 클라우드 세션이다. 공식 문서 기준으로 그 환경에는 Chrome for Testing(`CHROME_PATH`)과 Docker 가 있다. 웹 앱은 거기서 헤드리스 브라우저로 몰 수 있다. 데스크톱 앱, iOS·Android 앱처럼 화면과 시뮬레이터가 필요한 앱은 데스크톱 예약 작업(로컬)에서 돌린다. 클라우드에서 그런 앱의 능력이 빠졌으면 막힘으로 보고하고, 다른 것으로 재현을 흉내 내지 않는다.

## 환경 옮기기

환경 때문에 막혔다고 하기 전에, 플랫폼 고유 명사를 빼고 결함을 다시 말해 본다. 그리고 같은 동작을 지금 있는 환경에서 안전하게 시험할 수 있는지 묻는다.

예:

- 특정 브라우저 이름은 아무 외부 브라우저라는 뜻일 수 있다.
- 특정 키 이름은 설정된 단축키라는 뜻일 수 있다.
- 특정 원격 호스트 이름은 늦거나 끊긴 원격 대상이라는 뜻일 수 있다.

같은 바탕 동작을 시험할 때만 옮긴 시도를 쓴다. 옮긴 증거라고 이름표를 단다. 빠진 환경이 결함의 일부면 정확한 재현이라고 부르지 않는다.

하드웨어 권한 요청, 운영체제 권한 대화 상자, 기기 전용 API, 만들 수 없는 계정 상태는 진짜 막힘일 수 있다.

## 설정 확인

재현 자동화를 켜기 전에 해가 없는 어댑터 확인을 한 번 한다.

1. 앱을 띄운다.
2. 안정된 앱 표지를 확인한다.
3. 채운 기능 파일 하나를 읽는다.
4. 그 기능의 사용자 경로로 간다.
5. 지도의 어댑터 동작으로 버려도 되는 상태 하나를 다룬다.
6. 그 결과 상태를 본다.
7. 스크린샷을 찍는다.
8. 짧은 영상을 녹화한다.
9. 정리한다.

아홉 단계가 모두 성공하고 출처 채널 Slack 글이 하나도 끼지 않았을 때만 재현 일을 켠다.
