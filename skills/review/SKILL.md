# 리뷰

적대적 검토자들이 변경이나 설계를 깨려고 한다. 지적은 실행으로 증명될 때만 살아남는다. 지적을 보고한다. 고치지 않는다.

## Frame

범위는 사용자가 말한 것이다. 말하지 않았으면 기반 브랜치와의 merge-base 부터 작업 트리까지의 브랜치 diff 다. 사용자 메시지, 커밋, PR 설명에서 의도를 끌어내 `../mode/SKILL.md` 의 「꼭 지킬 것」 첫 줄대로 자기 말로 다시 적는다. 의도가 불분명하면 사용자에게 묻는다.

## Fan out

`../design/SKILL.md` 를 Read 로 읽고 그 경쟁 절차의 1. Frame 3·4단계와 2. Fan out 을 돌리되 네 가지를 바꾼다. `design runners` 대신 `~/.claude/rules/dev-models.md` 의 `review reviewers` 줄을 읽는다. 범위의 커밋하지 않은 변경을 각 worktree 에 복사한다. 검토자마다 `subagent_type: "general-purpose"` 로 띄운다. 경쟁 절차의 과제와 근거 글 대신 검토자마다 범위, 의도, 그리고 아래 브리프를 준다.

> 이 변경을 깨라. 지적마다 실제 코드를 상대로 돌린 것으로 증명한다. 실패하는 테스트, 재현 스크립트, 잘못된 동작을 보여 주는 명령 출력 같은 것이다. 설계나 계획이면 프로토타입을 돌리거나 지금 트리를 찔러 본다. 재현물은 네 worktree 안에 둔다. 지적마다 제목, 정확한 명령, 그 명령이 찍은 출력, 의도대로라면 나와야 할 출력을 적는다. 돌리지 않은 것은 뺀다. 스타일, 이름, 구조, 앞으로의 변경이 있어야 문제가 되는 위험이 여기 든다. 지적이 없는 것도 올바른 결과다.

## Verify

경쟁 절차의 6. Verify 대로 지적마다 그 명령을 다시 돌려 검증한다. 출력에 실패가 보이고 그 실패가 의도를 깨면 지적을 남긴다. 나머지는 버린다. 근본 원인이 같은 지적은 하나로 합친다.

경쟁 절차의 3. Cross-judge, 4. Pick, 5. Graft 는 건너뛴다. 검토자마다 다른 실패를 찾으므로, 결론은 한 검토자의 목록이 아니라 검증된 지적을 모두 남긴다.

## 보고

- **의도**: 다시 적은 의도.
- **지적**: 검증된 지적마다 명령, 그 출력, 어떻게 의도를 깨는지, 찾은 검토자. 살아남은 것이 없으면 「검증된 지적 없음」이라고 쓴다.
- **버림**: 검토자마다 버린 지적의 개수와 이유.

## 파급 범위

변경이 내보내지기 전에 다른 곳에서 무엇을 깨는지 찾는다. 「X 의 파급 범위」, 「이거 뭐가 깨질 수 있어」, 아직 믿지 못하는 작은 diff 를 볼 때 쓴다.

`/dev:how`, `/dev:why` 와 짝이다. `/dev:how` 는 코드가 무엇을 하는지 알려 준다. `/dev:why` 는 왜 그런 모양인지 알려 준다. 파급 범위는 그것이 다른 곳에서 무엇을 깨는지 알려 준다.

호출자 목록을 뽑는 것은 일이 아니다. 에이전트는 그것을 1초 만에 grep 한다. 일은 grep 이 보여 주지 않는 깨짐이다.

### 자기 글을 믿지 않는다

맞는 것처럼 들리는 파급 범위 글은 쓸모가 없다. 사실이든 아니든 똑같이 그럴듯하게 읽힌다. 그래서 글을 돌려주지 않는다. 전체가 기대는 사실 한두 개를 찾아 코드를 돌려 증명한다.

#### 얼마나 확실한가

변경의 안전이 기대는 사실마다, 싸게 갈 수 있는 데까지 이 목록을 내려가고 어디서 멈췄는지 적는다.

1. 말로만 했다. 그것만으로는 가치가 없다.
2. 줄을 가리켰다. 실제 `file:line`, 또는 라이브러리 자체 소스.
3. 나쁜 경우가 일어날 수 없음을 보였다. 실패를 한 단계씩 따라갔고 거기에 닿지 않는다.
4. 돌렸다. 실제 코드를 부르고, 틀렸으면 크게 실패하는 스크립트나 테스트.
5. 돌고 있는 앱에서 재현했다.

4단계는 보통 작은 스크립트 하나다. 앱이 싣는 것과 같은 라이브러리를 import 해서 걱정되는 바로 그 함수를 부른다.

### 단계

1. 변경을 읽는다. diff, 더하고 바꾸고 지운 심볼, 그리고 지금 달라진 동작. diff 가 말로 드러내지 않는 부분까지. PR 과 커밋을 가져온다.
2. 안전 근거인 사실 하나를 찾는다. 위험해 보이는 변경 대부분은 사실 하나 덕에 안전하다. 예를 들어 「이 호출은 이미 죽은 캐시 항목만 지우고 다른 일은 하지 않는다」. 그 사실을 찾는다. 그것이 성립하면 위험한 경우 대부분이 한꺼번에 지워진다. 「혹시」의 긴 목록이 아니라 여기에 시간을 쓴다.
3. grep 이 멈추는 곳을 본다. 부르는 라이브러리의 소스를 읽고, 고정된 버전과 로컬 패치를 확인한다. 언제 도는지 따진다. 마이크로태스크, unmount 와 teardown, Solid 와 React 의 차이. 심볼 검색이 놓치는 것을 따라간다. API 가 돌려주는 JSON, DB 컬럼, wire 포맷, 같은 바이트를 읽는 다른 언어, 기능 플래그, 세 단계 아래 코드.
4. 위험마다 정직하게. 실제로 일어날 확률과 일어났을 때의 비용을 단다. 확인한 위험은 남긴다. 확인하고 지운 것은 따로 적는다. 실제 `file:line` 을 인용한다. 아무것도 안 나온 검색도 답이다. 호출자나 API 를 지어내지 않는다.
5. 그 사실을 증명한다. 실제 코드를 돌리는 스크립트나 테스트를 써서 돌리고, 나온 출력을 붙인다.
6. 크거나 넓은 변경이면 `../design/SKILL.md` 를 Read 로 읽고 그 경쟁 절차로 돌린다. 같은 질문을 여러 모델에 묻고 답을 합친다. 다른 모델이 서로 다른 실제 버그를 잡는다.

### 돌려줄 것

- **무엇을 하는가.** 바뀐 것. 뻔하지 않은 부분까지.
- **안전 근거 하나.** 그 사실을 적고, 몇 단계까지 갔는지 말하고, 증명을 보인다. 증명하지 못했으면 「증명 안 됨」이라고 쓴다.
- **위험.** 위험마다 어떻게 깨지는지, `file:line`, 얼마나 일어날 법하고 얼마나 나쁜지, 어떻게 확인하는지. 중요한 것은 증명을 붙인다.
- **지운 것.** 확인한 것과 괜찮은 이유.
- **머지 전에.** 진짜 버그를 잡을 가장 싼 테스트나 재현. 쓴 스크립트 포함.

`../write/SKILL.md` 를 Read 로 읽고 그 기준으로 쓰고, 실제 코드를 인용하고, 공개되는 곳에 가기 전에 사적인 것을 지운다.

**답:** 위의 글. 안전 근거 하나는 증명했거나 「증명 안 됨」으로 적는다.
