# 리뷰

적대적 검토자들이 변경이나 설계를 깨려고 한다. 실행으로 증명된 지적만 살아남는다. 동시에 diff 밖에서 깨질 것을 찾고, 그 변경이 안전한 이유가 되는 사실 하나를 실제 코드를 돌려 증명한다.

지적을 보고만 한다. 고치지 않는다. 고치는 것은 사용자가 따로 시킬 때 한다.

`/dev:how` 는 코드가 무엇을 하는지, `/dev:why` 는 왜 그런 모양인지 알려 준다. 이 스킬은 그것이 다른 곳에서 무엇을 깨는지 알려 준다. 호출자 목록을 뽑는 것은 일이 아니다. grep 이면 1초다. 일은 grep 이 보여 주지 않는 깨짐이다.

## 시작

세션의 작업 목록 도구(데스크톱 앱이면 update_plan, 아니면 TodoWrite)에 Frame, 파급 범위, Fan out, Verify, 보고 를 연다.

## 1. Frame

범위는 사용자가 말한 것이다. 말하지 않았으면 기반 브랜치와의 merge-base 부터 작업 트리까지의 브랜치 diff 다.

```bash
base=$(git merge-base HEAD origin/main)   # 기반 브랜치가 다르면 바꾼다
git diff "$base"                           # 커밋한 것 + 커밋 안 한 것
git log --oneline "$base"..HEAD
```

변경의 의도를 자기 말로 다시 적는다. 사용자 메시지, 커밋, PR 설명(`gh pr view`)에서 끌어낸다. 의도가 불분명하면 가장 그럴듯한 의도로 정하고, 그 가정을 보고 맨 위에 적는다. 의도를 묻느라 멈추지 않는다. 의도 자체가 제품 결정이라 정할 수 없을 때만 AskUserQuestion 으로 하나 묻는다.

## 2. 파급 범위: 안전 근거 하나를 증명한다

검토자를 띄우고, 기다리는 동안 부모가 직접 한다.

### 그럴듯한 글을 믿지 않는다

맞는 것처럼 들리는 파급 범위 글은 쓸모가 없다. 사실이든 아니든 똑같이 그럴듯하게 읽힌다. 그래서 글을 돌려주지 않는다. 전체가 기대는 사실 한두 개를 찾아 코드를 돌려 증명한다.

### 확신 사다리

변경의 안전이 기대는 사실마다, 싸게 갈 수 있는 데까지 이 목록을 내려가고 어디서 멈췄는지 적는다.

1. 말로만 했다. 그것만으로는 가치가 없다.
2. 줄을 가리켰다. 실제 `file:line`, 또는 라이브러리 자체 소스.
3. 나쁜 경우가 일어날 수 없음을 보였다. 실패 경로를 한 단계씩 따라가 거기에 닿지 않음을 보였다.
4. 돌렸다. 실제 코드를 부르고, 틀렸으면 크게 실패하는 스크립트나 테스트.
5. 돌고 있는 앱에서 재현했다.

4단계는 보통 작은 스크립트 하나다. 앱이 싣는 것과 같은 라이브러리를 import 해서 걱정되는 바로 그 함수를 부른다.

### 단계

1. 변경을 읽는다. diff, 더하고 바꾸고 지운 심볼, 그리고 지금 달라진 동작. diff 가 말로 드러내지 않는 부분까지. PR 과 커밋을 가져온다.
2. 안전 근거인 사실 하나를 찾는다. 위험해 보이는 변경 대부분은 사실 하나 덕에 안전하다. 예를 들어 「이 호출은 이미 죽은 캐시 항목만 지우고 다른 일은 하지 않는다」. 그 사실을 찾는다. 그것이 성립하면 위험한 경우 대부분이 한꺼번에 지워진다. 「혹시」의 긴 목록이 아니라 여기에 시간을 쓴다.
3. grep 이 멈추는 곳을 본다. 부르는 라이브러리의 소스를 읽고, 고정된 버전과 로컬 패치를 확인한다. 언제 도는지 따진다. 마이크로태스크, unmount 와 teardown, Solid 와 React 의 차이. 심볼 검색이 놓치는 것을 따라간다. API 가 돌려주는 JSON, DB 컬럼, wire 포맷, 같은 바이트를 읽는 다른 언어, 기능 플래그, 세 단계 아래 코드.
4. 위험마다 정직하게. 실제로 일어날 확률과 일어났을 때의 비용을 단다. 확인한 위험은 남긴다. 확인하고 지운 것은 따로 적는다. 실제 `file:line` 을 인용한다. 아무것도 안 나온 검색도 답이다. 호출자나 API 를 지어내지 않는다.
5. 그 사실을 증명한다. 실제 코드를 돌리는 스크립트나 테스트를 써서 돌리고, 나온 출력을 붙인다. 스크립트는 `/tmp/review-<slug>/` 에 두고 경로를 보고한다.

## 3. Fan out: 적대적 검토자

검토자는 `~/.claude/rules/dev-models.md` 의 `review reviewers` 줄의 항목마다 하나씩이고, 없으면 `fable high`, `opus high`, 부모 모델(`model` 을 뺀다) 하나씩이다. 작고 위험이 낮은 diff 면 하나로 줄인다. 크거나 넓은 변경이면 이 패널을 꼭 돌린다. 다른 모델이 서로 다른 실제 버그를 잡는다. `Agent` 가 모델을 거부하면 그 자리를 남은 모델로 돌리고 그렇게 말한다.

1. 커밋하지 않은 변경을 패치로 만든다. 검토자 worktree 는 커밋에서 잘리므로 이 패치가 없으면 커밋 안 한 변경을 보지 못한다.

   ```bash
   mkdir -p /tmp/review-<slug>
   { git diff HEAD; git ls-files -z --others --exclude-standard | xargs -0 -n1 git diff --no-index /dev/null; } \
     > /tmp/review-<slug>/uncommitted.patch   # 추적 안 하는 새 파일까지
   ```

2. 검토자 N개를 한 메시지에서 띄운다. 각 호출은 `subagent_type: "dev:worker"`, `model`, `isolation: "worktree"`, `run_in_background: true`. 브리프에 범위, 다시 적은 의도, 패치 경로와 「먼저 `git apply /tmp/review-<slug>/uncommitted.patch`」, 그리고 아래 지시를 그대로 넣는다.

> 이 변경을 깨라. 지적마다 실제 코드를 상대로 돌린 것으로 증명한다. 실패하는 테스트, 재현 스크립트, 잘못된 동작을 보여 주는 명령 출력. 설계나 계획이면 프로토타입을 돌리거나 지금 트리를 찔러 본다. 재현물은 네 worktree 안에 둔다. 지적마다 제목, 정확한 명령, 그 명령이 찍은 출력, 의도대로라면 나와야 할 출력을 적는다. 돌리지 않은 것은 뺀다. 스타일, 이름, 구조, 미래의 변경이 있어야 문제가 되는 위험이 여기 든다. 지적이 없는 것도 올바른 결과다. 저장소 파일은 고치지 말고 커밋하지 마라.

검토자가 결과 없이 떨어지면 N-1 개로 진행하고 적는다. `/dev:design` 의 심사, 기반 고르기, 접붙이기는 하지 않는다. 검토자마다 다른 결함을 찾으므로 한 검토자의 목록을 고르지 않고 검증된 지적을 모두 남긴다.

## 4. Verify: 다시 돌려 나눈다

지적마다 그 명령을 부모가 직접 다시 돌린다. 파급 범위에서 찾은 위험도 같이 나눈다. 같은 근본 원인을 가진 지적은 하나로 합친다.

| 분류 | 조건 |
|---|---|
| **act on** | 다시 돌려 실패가 보이고, 그 실패가 의도를 깬다. |
| **consider** | 다시 돌려 실패가 보이지만, 의도를 깨는지는 판단이 남는다. 드문 조건에서만 나거나, 의도가 그 경우를 정하지 않았거나, 비용이 확률에 비해 작다. 판단에 필요한 것을 한 줄 적는다. |
| **noted** | 사실이지만 의도를 깨지 않는 것. 파급 범위에서 확인하고 지운 것도 여기 적는다. |
| **dismissed** | 다시 돌려도 실패가 재현되지 않았거나, 돌린 증거가 없거나, 실패가 의도와 관계없다. 검토자마다 개수와 이유를 적는다. |

검토자는 모두 같은 회사(Anthropic) 모델이다. 비슷한 맹점을 함께 가질 수 있으니 「지적 없음」을 안전의 증명으로 쓰지 않는다. 이 한계를 보고에 적는다.

끝나면 검토자 worktree 와 브랜치는 지운다. 증거로 남길 재현물은 `/tmp/review-<slug>/` 로 옮긴 뒤 지운다.

## 보고

`/dev:write` 기준으로 쓴다. 실제 코드를 인용한다. 공개되는 곳에 올리기 전에 사적인 정보를 지운다.

- **의도**: 다시 적은 의도. 가정했으면 그 가정.
- **무엇을 하는가**: 바뀐 것. 뻔하지 않은 부분까지.
- **안전 근거 하나**: 그 사실, 사다리 몇 단계까지 갔는지, 증명(명령과 출력). 증명하지 못했으면 「증명 안 됨」.
- **act on**: 지적마다 명령, 출력, 어떻게 의도를 깨는지, `file:line`, 확률과 피해, 찾은 검토자.
- **consider**: 같은 꼴에 판단할 거리 한 줄.
- **noted**: 확인하고 괜찮았던 것과 이유.
- **dismissed**: 검토자마다 버린 개수와 이유.
- **머지 전에**: 진짜 버그를 잡을 가장 싼 테스트나 재현. 쓴 스크립트 경로 포함.
- **한계**: 검토 패널이 모두 같은 회사 모델이라는 한 줄.

검증된 지적이 없으면 「검증된 지적 없음」이라고 쓴다.
