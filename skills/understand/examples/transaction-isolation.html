UNDERSTAND

트랜잭션 격리 수준

트랜잭션이 같은 행을 읽고 판단하고 쓰는 사이에 다른 커밋이 끼어들면, DB 는 격리 수준과 읽는 방식에 따라 늦은 쪽이 덮어쓰게 두거나 기다리게 하거나 중단시키고, 중단된 쪽은 앱이 읽기부터 다시 돌린다.

01출발점

여러 스레드가 공유 변수를 읽고 계산하고 쓰는(read-modify-write) 사이에 다른 스레드가 끼면 갱신을 잃는 경쟁 조건은 이미 안다.

  • 읽기 ≈ 변수 읽기
  • 앱의 판단 ≈ 계산
  • 쓰기 ≈ 변수 쓰기
  • 끼어든 커밋 ≈ 다른 스레드

결과를 바꾸는 차이

  • 스레드 코드는 mutex 나 CAS 를 직접 써야 막힌다. DB 에서는 코드의 잠금이 아니라 격리 수준과 읽는 방식이 덮어쓰기, 기다리기, 중단 가운데 하나를 고른다.
  • CAS 실패는 값 하나를 다시 읽는 일이지만 40001 은 트랜잭션 전체의 롤백이다. 트랜잭션 안에서 한 판단과 쓰기를 모두 다시 해야 한다.

02뼈대

1재고 10 을 읽고 1 을 뺄지 판단한다

주문 트랜잭션이 SELECT 로 재고 10 을 읽는다.

앱은 재고가 남았으니 9 를 새 값으로 정한다.

2판단한 값을 UPDATE 로 쓴다

UPDATE 가 재고를 9 로 바꾸고 커밋한다. SELECT 와 UPDATE 사이에는 앱이 판단하는 시간만큼 틈이 있다.

3그 틈에 다른 주문이 먼저 커밋한다

두 번째 주문도 같은 순간에 재고 10 을 읽고 9 로 정한다. 한쪽이 먼저 9 를 커밋하면 다른 쪽이 읽은 10 은 낡은 값이 된다.

늦은 쪽도 그대로 9 를 쓰면 두 개가 팔렸는데 재고는 9 인 lost update 가 된다.

4늦은 쪽이 가는 길은 DB 가 정한다

PostgreSQL 기본값 READ COMMITTED 의 일반 UPDATE 는 오류 없이 덮어쓴다.

SELECT ... FOR UPDATE 로 읽으면 앞 주문의 커밋을 기다렸다가 9 를 읽는다.

REPEATABLE READ 에서는 늦은 쪽의 UPDATE 가 SQLSTATE 40001 로 중단된다.

5중단된 쪽은 앱이 처음부터 다시 돌린다

40001 을 받은 트랜잭션은 통째로 롤백된다. 앱이 SELECT 부터 다시 돌리면 9 를 읽고 8 을 쓴다.

03설명되는 현상

MySQL InnoDB 의 REPEATABLE READ 는 이름이 같아도 lost update 를 막지 않는다. 일반 SELECT 는 스냅샷을 읽지만 UPDATE 는 최신 커밋 행에 써서, 늦은 쪽이 낡은 판단의 값을 오류 없이 쓴다.

끼어든 커밋 → 읽기 → 앱의 판단 → 쓰기 → DB 의 충돌 규칙

UPDATE ... SET stock = stock - 1 WHERE id = 7 AND stock >= 1 은 읽기와 판단과 쓰기를 한 문장에서 한다. READ COMMITTED 에서도 늦은 쪽은 앞 커밋을 기다린 뒤 갱신된 행으로 조건을 다시 보고 8 을 쓴다.

읽기 → 앱의 판단 → 쓰기 → DB 의 충돌 규칙

인기 상품 한 행에 FOR UPDATE 주문이 몰리면 뒤 주문은 앞 주문들이 모두 커밋할 때까지 줄을 선다. 오류는 나지 않고 응답만 길어진다.

DB 의 충돌 규칙 → 읽기 → 끼어든 커밋

격리 수준을 REPEATABLE READ 로 올려도 재시도 코드가 없으면 잃던 갱신만큼 40001 오류가 사용자에게 간다. 틀린 결과가 오류로 바뀔 뿐이다.

DB 의 충돌 규칙 → 쓰기 → 재시도

몇 분 걸리는 정산 조회가 REPEATABLE READ 로 도는 동안에도 주문 쓰기는 기다리지 않고 정산도 중단되지 않는다. 일반 읽기는 잠그지 않고, 쓰기가 없는 트랜잭션에는 충돌이 걸릴 자리가 없다.

읽기 → DB 의 충돌 규칙 → 쓰기

04새로운 추론

콘서트 좌석처럼 한 행에 수백 명이 동시에 몰리면 무엇을 쓰는가?

잠금 읽기나 한 문장의 조건부 UPDATE 를 쓴다. 중단과 재시도에 기대지 않는다.

거의 모든 요청이 같은 행에 쓰므로, 중단된 요청이 재시도로 다시 읽는 사이에 또 다른 커밋이 끼어든다. 기다리게 하는 규칙에서는 한 번 줄을 선 요청이 다시 돌지 않는다.

DB 의 충돌 규칙 → 쓰기 → 재시도 → 읽기 → 끼어든 커밋

상품 상세를 많이 읽고 그 가운데 몇 %만 재고를 고치면 무엇을 쓰는가?

REPEATABLE READ 와 재시도를 쓰고, 읽을 때마다 FOR UPDATE 를 걸지 않는다.

잠금은 판단 앞의 읽기에 걸려 쓰지 않을 요청까지 줄을 세운다. 중단은 실제로 쓰는 요청이 같은 행에서 겹칠 때만 일어난다.

DB 의 충돌 규칙 → 읽기 → 앱의 판단 → 쓰기

판단 단계에서 외부 결제 API 를 부르는 트랜잭션이 40001 을 받으면 어떻게 되는가?

재시도가 결제를 한 번 더 부른다. 결제 호출은 커밋이 끝난 뒤로 옮긴다.

재시도는 읽기부터 판단까지 다시 돌리는데, 롤백은 DB 안의 쓰기만 되돌리고 판단에서 부른 바깥 호출은 되돌리지 않는다.

쓰기 → 재시도 → 읽기 → 앱의 판단

재고를 읽어 화면에 보여 주고 사용자가 몇 분 뒤 확정하는 흐름은 어떻게 짜는가?

읽기와 쓰기를 다른 트랜잭션으로 나누고, 쓸 때 조건부 UPDATE 로 읽은 값이 그대로인지 다시 확인한다.

판단이 길수록 읽기와 쓰기 사이 틈에 끼어드는 커밋이 늘고, 그 틈을 잠금으로 막으면 몇 분 동안 다른 요청이 기다린다.

끼어든 커밋 → 읽기 → 앱의 판단 → 쓰기 → DB 의 충돌 규칙

05적용 한계

성립 조건

  • InnoDB 의 잠금 읽기와 SERIALIZABLE 의 공유 잠금 읽기 변환은 autocommit 이 꺼져 있을 때(START TRANSACTION 이나 autocommit = 0)만 일어난다.

반례

  • FOR UPDATE 는 찾은 행만 잠근다. 같은 시간대 예약이 없는지 확인한 결과가 빈 집합이면 잠글 행이 없어 동시 요청 두 건이 모두 INSERT 되고, SERIALIZABLE 이나 배타 제약(EXCLUDE)이 있어야 막힌다.
  • 두 트랜잭션이 같은 조건을 읽고 서로 다른 행을 고치는 write skew 는 겹치는 쓰기가 없어 REPEATABLE READ 를 통과하고, PostgreSQL SERIALIZABLE 만 잡는다.

트레이드오프

  • PostgreSQL SERIALIZABLE 은 차례로 돌렸다면 나지 않았을 직렬화 실패도 낸다. 같은 행 충돌이 없어도 재시도 코드가 필요하다.
  • 여러 행을 서로 다른 순서로 잠그는 트랜잭션들은 교착에 빠질 수 있고, 그러면 DB 가 한쪽을 중단시킨다. 기다리게 하는 규칙도 재시도를 완전히 없애지 못한다.
