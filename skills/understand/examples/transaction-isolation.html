UNDERSTAND

트랜잭션 격리 수준

같은 행을 읽고 판단하고 쓰는 요청이 겹치면 DB 는 격리 수준과 읽는 방식에 따라 그 끼어듦을 덮어쓰게 두거나 기다리게 하거나 중단시키고, 기다림과 재시도 가운데 어느 쪽이 싼지는 쓰는 요청의 비율과 재시도 비용이 정한다.

01출발점

여러 스레드가 공유 변수를 읽고 계산하고 쓰는(read-modify-write) 사이에 다른 스레드가 끼면 갱신을 잃는 경쟁 조건은 이미 안다.

그대로 통하는 것

  • 트랜잭션이 SELECT 로 읽고 앱에서 판단한 뒤 UPDATE 로 쓰는 사이에 다른 트랜잭션이 같은 행을 고치고 커밋하면, 스레드 경쟁 조건과 같이 앞 갱신이 사라진다.
  • 막는 길도 같은 둘이다. mutex 처럼 상대를 기다리게 하거나, CAS 루프처럼 쓰는 순간 값이 바뀌었으면 실패시키고 다시 읽게 한다.

결과를 바꾸는 차이

  • 어느 길로 갈지는 코드의 잠금이 아니라 격리 수준과 읽는 방식이 정한다. READ COMMITTED 의 일반 UPDATE 는 덮어쓰고, SELECT ... FOR UPDATE 는 기다리게 하고, REPEATABLE READ 는 40001 로 중단시킨다.
  • CAS 실패는 값 하나를 다시 읽는 일이지만 40001 은 트랜잭션 전체의 롤백이다. 재시도 한 번마다 트랜잭션 길이와 앱 왕복이 다시 들어, 기다림과 재시도의 비용이 달라진다.
  • MVCC 에서는 읽기가 쓰기를 기다리지 않고 읽기만 한 트랜잭션은 중단되지 않는다. 그래서 충돌은 요청 수가 아니라 실제로 쓰는 요청 수로 정해진다.

02핵심 메커니즘

직렬화 가능성

같은 행을 읽고 쓰는 요청 w 건이 겹치면 차례 실행과 같은 결과는 한 번에 하나씩 커밋하는 것뿐이라, 나머지 w-1 건은 덮어쓰거나 기다리거나 중단돼야 한다.

이 모델이 설명하지 못하는 것직렬화 가능성은 결과가 어떤 차례 순서와 같다는 것만 보장하고, 어느 요청이 먼저 성공할지는 정하지 않는다.

낙관적·비관적 동시성 제어

잠금은 충돌을 미리 가정해 같은 행의 모든 요청을 줄 세우고, 스냅샷과 재시도는 충돌이 없다고 가정해 진행한 뒤 겹친 쓰기만 다시 돌린다.

이 모델이 설명하지 못하는 것이 비교는 한 행의 경합만 본다. 여러 행을 다른 순서로 잠그는 교착이나, 실제 부하에서의 대기와 재시도 비용은 재야 알 수 있다.

가정 모델: 요청 n 건이 한 행에 동시에 와서 길이 d 의 트랜잭션으로 읽고 그 가운데 비율 q 만 쓴다. 잠금 방식은 쓸지 정하기 전에 읽으므로 모든 요청이 FOR UPDATE 로 줄을 서고, 재시도 방식에서 40001 을 받은 요청은 r 뒤에 함께 다시 시작한다.

03설명되는 현상

  • PostgreSQL 기본값 READ COMMITTED 에서 재고 10 인 행에 주문 둘이 동시에 읽고 쓰면 두 주문이 모두 성공하고 재고는 9 다. 이 lost update 는 오류 없이 일어난다.

    쓰는 요청RC 에서 잃는 갱신

  • 같은 두 주문을 REPEATABLE READ 로 돌리면 늦게 쓴 쪽이 SQLSTATE 40001 로 롤백되고, 앱이 SELECT 부터 다시 돌려야 9 를 읽고 8 을 쓴다.

    쓰는 요청RR 에서 버린 실행

  • 격리 수준을 올려도 재시도 코드가 없으면 잃던 갱신만큼 40001 오류가 사용자에게 간다. 높은 등급은 틀린 결과를 오류로 바꿀 뿐이다.

    RC 에서 잃는 갱신RR 에서 버린 실행

  • SELECT ... FOR UPDATE 로 읽으면 오류 없이 앞 요청의 커밋을 기다렸다가 새 값을 받는다. 인기 상품 한 행에 요청이 몰리면 뒤 요청은 앞 요청 수만큼 기다린다.

    같은 행 동시 요청잠금 방식 평균 응답

  • 몇 분 걸리는 정산 조회가 REPEATABLE READ 로 도는 동안에도 주문 쓰기는 기다리지 않고, 정산은 중단되지 않는다. 읽기만 하는 트랜잭션은 쓰는 요청 수에 들지 않는다.

    읽은 뒤 쓰는 비율쓰는 요청

04새로운 추론

콘서트 좌석 예매처럼 인기 좌석 한 행에 수백 명이 동시에 몰리면 무엇을 쓰는가?

잠금 읽기나 한 문장의 조건부 UPDATE 를 쓴다. 재시도 방식은 쓰지 않는다.

읽은 요청 거의 모두가 쓰므로 쓰는 비율이 100% 에 가깝고, 버린 실행은 쓰는 요청 수의 제곱으로 늘어 재시도 비용이 그만큼 곱해지는 반면 잠금의 대기는 요청 수에 비례한다.

상품 상세를 많이 읽고 그 가운데 몇 %만 장바구니에 담아 재고를 고치면 무엇을 쓰는가?

REPEATABLE READ 와 재시도를 쓰고, 읽을 때마다 FOR UPDATE 를 걸지 않는다.

쓰는 비율이 낮으면 쓰는 요청이 둘이 되지 않아 충돌이 없지만, 잠금 방식은 쓰지 않을 요청까지 같은 줄에 세워 평균 응답이 요청 수에 비례해 는다.

트랜잭션을 짧게 줄이면 두 방식 가운데 어느 쪽이 더 이득을 보는가?

재시도 비용이 그대로라면 잠금 방식이 더 이득을 보고, 재시도 방식이 성립하는 쓰기 비율의 상한이 낮아진다.

트랜잭션 길이는 두 평균 응답에 똑같이 곱해지므로 교차점은 재시도 비용과 트랜잭션 길이의 비율로 정해지고, 길이를 줄이면 그 비율이 커진다.

40001 을 받으면 외부 결제 API 를 다시 부르는 구조라면 교차점은 어디로 가는가?

더 낮은 쓰기 비율로 옮겨 가 잠금 방식이 일찍 이긴다. 결제가 두 번 일어나지 않게 하는 일도 따로 남는다.

재시도 한 번 비용이 커지면 재시도 방식의 평균 응답에서 버린 실행 항이 커지고, DB 의 롤백은 바깥 호출을 되돌리지 않는다.

같은 행을 고치는 두 주문을 다른 DB 설정이나 쓰기 방식으로 돌리면 늦은 쪽은 어느 길로 가는가?

중단된다. 늦은 쪽은 REPEATABLE READ 때와 같이 40001 로 롤백되고, 재시도하면 새 값을 읽는다.

SERIALIZABLE 은 REPEATABLE READ 의 쓰기 충돌 검사에 읽기와 쓰기의 의존을 보는 SSI 검사를 더한 것이라 같은 행 충돌은 같은 방식으로 잡힌다.

덮어쓴다. 늦은 쪽의 UPDATE 가 오류 없이 낡은 판단의 값을 써서 두 주문이 성공하고 재고는 9 로 남는다.

InnoDB 의 일반 SELECT 는 스냅샷을 읽지만 UPDATE 는 최신 커밋 행에 쓰므로, 이름이 같아도 lost update 를 막지 않는다.

기다리다 중단된다. 두 SELECT 가 공유 잠금을 잡아 서로의 UPDATE 를 막는 교착이 생기고 InnoDB 가 한쪽을 롤백한다.

autocommit 이 꺼져 있으면 InnoDB SERIALIZABLE 은 일반 SELECT 를 공유 잠금 읽기로 바꾼다. 롤백된 쪽을 다시 돌리는 일은 여기서도 앱이 한다.

기다린다. UPDATE ... SET stock = stock - 1 WHERE id = 7 AND stock >= 1 에서 늦은 쪽은 앞 커밋을 기다린 뒤 9 에서 1 을 빼 8 을 쓴다.

READ COMMITTED 의 UPDATE 는 상대 커밋 뒤 갱신된 행으로 식과 WHERE 를 다시 평가하므로, 읽기와 판단과 쓰기가 한 문장에서 일어나 끼어들 틈이 없다.

05적용 한계

성립 조건

  • 격리 수준은 한 DB 안의 트랜잭션 사이 보장이다. 캐시, 메시지 큐, 외부 결제 호출은 그 밖에 있어서 재시도하면 두 번 일어날 수 있다.
  • InnoDB 의 잠금 읽기와 SERIALIZABLE 의 공유 잠금 읽기 변환은 autocommit 이 꺼져 있을 때(START TRANSACTION 이나 autocommit = 0)만 일어난다.

반례

  • FOR UPDATE 는 찾은 행만 잠근다. 같은 시간대 예약이 없는지 확인한 결과가 빈 집합이면 잠글 행이 없어 동시 요청 두 건이 모두 INSERT 되고, SERIALIZABLE 이나 배타 제약(EXCLUDE)이 있어야 막힌다.
  • 두 트랜잭션이 같은 조건을 읽고 서로 다른 행을 고치는 write skew 는 겹치는 쓰기가 없어 REPEATABLE READ 를 통과하고, PostgreSQL SERIALIZABLE 만 잡는다.
  • PostgreSQL SERIALIZABLE 은 차례 실행이었다면 나지 않았을 직렬화 실패도 내므로, 실제 버린 실행은 이 모델의 같은 행 충돌보다 많을 수 있다.

확인되지 않은 전제

  • 모든 요청이 같은 순간에 오고 실패한 요청이 함께 다시 시작한다고 둔 상한 모델이다. 도착이 흩어지거나 재시도에 무작위 대기를 두면 버린 실행은 이보다 적다.
