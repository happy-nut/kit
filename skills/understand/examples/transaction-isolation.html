01

본질

트랜잭션 격리 수준은 동시에 도는 트랜잭션들이 하나씩 차례로 돌았을 때와 다른 결과를 어디까지 허용할지 정한 등급이다.

모든 트랜잭션을 차례로 돌리면 결과는 늘 맞지만, 서로 기다리느라 처리량이 떨어진다.

그래서 DB 는 몇 가지 이상 현상을 허용하는 낮은 등급을 두고, 무엇을 감수할지는 애플리케이션이 고르게 한다.

같은 이름의 등급도 DB 마다 막는 현상이 달라서, 이름만 보고 고르면 동시성 버그가 남는다.

이 깊이에서 보이는 항목이 없다. 더 보기를 누르면 이 섹션만 펼친다.

02

전체 구조

L1
막을 현상과 치를 값의 교환

등급을 올리면 막는 이상 현상이 늘고, 그만큼 대기나 중단 같은 값을 더 치른다.

L2
교환을 이루는 네 요소

이상 현상

아래 다섯은 뒤로 갈수록 알아채기 어렵다. 앞의 셋은 SQL 표준이 이름 붙였고, 뒤의 둘은 표준의 표 밖에 있다.

  • L3
    dirty read 커밋 전 값 읽기다. 다른 트랜잭션이 아직 커밋하지 않은 값을 읽는다. 그쪽이 롤백하면 없던 값을 근거로 판단한 셈이 된다.
  • L3
    nonrepeatable read 다시 읽으면 값이 바뀌는 현상이다. 같은 행을 두 번 읽는 사이에 다른 트랜잭션이 그 행을 고치고 커밋했다.
  • L3
    phantom read 다시 세면 행이 늘거나 주는 현상이다. 같은 조건으로 두 번 조회하는 사이에 다른 트랜잭션이 조건에 맞는 행을 넣거나 지웠다.
  • L3
    lost update 갱신 손실이다. 두 트랜잭션이 같은 값을 읽고 각자 계산해 쓰면, 나중 쓰기가 먼저 쓰기를 덮어 한쪽 변경이 사라진다.
  • L3
    write skew 각자 맞고 합치면 틀리는 현상이다. 두 트랜잭션이 같은 조건을 읽고 서로 다른 행을 고쳐, 둘이 함께 지키던 규칙이 깨진다.

SQL 표준 네 등급5

READ UNCOMMITTED(커밋 안 된 것도 읽음), READ COMMITTED(커밋된 것만 읽음), REPEATABLE READ(다시 읽어도 같음), SERIALIZABLE(차례 실행과 같음) 순으로 강해진다.

표준의 표에는 lost update 와 write skew 가 없다. 그래서 이 둘을 막는지는 같은 등급 이름이라도 DB 마다 다르다.

막는 방법

  • L3
    잠금 충돌하는 트랜잭션을 상대가 커밋할 때까지 기다리게 한다.
    자세히

    읽으면서 행을 잠그는 조회를 잠금 읽기라고 한다. SELECT ... FOR UPDATE 가 그 예다.

    InnoDB 의 갭 락(gap lock, 인덱스 값 사이 빈 구간에 거는 잠금)은 아직 없는 행이 새로 들어오는 것까지 막는다.

  • L3
    MVCC1 다중 버전 동시성 제어다. 쓸 때 행의 새 버전을 만들고, 읽기는 스냅샷(정해진 시점까지 커밋된 데이터의 모습)을 보게 한다.
    자세히

    읽기가 옛 버전을 보므로 읽기와 쓰기가 서로 기다리지 않는다.

    트랜잭션 전체가 스냅샷 하나를 읽는 방식을 스냅샷 격리라고 한다. PostgreSQL 의 REPEATABLE READ 가 이 방식이다.

  • L3
    SSI6 직렬화 가능 스냅샷 격리다. 트랜잭션마다 스냅샷 하나를 읽게 하면서 서로의 읽기와 쓰기를 검사해, 차례 실행과 다른 결과가 날 수 있으면 하나를 중단한다.

치르는 값

교착은 두 트랜잭션이 서로의 잠금을 기다려 둘 다 못 나가는 상태다. DB 는 한쪽을 끊어 푼다.

중단된 트랜잭션을 처음부터 다시 실행하는 일은 DB 가 아니라 애플리케이션의 몫이다.

이 깊이에서 보이는 항목이 없다. 더 보기를 누르면 이 섹션만 펼친다.

같은 REPEATABLE READ 가 쓰기에서 갈린다

PostgreSQL 과 InnoDB 모두 REPEATABLE READ 의 일반 SELECT 는 트랜잭션에서 처음 데이터를 읽을 때 잡은 스냅샷을 끝까지 읽는다.

PostgreSQL 은 스냅샷 이후 다른 트랜잭션이 고치고 커밋한 행을 쓰려 하면 「could not serialize access due to concurrent update」 오류로 트랜잭션을 중단한다.

InnoDB 는 UPDATE 와 DELETE 를 할 때 스냅샷이 아니라 최신 커밋 값을 읽고 쓴다. 오류 없이 덮어쓰므로 lost update 가 생긴다.

InnoDB 에서는 자기가 고친 행이 그 뒤 조회에 보인다. 그래서 다른 트랜잭션이 막 넣은 행을 UPDATE 로 건드리면, 첫 조회에 없던 행이 나타난다.13

같은 등급 이름, DB 마다 다른 보장12

비교 기준: 각 칸은 잠금 읽기를 쓰지 않을 때 그 DB 에서 실제로 생기는 이상 현상이다

당직 의사 두 명 지어낸 예시

규칙은 「당직 의사는 늘 한 명 이상」이다. 지금 의사 A 와 B 가 당직이다.

A 와 B 가 동시에 당직을 빼 달라고 요청한다. 두 트랜잭션은 각자의 스냅샷에서 당직 수를 세고 두 명을 본다.

A 의 트랜잭션은 A 의 행을, B 의 트랜잭션은 B 의 행을 당직 해제로 고친다. 고친 행이 서로 달라 쓰기 충돌이 없다.

REPEATABLE READ 에서는 둘 다 커밋되고 당직은 0 명이 된다. 두 판단은 각자의 스냅샷에서는 맞았다.

PostgreSQL SERIALIZABLE 에서는 둘 중 하나가 직렬화 실패로 중단된다. 다시 시도하면 당직 한 명을 보고 요청을 거절한다.

PostgreSQL SSI 가 write skew 를 막는 법

SSI 는 트랜잭션마다 무엇을 읽었는지 술어 잠금(predicate lock, 읽은 조건의 범위에 남기는 표시)으로 기록한다.

이 표시는 다른 트랜잭션을 기다리게 하지 않는다. 누가 누구의 쓰기를 못 본 채 읽었는지 알아내는 데만 쓴다.

그런 관계가 이어져 차례 실행으로 설명할 수 없는 모양이 될 수 있으면, 그중 하나를 「could not serialize access due to read/write dependencies among transactions」 오류로 중단한다.

표시가 많아 메모리가 모자라면 페이지 단위 표시를 테이블 단위로 합친다. 이때 직렬화 실패가 더 자주 난다.16

InnoDB 의 갭 락과 next-key lock

InnoDB 의 REPEATABLE READ 는 잠금 읽기, UPDATE, DELETE 에서 next-key lock(행 잠금과 그 앞 갭 락을 합친 것)을 건다.

next-key lock 은 훑은 인덱스 범위 전체에 새 행이 들어오지 못하게 해서 잠금 읽기의 phantom read 를 막는다.

유일 인덱스로 한 행을 정확히 찾을 때는 그 행만 잠그고 앞의 갭은 잠그지 않는다.

갭 락끼리는 충돌하지 않는다. 두 트랜잭션이 같은 갭을 잠근 뒤 둘 다 그 갭에 행을 넣으려 하면 서로 기다리다 교착이 난다.

READ COMMITTED 로 내리면 갭 락은 외래 키와 중복 키 검사에만 쓰인다. 대기는 줄고 phantom read 가 생긴다.42

이 깊이에서 보이는 항목이 없다. 더 보기를 누르면 이 섹션만 펼친다.

04

조건과 한계

성립 조건

  • 높은 등급의 보장은 중단된 트랜잭션을 애플리케이션이 처음부터 다시 실행할 때 완성된다. 재시도 코드가 없으면 직렬화 실패가 그대로 사용자 오류가 된다.1

핵심 전제

  • 격리 수준은 한 DB 안의 트랜잭션 사이의 약속이다. 캐시, 메시지 큐, 다른 DB 를 함께 고치는 흐름은 이 보장 밖에 있다.

반례

  • Oracle 의 SERIALIZABLE 은 스냅샷 격리라서 write skew 가 생긴다. 등급 이름이 같아도 막는 현상은 같지 않다.7

트레이드오프

  • 등급을 올리면 이상 현상은 줄지만 대기, 교착, 중단이 는다. 인기 상품 재고처럼 한 행에 쓰기가 몰리면 이 값이 커진다. 얼마나 커지는지는 실제 부하로 재야 안다.

적용 한계

  • PostgreSQL 의 잠금 읽기는 이미 있는 행만 잠근다. 「같은 시간대 예약이 없음」을 확인하고 넣는 흐름은 잠금 읽기로 못 막고 SERIALIZABLE 이나 배타 제약(EXCLUDE)이 필요하다.
  • InnoDB 의 REPEATABLE READ 에서는 같은 흐름을 잠금 읽기로 막을 수 있다. 조회 범위의 빈 구간에 갭 락이 걸려 다른 트랜잭션의 삽입이 기다리기 때문이다.4
재고가 1 개 남은 상품에 주문 두 건이 동시에 온다. 각 주문은 재고를 읽고, 1 이상이면 1 을 뺀 값을 써넣는다. 무엇을 고르면 어떻게 되는가?

조건을 고르면 결과와 이유가 보인다.

결과 두 주문이 모두 성공하고 재고는 0 이 된다. 한 개를 두 번 판다.

이유 둘 다 재고 1 을 읽고 0 을 쓴다. 나중 쓰기가 먼저 쓰기를 덮어 lost update 가 된다.

결과 늦게 쓴 주문이 직렬화 실패로 중단된다. 다시 시도하면 재고 0 을 읽고 거절된다.

이유 스냅샷 이후 다른 트랜잭션이 고친 행을 쓰려 하면 PostgreSQL 이 그 트랜잭션을 중단한다.

결과 두 주문이 모두 성공한다. REPEATABLE READ 인데도 한 개를 두 번 판다.

이유 일반 SELECT 는 스냅샷을 읽지만 UPDATE 는 최신 값에 오류 없이 덮어쓴다.

결과 둘째 주문은 첫째가 끝날 때까지 기다린 뒤 재고 0 을 읽고 거절된다.

이유 잠금 읽기는 최신 커밋 값을 읽고 행을 잡아 둔다. 읽기에서 쓰기까지 다른 쓰기가 끼어들지 못한다.

결과 둘째 주문의 UPDATE 는 0 행을 고친다. 애플리케이션은 이것을 보고 주문을 거절한다.

이유 「재고가 1 이상일 때만 1 을 뺀다」를 UPDATE 한 문장으로 쓰면, DB 가 쓰는 순간의 최신 값으로 조건을 다시 확인한다.

이 깊이에서 보이는 항목이 없다. 더 보기를 누르면 이 섹션만 펼친다.

05

기억할 원리

  1. 읽고 판단하고 쓰는 일이 동시에 돌면, 각자 맞게 판단해도 합친 결과는 틀릴 수 있다.

    성립 조건 여럿이 같은 상태를 읽고 그 판단으로 쓸 때 성립한다. 판단과 쓰기를 한 동작으로 묶거나 차례로 세우면 깨지지 않는다.

    적용 예 운영자 둘이 「서버는 한 대 이상 켜 둔다」를 각자 확인하고 서로 다른 서버를 동시에 내리면, 서버가 모두 꺼진다.

  2. 같은 이름의 보장이라도 구현마다 막는 것이 다르다. 이름이 아니라 막는 현상의 목록으로 확인한다.

    성립 조건 표준이 이름과 최소 조건만 정하고 구현의 재량이 큰 영역에서 성립한다.

    적용 예 HTTP 의 Cache-Control: no-cache 는 저장하지 말라는 뜻이 아니라 저장한 사본을 내주기 전에 서버에 다시 확인하라는 뜻이다. 저장을 막으려면 no-store 를 쓴다.

  3. 충돌이 드물면 일단 진행하고 끝에 검사하는 쪽이 싸고, 충돌이 잦으면 먼저 잠그는 쪽이 싸다.

    성립 조건 실패한 작업을 다시 해도 결과가 같을 때 성립한다. 외부 결제 호출처럼 다시 할 수 없는 작업은 먼저 잠근다.

    적용 예 위키는 편집 충돌이 드물어 저장할 때 버전을 견주고 겹치면 다시 고치게 한다. 공연 예매는 한 자리에 사람이 몰려 고르는 순간 좌석을 잡아 둔다.

이해 확인

먼저 답을 떠올린 뒤 연다.

PostgreSQL REPEATABLE READ 트랜잭션 A 가 주문 수를 센 뒤, B 가 새 주문을 넣고 커밋했다. A 가 다시 세면 늘어난 수가 보이는가?

답 보이지 않는다. A 는 처음 센 때의 스냅샷을 트랜잭션이 끝날 때까지 읽는다.

표준은 REPEATABLE READ 에서 phantom read 를 허용하지만 PostgreSQL 은 이것도 막는다.

A 가 READ COMMITTED 였다면 문장마다 새 스냅샷을 잡으므로 늘어난 수가 보인다.

「MySQL 은 기본이 REPEATABLE READ 라서 읽고 계산해 쓰는 코드도 안전하다」는 판단의 틀린 점은?

답 InnoDB 의 UPDATE 는 스냅샷이 아니라 최신 값에 덮어써서 lost update 가 생긴다. write skew 는 어느 DB 의 REPEATABLE READ 에서도 생긴다.

막는 현상은 등급 이름이 아니라 DB 구현이 정한다. 같은 코드를 PostgreSQL REPEATABLE READ 에서 돌리면 lost update 는 오류로 바뀐다.

두 사람이 같은 main 브랜치에서 갈라 각자 테스트를 통과한 변경을 동시에 머지했다. 충돌 없이 합쳐졌는데 main 의 테스트가 깨졌다. 어느 이상 현상과 같은 모양인가?

답 write skew 와 같다. 각자 갈라 낸 시점의 main 에서 맞게 판단했고, 고친 곳이 달라 쓰기 충돌이 감지되지 않았다.

머지를 하나씩 세우고 합친 결과로 다시 시험하는 머지 큐는, SERIALIZABLE 처럼 판단과 쓰기를 차례로 만든다.

PostgreSQL 을 SERIALIZABLE 로 바꾸자, 실제로는 문제가 없었을 트랜잭션도 가끔 직렬화 실패로 중단된다. 왜 그런가?

답 SSI 는 이상이 실제로 생길지 끝까지 따지지 않고, 생길 수 있는 의존 모양만 보고 중단하기 때문이다.

모든 경우를 정확히 따지는 비용보다 가끔 다시 시도하는 비용이 싸다는 설계다.

순차 스캔처럼 테이블 전체를 읽으면 표시가 테이블 단위로 남아 중단이 더 잦아진다.

이 깊이에서 보이는 항목이 없다. 더 보기를 누르면 이 섹션만 펼친다.
