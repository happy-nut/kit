UNDERSTAND

트랜잭션 격리 수준

격리 수준은 동시에 도는 트랜잭션이 하나씩 차례로 돈 것과 다른 결과를 낼 때, DB 가 그 결과를 허용할지, 기다리게 할지, 중단시킬지를 정하는 설정이다.

스냅샷은 정해진 시점까지 커밋된 데이터의 모습이고, MVCC 는 행의 버전을 여럿 두어 읽기가 스냅샷을 보게 하는 방식이다.

직렬화 가능(serializable)은 동시 실행의 결과가 트랜잭션을 어떤 순서로 하나씩 돌린 결과와 같다는 뜻이다.

같은 등급 이름이라도 막는 현상은 DB 구현이 정한다. PostgreSQL 의 기본은 READ COMMITTED, MySQL InnoDB 의 기본은 REPEATABLE READ 다.

01전체 구조

문제는 한 트랜잭션이 읽은 값으로 판단하고 쓰는 사이에 다른 트랜잭션의 커밋이 끼는 자리에서 생긴다.

격리 수준은 B 의 마지막 쓰기에서 DB 가 덮어쓸지, 중단시킬지를 정한다. 잠금 읽기를 쓰면 B 의 첫 읽기부터 기다리게 할 수도 있다.

02작동 원리

대표 사례

재고 1개에 주문 두 건 (PostgreSQL)

상품 7번의 재고가 1개 남았을 때 주문 A 와 B 가 거의 같은 순간에 들어온다.

주문마다 트랜잭션 하나가 SELECT 로 재고를 읽고, 1 이상이면 앱에서 1 을 뺀 값을 UPDATE 로 써넣고 커밋한다.

  1. 두 트랜잭션이 같은 값을 읽는다

    A 가 재고 1 을 읽고, A 가 커밋하기 전에 B 도 재고 1 을 읽는다.

    둘 다 팔 수 있다고 판단하고 앱에서 써넣을 값 0 을 계산한다.

  2. READ COMMITTED 에서는 나중 쓰기가 덮어쓴다

    A 가 재고를 0 으로 고치고 커밋한다. B 의 UPDATE 는 A 의 행 잠금을 기다렸다가, A 가 커밋하면 갱신된 행에 B 가 계산한 0 을 쓴다.

    두 주문이 모두 성공하고 재고는 0 이다. A 가 1 을 뺀 변경이 B 의 쓰기에 덮여 사라졌고, 이것을 lost update 라 한다.

  3. 원인은 쓰는 순간 낡은 판단 근거다

    B 가 판단에 쓴 재고 1 은 B 가 쓰는 순간 이미 0 이다.

    A 가 끝난 뒤 B 가 시작했다면 B 는 0 을 읽고 거절했다. 그래서 두 주문 성공은 어느 차례 순서로도 나오지 않는 결과다.

  4. REPEATABLE READ 는 낡은 근거의 쓰기를 중단시킨다

    REPEATABLE READ 트랜잭션은 첫 문장에서 잡은 스냅샷을 끝까지 읽는다.

    B 가 자기 스냅샷 뒤에 A 가 고치고 커밋한 행을 쓰려 하면, PostgreSQL 은 「could not serialize access due to concurrent update」 오류(SQLSTATE 40001)로 B 를 롤백한다.

  5. 앱이 처음부터 다시 돌려야 결과가 맞는다

    앱은 40001 을 받으면 B 를 새 트랜잭션으로 SELECT 부터 다시 실행한다.

    새 스냅샷에서 B 는 재고 0 을 읽고 품절로 거절한다. A 다음에 B 가 돈 것과 같은 결과다.

    UPDATE 만 다시 보내면 옛 판단으로 또 쓰므로 읽기부터 다시 한다.

03핵심 관계

비관적·낙관적 동시성 제어

DB 는 충돌하는 쓰기를 잠금으로 기다리게 하거나, 스냅샷으로 진행시킨 뒤 쓰는 순간 검사해 중단시킨다.

작동잠금은 충돌을 미리 가정해 상대를 멈추고, MVCC 스냅샷은 충돌이 없다고 가정해 진행한 뒤 쓰려는 행의 버전을 견준다.

이 모델로 설명되는 현상

  • PostgreSQL REPEATABLE READ 에서 동시 주문은 대기가 아니라 40001 오류로 끝나므로 앱에 재시도 코드가 있어야 한다.
  • SELECT ... FOR UPDATE 로 읽으면 오류는 없지만, 인기 상품 한 행에 주문이 몰리면 뒤 주문은 앞 주문들이 커밋할 때까지 기다린다.
  • MVCC 에서 일반 SELECT 는 옛 버전을 읽으므로 긴 조회가 주문 쓰기를 막지 않고, 쓰기도 조회를 막지 않는다.
  • InnoDB SERIALIZABLE 은 autocommit 이 꺼져 있으면 일반 SELECT 를 공유 잠금 읽기로 바꾸므로 대기와 교착이 는다.

설명하지 못하는 것어느 쪽이 싼지는 충돌 빈도와 트랜잭션 길이로 정해지며, 실제 대기와 재시도 비용은 실제 부하로 재야 알 수 있다.

직렬화 가능성

동시 실행의 결과가 어떤 차례 순서와도 같지 않으면 틀린 것이고, SERIALIZABLE 아래 등급은 이 어긋남 가운데 일부 모양만 막는다.

작동판단 근거가 된 읽기와 그 판단으로 한 쓰기 사이에 다른 트랜잭션의 커밋이 끼면, 각자 맞게 판단해도 합친 결과는 어떤 순서로도 설명되지 않는다.

이 모델로 설명되는 현상

  • lost update 는 두 트랜잭션이 같은 행을 쓴 경우라, PostgreSQL REPEATABLE READ 의 쓰기 충돌 검사가 잡는다.
  • write skew 는 두 트랜잭션이 같은 조건을 읽고 서로 다른 행을 고쳐 함께 지키던 규칙을 깨는 경우다. 겹치는 쓰기가 없어 REPEATABLE READ 는 통과시키고 PostgreSQL SERIALIZABLE 의 SSI 만 잡는다.
  • 「그 시간대 예약이 없음」을 확인하고 넣는 두 트랜잭션은 확인한 행이 아직 없어서 행 잠금으로 막을 수 없다.

설명하지 못하는 것직렬화 가능성은 결과가 어떤 차례 순서와 같다는 것만 보장하고, 어느 주문이 먼저 성공할지는 정하지 않는다.

04적용과 한계

InnoDB 기본 설정에서 쿠폰 잔여 수를 SELECT 로 읽고, 앱에서 1 을 뺀 값을 UPDATE 로 써넣는다.

동시 요청 두 건이 같은 값을 쓰고 쿠폰이 한 장 더 나간다.

InnoDB 의 UPDATE 는 스냅샷이 아니라 최신 커밋 값에 오류 없이 쓰므로, REPEATABLE READ 라는 이름과 달리 lost update 가 생긴다.

PostgreSQL 을 SERIALIZABLE 로 올렸는데 앱에 40001 재시도 코드가 없다.

주문이 몰리면 일부 사용자는 품절 안내가 아니라 오류 화면을 본다.

높은 등급은 틀린 결과를 직렬화 실패로 바꿀 뿐이고, 실패한 트랜잭션을 다시 돌리는 일은 앱이 맡는다.

PostgreSQL READ COMMITTED 에서 회의실 예약 전에 같은 시간대 예약이 없는지 SELECT ... FOR UPDATE 로 확인하고 INSERT 한다.

동시 요청 두 건이 모두 예약된다.

FOR UPDATE 는 찾은 행만 잠그는데 확인 결과가 빈 집합이라 잠글 행이 없으므로, SERIALIZABLE 이나 배타 제약(EXCLUDE)이 있어야 막힌다.

PostgreSQL REPEATABLE READ 로 월말 정산 조회를 몇 분 돌리는 동안 주문이 계속 들어온다.

정산은 시작 시점의 일관된 합계를 내고, 주문 쓰기는 조회를 기다리지 않는다.

MVCC 에서 읽기는 옛 버전을 보고 쓰기는 새 버전을 만들어 서로 막지 않는다.

한 행에 몰린 주문: 중단과 재시도 대 대기

가정 모델: 주문 n 건이 재고가 넉넉한 같은 행을 동시에 고치고, 트랜잭션마다 같은 시간이 걸리며, 40001 로 실패한 주문은 곧바로 함께 다시 시작한다.

동시 주문이 하나면 충돌이 없어 두 방식의 결과와 비용이 같다.

두 방식 모두 이 행의 쓰기를 하나씩 처리하므로 마지막 주문의 완료 시각은 같고, 차이는 RR 이 버리는 실행 수다.

RR 의 실행 수가 주문 수의 세 배를 넘는다. 이 경합에서는 잠금 읽기나 조건부 UPDATE 가 DB 의 일을 덜 쓴다.

PostgreSQL 에서 늦은 주문 B 는 막는 방법마다 어떻게 끝나는가?

B 의 SELECT ... FOR UPDATE 는 A 가 커밋할 때까지 기다린 뒤 재고 0 을 받고, B 는 품절로 거절된다.

READ COMMITTED 의 잠금 읽기는 상대가 커밋하면 갱신된 행을 잠가 돌려주므로 오류 없이 차례로 돈다.

UPDATE ... SET stock = stock - 1 WHERE id = 7 AND stock >= 1 에서 B 는 0 행을 고치고, 앱은 고친 행 수 0 을 보고 거절한다.

READ COMMITTED 의 UPDATE 는 상대 커밋 뒤 갱신된 행으로 WHERE 를 다시 평가하므로 판단과 쓰기가 한 문장에서 일어난다.

B 는 40001 로 롤백되고, 다시 돌면 재고 0 을 읽고 거절된다.

스냅샷 뒤에 남이 고친 행을 쓰려는 트랜잭션을 중단시키고, 다시 읽는 일은 앱의 재시도가 한다.

재고는 맞게 0 이 되지만 B 의 사용자는 품절 안내 대신 오류를 받는다.

DB 는 틀린 쓰기를 막는 데서 멈추고, 실패를 품절 판단으로 바꾸는 것은 앱의 몫이다.

성립 조건

  • 격리 수준은 한 DB 안의 트랜잭션 사이 보장이다. 캐시, 메시지 큐, 외부 결제 호출은 그 밖에 있어서 재시도하면 두 번 일어날 수 있다.
  • InnoDB 의 잠금 읽기는 autocommit 이 꺼져 있을 때(START TRANSACTION 이나 autocommit = 0)만 잠금으로 동작한다.

반례

  • PostgreSQL SERIALIZABLE 은 차례 실행이었다면 나지 않았을 직렬화 실패도 낸다. 순차 스캔은 테이블 단위 술어 잠금을 남겨 실패가 더 잦아진다.

05재사용할 원리

확인 후 실행 경쟁 조건(TOCTOU)

상태를 확인한 시점과 그 확인으로 행동하는 시점 사이에 다른 행위자가 상태를 바꾸면 판단이 틀리므로, 확인을 행동 안에 넣거나 그 구간을 차례로 세운다.

적용 조건여러 행위자가 같은 상태를 읽고 그 판단으로 쓸 때 성립한다.

  • 파일 시스템파일이 없는지 확인하고 만드는 대신 open 의 O_CREAT 와 O_EXCL 을 함께 써서 확인과 생성을 한 호출로 묶는다.
  • HTTP APIIf-Match 헤더에 읽은 ETag 를 실어, 서버의 자원이 그 버전일 때만 덮어쓰게 한다.
  • 코드 머지두 사람이 각자 테스트를 통과한 변경을 동시에 머지하면 충돌 없이 main 이 깨질 수 있고, 머지 큐는 합친 결과로 하나씩 다시 시험해 차례를 세운다.

충돌 빈도로 낙관과 비관 고르기

충돌이 드물면 먼저 진행하고 끝에 검사하는 쪽이 싸고, 충돌이 잦으면 먼저 잠그는 쪽이 싸다.

적용 조건실패한 작업을 다시 해도 결과가 같을 때 낙관적 방식을 쓸 수 있고, 다시 할 수 없는 작업은 먼저 잠근다.

  • 문서 편집위키는 편집 충돌이 드물어 저장할 때 버전을 견주고, 겹치면 사용자에게 다시 고치게 한다.
  • 좌석 예매공연 예매는 한 좌석에 사람이 몰려 고르는 순간 좌석을 일정 시간 잡아 둔다.
