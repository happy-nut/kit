UNDERSTAND

트랜잭션 격리 수준

격리 수준은 동시에 도는 트랜잭션이 하나씩 차례로 돈 것과 다른 결과를 낼 때, DB 가 그 결과를 허용할지, 기다리게 할지, 중단시킬지를 정하는 설정이다.

01작동 원리

  1. A 가 재고를 읽고 판단한다

    PostgreSQL 에서 상품 7번의 재고가 10개일 때 주문 A 와 B 가 거의 같은 순간에 들어온다.

    주문마다 트랜잭션 하나가 SELECT 로 재고를 읽고, 앱에서 1 을 뺀 값을 UPDATE 로 써넣고 커밋한다.

    A 는 재고 10 을 읽고 써넣을 값 9 를 계산한다.

  2. B 도 같은 값을 읽는다

    A 가 커밋하기 전에 B 도 재고 10 을 읽고 9 를 계산한다.

    PostgreSQL 은 행의 버전을 여럿 두는 MVCC 를 쓴다. 읽기는 커밋된 버전을 보고 다른 트랜잭션의 쓰기를 기다리지 않는다.

  3. A 가 쓰고 커밋한다

    A 가 재고를 9 로 고치고 커밋한다. 여기까지 판매 1개, 재고 9 로 장부가 맞다.

    이 순간 B 가 판단에 쓴 재고 10 은 낡은 값이 된다.

  4. B 가 낡은 판단으로 쓴다

    B 는 자기가 읽은 10 으로 계산한 9 를 UPDATE 로 보낸다.

    A 가 끝난 뒤 B 가 시작했다면 B 는 9 를 읽고 8 을 썼다. 이 쓰기를 받아들일지, 막을지를 격리 수준이 정한다.

  5. READ COMMITTED 면 덮어쓴다

    READ COMMITTED 는 PostgreSQL 의 기본 격리 수준이다. 문장마다 그 순간까지 커밋된 값을 보고, B 의 UPDATE 는 A 가 커밋한 행에 9 를 그대로 쓴다.

    두 주문이 모두 성공했는데 재고는 9 다. A 가 뺀 1 이 B 의 쓰기에 덮여 사라졌고, 이것을 lost update 라 한다.

  6. REPEATABLE READ 면 40001 로 중단된다

    REPEATABLE READ 트랜잭션은 첫 문장에서 잡은 스냅샷을 끝까지 본다. 스냅샷은 그 시점까지 커밋된 데이터의 모습이다.

    B 가 자기 스냅샷 뒤에 A 가 고치고 커밋한 행을 쓰려 하면, PostgreSQL 은 직렬화 실패 오류(SQLSTATE 40001)로 B 를 롤백한다.

    재고는 9 로 맞지만 B 의 주문은 아직 처리되지 않았다.

  7. 앱이 읽기부터 다시 돌린다

    앱은 40001 을 받으면 B 를 새 트랜잭션으로 SELECT 부터 다시 돌린다. B 는 새 스냅샷에서 9 를 읽고 8 을 쓴다.

    A 다음 B 가 돈 것과 같은 결과다. 동시 실행의 결과가 이렇게 어떤 차례 실행과 같으면 직렬화 가능하다고 한다. UPDATE 만 다시 보내면 옛 판단의 9 를 또 쓴다.

    같은 행에 주문 2건이 동시에 오면 회차마다 하나만 커밋하고 나머지는 다시 돈다. 실행은 모두 3회이고, 그 가운데 1회가 40001 로 버려진다.

    동시 주문이 하나면 충돌이 없어 40001 도, 재시도도 생기지 않는다.

  8. 잠금 읽기는 중단 대신 기다리게 한다

    READ COMMITTED 에서 SELECT ... FOR UPDATE 로 읽으면 B 의 읽기가 A 의 커밋까지 기다렸다가 9 를 받는다. 버려지는 실행이 없어 실행은 주문 수와 같은 2회다.

    트랜잭션 하나가 20ms 걸리면 두 방식 모두 이 행의 쓰기를 하나씩 처리해, 마지막 주문은 40ms 에 끝난다. 차이는 REPEATABLE READ 가 버리는 실행 1회다.

    REPEATABLE READ 의 실행 수가 주문 수의 세 배를 넘는다. 이 경합에서는 잠금 읽기나 조건부 UPDATE 가 DB 의 일을 덜 쓴다.

가정 모델: 재고가 넉넉한 한 행을 주문 n 건이 동시에 고치고, 트랜잭션마다 같은 시간이 걸리며, 40001 로 실패한 주문은 곧바로 함께 다시 시작한다.

02핵심 관계

비관적·낙관적 동시성 제어

DB 는 충돌하는 쓰기를 잠금으로 기다리게 하거나, 스냅샷으로 진행시킨 뒤 쓰는 순간 검사해 중단시킨다. 잠금은 충돌을 미리 가정해 상대를 멈추고, 스냅샷 방식은 충돌이 없다고 가정해 진행한 뒤 쓰려는 행이 스냅샷 뒤에 바뀌었는지 견준다.

REPEATABLE READ 의 B 가 기다리지 않고 40001 로 끝난 것은 낙관적 방식이라서이고, 그래서 이 방식을 쓰는 앱에는 재시도 코드가 있어야 한다. FOR UPDATE 의 B 가 오류 없이 기다린 것은 비관적 방식이라서이고, 인기 상품 한 행에 주문이 몰리면 뒤 주문이 앞 주문들의 커밋을 차례로 기다린다. B 의 첫 SELECT 가 A 를 기다리지 않은 것처럼, MVCC 에서는 긴 조회와 주문 쓰기가 서로를 막지 않는다.

어느 쪽이 싼지는 충돌 빈도와 트랜잭션 길이로 정해지며, 실제 대기와 재시도 비용은 실제 부하로 재야 알 수 있다.

직렬화 가능성

동시 실행의 결과가 어떤 차례 순서와도 같지 않으면 틀린 것이고, SERIALIZABLE 아래 등급은 이 어긋남 가운데 일부 모양만 막는다. 판단 근거가 된 읽기와 그 판단으로 한 쓰기 사이에 다른 트랜잭션의 커밋이 끼면, 각자 맞게 판단해도 합친 결과는 어떤 순서로도 설명되지 않는다.

READ COMMITTED 의 결과인 주문 둘, 재고 9 는 A 다음 B 로도, B 다음 A 로도 나오지 않으므로 틀린 결과다. lost update 는 두 트랜잭션이 같은 행을 쓴 경우라, PostgreSQL REPEATABLE READ 의 쓰기 충돌 검사가 잡는다. write skew 는 두 트랜잭션이 같은 조건을 읽고 서로 다른 행을 고쳐 함께 지키던 규칙을 깨는 경우다. 겹치는 쓰기가 없어 REPEATABLE READ 는 통과시키고 PostgreSQL SERIALIZABLE 만 잡는다.

직렬화 가능성은 결과가 어떤 차례 순서와 같다는 것만 보장하고, 어느 주문이 먼저 성공할지는 정하지 않는다.

03적용과 한계

PostgreSQL 을 SERIALIZABLE 로 올렸는데 앱에 40001 재시도 코드가 없다.

주문이 몰리면 일부 사용자는 주문 완료나 품절 안내가 아니라 오류 화면을 본다.

높은 등급은 틀린 결과를 직렬화 실패로 바꿀 뿐이고, 실패한 트랜잭션을 다시 돌리는 일은 앱이 맡는다.

PostgreSQL READ COMMITTED 에서 회의실 예약 전에 같은 시간대 예약이 없는지 SELECT ... FOR UPDATE 로 확인하고 INSERT 한다.

동시 요청 두 건이 모두 예약된다.

FOR UPDATE 는 찾은 행만 잠그는데 확인 결과가 빈 집합이라 잠글 행이 없으므로, SERIALIZABLE 이나 배타 제약(EXCLUDE)이 있어야 막힌다.

PostgreSQL REPEATABLE READ 로 월말 정산 조회를 몇 분 돌리는 동안 주문이 계속 들어온다.

정산은 시작 시점의 일관된 합계를 내고, 주문 쓰기는 조회를 기다리지 않는다.

정산은 읽기만 하므로 쓰기 충돌 검사에 걸리지 않고, 첫 문장의 스냅샷을 끝까지 본다.

같은 두 주문을 다른 DB 설정이나 쓰기 방식으로 돌리면 B 는 어떻게 끝나는가?

B 는 REPEATABLE READ 때와 같이 40001 로 롤백되고, 재시도하면 9 를 읽고 8 을 쓴다.

SERIALIZABLE 은 REPEATABLE READ 의 쓰기 충돌 검사에 읽기와 쓰기의 의존을 보는 SSI 검사를 더한 것이라, 같은 행 충돌은 같은 방식으로 잡힌다.

B 의 UPDATE 가 오류 없이 9 를 써서, 두 주문이 성공하고 재고는 9 로 남는다.

InnoDB 의 일반 SELECT 는 스냅샷을 읽지만 UPDATE 는 최신 커밋 행에 오류 없이 쓰므로, 이름이 같아도 lost update 를 막지 않는다.

두 SELECT 가 공유 잠금을 잡아 서로의 UPDATE 를 막는 교착이 생기고, InnoDB 가 한쪽을 롤백한다.

autocommit 이 꺼져 있으면 InnoDB SERIALIZABLE 은 일반 SELECT 를 공유 잠금 읽기로 바꾼다. 롤백된 쪽을 다시 돌리는 일은 여기서도 앱이 한다.

UPDATE ... SET stock = stock - 1 WHERE id = 7 AND stock >= 1 에서 B 는 A 가 커밋한 9 에서 1 을 빼 8 을 쓴다. 재고가 0 이면 0 행을 고치고 앱이 품절로 거절한다.

READ COMMITTED 의 UPDATE 는 상대 커밋 뒤 갱신된 행으로 식과 WHERE 를 다시 평가하므로 판단과 쓰기가 한 문장에서 일어난다.

성립 조건

  • 격리 수준은 한 DB 안의 트랜잭션 사이 보장이다. 캐시, 메시지 큐, 외부 결제 호출은 그 밖에 있어서 재시도하면 두 번 일어날 수 있다.
  • InnoDB 의 잠금 읽기와 SERIALIZABLE 의 공유 잠금 읽기 변환은 autocommit 이 꺼져 있을 때(START TRANSACTION 이나 autocommit = 0)만 일어난다.

반례

  • PostgreSQL SERIALIZABLE 은 차례 실행이었다면 나지 않았을 직렬화 실패도 낸다. 순차 스캔은 테이블 단위 술어 잠금을 남겨 실패가 더 잦아진다.
  • InnoDB REPEATABLE READ 의 일반 SELECT 는 스냅샷을 보지만, 같은 트랜잭션이 그 행을 UPDATE 한 뒤에는 남이 커밋한 최신 값이 보인다.
