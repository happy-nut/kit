# Verify setup

제대로 된 프로젝트에는 실제 앱을 몰아 동작을 증명하는 스크립트된 길이 있어야 한다. 앱을 띄우고, 기능을 사용자처럼 써 보고, 증거를 남긴다. 이 스킬은 그 길을 저장소에 맞춘 프로젝트 전용 스킬 `<저장소>/.claude/skills/verify-<앱>/` 으로 만들고(「만들기」), 앱이 바뀌면 그 스킬이 사실을 말하게 다시 맞춘다(「유지」).

만드는 글은 사람이 아니라 다음 에이전트가 읽는다. 앱을 한 번도 본 적 없는 에이전트가 일하는 도중에 아무 맥락 없이 읽는다. Claude Code 의 `run` 스킬은 앱을 띄우는 프로젝트 스킬을 먼저 찾으므로, 여기서 만든 스킬이 그 자리를 채운다.

「됐다」는 눈으로 본 결과다. 이 스킬이 만드는 검증은 화면이 있으면 기능마다 스크린샷을 남기고, 백엔드 값만이 아니라 화면에 보이는 값까지 확인한다. 저장소의 `AGENTS.md`·`CLAUDE.md` 가 이 스킬보다 앞선다. 거기 적힌 검증 명령(예: `npm run build:local`)과 금지(예: 워크트리에서 백엔드 서버 띄우기 금지)를 먼저 읽고 따른다.

어느 절을 할지: `.claude/skills/verify-*/` 가 없으면 「만들기」, 있으면 「유지」.

# 만들기

## 1. 사용자가 아니라 저장소에 묻는다

아래를 코드베이스에서 답하고, 볼 수 없는 것만 사용자에게 묻는다.

- **표면.** 사용자가 실제로 만지는 것은? 웹 UI, CLI·TUI, 데스크톱 앱, API, 모바일 앱, 라이브러리? 저장소에 여럿이 있을 수 있다. 주된 것 하나를 고르고 나머지는 적어 둔다. 사용자가 만지는 것이 정말 없으면(설정, 문서, 플러그인 저장소) 만들지 말고 `.verify/NONE` 에 그 이유 한 줄을 적어 커밋한다. 세션 시작 훅은 `.verify/run.sh` 도 `.verify/NONE` 도 없는 저장소에서 이 스킬을 먼저 돌리라고 안내한다.
- **실행.** 로컬에서 앱이 어떻게 뜨나? 저장소가 문서로 적은 개발 명령(패키지 스크립트, Makefile, README 빠른 시작)을 먼저 쓴다. 포트, 환경 변수, 시드 데이터, 인증을 적는다.
- **몰기.** 에이전트가 코드로 어떻게 다루나? 이 표면을 실제 사용자처럼 몰고 그 결과를 사용자가 보는 그대로 관찰할 수 있는 방법을 먼저 정한다. 웹과 Electron 은 브라우저 도구(playwright MCP, Claude in Chrome, 내장 브라우저)나 CDP, CLI·TUI 는 tmux·PTY, 서비스는 평범한 HTTP, iOS 앱은 시뮬레이터 도구. 이미 있는 장치(Playwright·Cypress 스펙, expect 스크립트, PTY 도우미, curl 로 부를 수 있는 엔드포인트, 디버그 포트)는 그 방법을 실제로 충족하는지 보고서야 쓴다. 있다는 이유로 기준에 못 미치는 장치를 쓰지 않는다. 백엔드를 mock 하거나, 내부 엔드포인트만 찌르거나, 사용자가 보는 화면과 다른 것을 확인하는 장치는 손이 덜 가도 버리고 더 맞는 방법을 쓴다(principles.md 의 Prove It Works).
- **관찰.** 무엇을 증거로 잡을 수 있나? 스크린샷, 터미널 기록, 응답 본문, 로그, 종료 코드, DB 상태.
- **격리.** 두 인스턴스가 나란히 돌 수 있나(포트, 데이터 폴더, 프로필)? 안 되면 만들 스킬에 그렇게 적는다. 공유 인스턴스를 둘이 몰아 사용자 세션을 망가뜨리느니 거부하는 게 낫다.
- **어디서 도나.** 검증은 사용자의 화면과 입력을 쓰지 않는다. 사람이 맥을 쓰는 동안 창이 뜨거나 포커스를 뺏으면 안 된다. 리눅스 컨테이너의 가상 화면(Xvfb)에서 앱을 띄울 수 있는지 본다. 웹·Electron·CLI·서비스는 대개 된다. macOS·iOS 에만 있는 동작(⌥ 조합의 OS 처리, 맥 메뉴, 입력기, 시뮬레이터)은 컨테이너가 못 덮는다. 그런 기능은 기능 지도의 `Gotchas` 에 「macOS 전용」으로 적는다.

체크아웃이 그대로 빌드되거나 뜨지 않으면 만들기 전에 먼저 고치거나 정확히 보고한다. 망가진 바탕 위에 쓴 스킬은 틀린 단계를 가르친다. 상관없는 자원이 없어서 시작이 막히면(API 가 쓰지도 않는 정적 폴더, 예시 설정) 만들 스킬이 그것을 만들어도 된다. 검증용 임시물이라고 분명히 표시하고 정리 단계에서 지운다.

## 2. 스킬을 만든다

`<저장소>/.claude/skills/verify-<앱>/SKILL.md` 를 쓴다. YAML frontmatter 에 `name: verify-<앱>` 과 앱·표면·언제 쓰는지를 담은 `description` 을 넣는다. frontmatter 가 없으면 스킬이 등록되지 않는다. 아래 절을 모두 넣고, 각 절은 1단계에서 실제로 찾은 것으로 채운다. 자리표시가 남으면 안 되고, 「이 스킬은 verify-setup 으로 작성됐다」처럼 다음 에이전트의 판단에 안 쓰이는 자기소개 문장도 넣지 않는다.

- **Launch.** 검증용으로 앱을 띄우는 정확한 명령과 준비됐다고 아는 법(로그 한 줄, 프롬프트). 빈 데이터 폴더에서 마이그레이션과 시드 데이터까지 거쳐 쓸 수 있는 상태에 닿아야 한다. 준비는 프로세스가 응답한다는 뜻이 아니라 쓸 수 있다는 뜻이다. DB 헬스 체크는 초기화 스크립트가 아직 도는 중에도 통과할 수 있다. 내리는 법도 넣는다. 짧게 끝나는 CLI·TUI 는 살려 둘 서버가 없다. 이때 Launch 는 바이너리를 한 번 빌드(또는 의존성 설치)하고, 몰 때마다 따로 격리된 PTY 나 tmux 세션에서 시작하는 것이다.
- **Doctor.** 「이 인스턴스를 몰 만한가」에 답하는 읽기 전용 확인 하나. 프로세스가 떠 있나, 맞는 버전·빌드인가, 포트가 우리 것인가, 인증이 유효한가. 뭔가 이상해 보이면 에이전트가 이것부터 돌린다.
- **Drive.** 예시가 아니라 이 저장소의 실제 선택자·명령으로 쓴 몰기 방법. 좌표나 탭 순서보다 안정된 손잡이(ARIA 라벨, data 속성, 프롬프트 문자열, 라우트 경로)를 쓴다.
- **Evidence.** 증명에 무엇을 잡고 어디에 두나. 증명 기준을 적는다. 내부 setter 나 시험용 엔드포인트가 아니라 실제 사용자 경로를 거친다. 마지막 화면만이 아니라 행동과 그 결과 상태를 잡는다. 보이는 것과 함께 부작용(쓴 파일, 넣은 행, 보낸 메시지)을 확인한다. mock 은 운영 경계가 이미 외부 시스템을 떼어 놓은 자리에서만 쓴다. 안전한 길이 dry-run 이나 시험 모드면 이름을 믿지 말고 실제로 무엇을 건너뛰는지 관찰(파일, 네트워크, git ref)로 확인한다. 어떤 dry-run 은 네트워크를 건드리거나 브라우저를 연다. 화면이 있는 앱이면 기능마다 스크린샷을 한 장씩 남긴다.
- **Cleanup.** 실행이 만든 인스턴스를 내리는 법. 프로세스 이름으로 죽이지 않는다. 내가 띄운 것만 죽인다(띄울 때 PID 나 tmux 세션 이름을 적어 둔다). 정리는 인스턴스와 임시 상태를 지우지 증거는 지우지 않는다. 증명 산출물은 정리 뒤에도 스킬이 정한 자리에 남는다. 그 자리는 git 밖(`.git/info/exclude` 에 적은 폴더나 임시 폴더)이다.
- **Isolated run.** 사람의 화면 밖에서 에이전트가 기능 지도를 사용자처럼 도는 길. [`references/isolated/`](references/isolated/) 를 저장소에 옮긴다. `Dockerfile`, `run.sh`, `walk.sh`, `walk-prompt.md` 는 `<저장소>/.verify/` 에, `dockerignore` 는 `<저장소>/.dockerignore` 에, `verify.yml` 은 `.github/workflows/verify.yml` 에 둔다. 저장소에 맞게 세 곳만 고친다. `Dockerfile` 의 도구 사슬(언어 런타임, 시스템 라이브러리), `VERIFY_PREPARE`(의존성 설치와 빌드 명령), `verify.yml` 의 `VERIFY_SKILL_NAME`. 로컬은 `VERIFY_SKILL=.claude/skills/verify-<앱> sh .verify/run.sh diff` 로 돌고, colima·OrbStack·Docker Desktop 가운데 하나의 데몬이 필요하다. CI 는 PR 마다 diff 가 닿는 기능을, 매일 밤 전체를 돌고, 판정 표를 PR 코멘트로, 스크린샷을 아티팩트로 남긴다. 에이전트 인증은 `ANTHROPIC_API_KEY` 나 `CLAUDE_CODE_OAUTH_TOKEN`(`claude setup-token`) 저장소 시크릿이고, 사람이 넣는다. 스킬의 Launch·Drive 는 이 컨테이너 안에서도 그대로 돌아야 한다. Chromium·Electron 은 `--shm-size` 가 작으면 글꼴을 싣다 죽으므로 `run.sh` 가 2g 를 준다.
- **Helpers.** 스킬이 딸고 가는 스크립트는 실행 권한이 있고, 부르는 법이 스킬 본문에 보인다. 읽는 사람이 거꾸로 풀어야 하는 도우미는 도우미가 아니다.

## 3. 기능 지도를 심는다

`<저장소>/.claude/skills/verify-<앱>/features/README.md` 와, 찾을 수 있는 사용자 기능마다 파일 하나를 만든다. 처음에는 라우트, 명령, 메뉴, 문서에서 위에서부터 3~5개를 목표로 한다. 모양은 [`references/feature-map-example/`](references/feature-map-example/) 을 따른다. README 색인과 기능마다 파일 하나다. 각 파일은 사용자 눈으로 답한다. 그 기능이 무엇이고, 어떻게 닿고, 장치로 어떻게 몰고, 어떤 관찰 가능한 끝 상태가 동작을 증명하나. H2 넷은 `Sub-features`, `How to get to it (user POV)`, `Driving it with <장치>`, `Gotchas` 다. 시드 데이터에 어떤 여정의 전제가 없으면 그 여정은 실패로 보고하고 이유를 그 기능의 `Gotchas` 에 적는다. 통과시키려고 여정을 약하게 만들지 않는다. 기능 파일의 H1 은 `# <ID> - <영어 이름>` 이나 `# <영어 이름>`, 그 아래 첫 문장은 한국어 설명이다. `Sub-features` 글머리는 `` - `<ID>` **<영어 이름>**: <한국어 설명> `` 이다. 이 이름이 사람과 에이전트가 기능을 부르는 말이다. 하위 기능 글머리에 그 하위 기능을 부르는 키·플래그·라우트를 코드에 적힌 글자 그대로 쓴다. `/dev:featuremap` 이 코드에서 뽑은 진입점에 이 글자로 검증 판정을 덧칠한다. 지도는 저장소가 관리하는 검증 정본이다. 지도가 여러 진입점을 적었는데 편한 하나만 몬 증명은 덜 끝난 것이다.

## 4. 넘기기 전에 만든 스킬을 증명한다

만든 스킬의 지시를 처음부터 끝까지 한 번 돌린다. Launch, Doctor, 지도의 기능 하나 몰기(하나면 된다. 나머지는 지도가 있으니 뒤 실행이 덮는다), 증거 잡기, 정리. 이 순서를 Isolated run 의 컨테이너 안에서도 한 번 돌려, 스크린샷이 나오고 그동안 사람의 화면에 창이 뜨지 않는 것을 확인한다. 인증 시크릿이 없어 에이전트 순회를 못 돌렸으면 그렇게 보고한다. 정리 뒤에도 증거가 정한 자리에 남아 있는지 확인한다. 정리가 증거를 먹으면 이 단계는 실패다. 실패한 것을 고친다. 실패한 반복마다 만든 정리 단계도 돌려서 망가진 시도가 프로세스와 포트를 남기지 않게 한다. 한 번도 돌려 보지 않은 스킬은 초안이지 결과물이 아니다. 실제 대상 대신 비슷한 것(새 VM 대신 컨테이너, 원격 스택 대신 로컬 스택)에서 증명했으면, 그 대용물이 해 줬지만 실제 대상은 해 주지 않을 준비 단계를 모두 적는다. 실제 대상에서 돌릴 때까지 그 단계는 검증되지 않은 것이다.

증명에서 찍은 스크린샷과 출력은 보고에 붙인다.

## 5. 커밋하고 유지를 알린다

만든 스킬을 커밋하고 PR 을 연다. 사용자에게 앱이 바뀌면 `/dev:verify-setup` 을 다시 부르면 「유지」로 지도를 맞춘다고 한 줄 알린다. 주기는 사용자가 물을 때만 제안한다.

## 6. 더 깊은 층은 필요할 때 제안한다

몰아 보기로 못 잡는 버그가 있다. 만든 스킬의 끝에, 해당하면 한 번씩 제안한다. 설치는 필요가 확인된 뒤에만.

- **여러 기기·플랫폼에 걸친 흐름, 동시성, 상태 기계** (알림, 동기화, 재시도): TLA+ 로 모델 검사. 주요 사용자 흐름을 상태 기계로 적고 불변식(중복 없음, 결국 도착)을 검사한다.
- **알고리즘의 성질** (가상화 목록이 깜빡이지 않음, 정렬·병합이 순서를 지킴): Lean 같은 증명 도구로 핵심 함수의 성질을 증명한다.
- **웹 UI 를 무작위로 탐색하며 성질 확인**: Bombadil(Antithesis, 웹 UI 속성 기반 테스트, TypeScript 스펙). 「화면에 보이는 숫자와 상태가 늘 맞다」 같은 성질을 적어 두면 사람이 생각 못 한 순서로 눌러 본다. 초기 위반 상당수는 스펙 오류라 먼저 스펙을 의심한다.

형식 검증도 은탄환이 아니다. 피라미드의 한 층이다. 필요가 확인되면 `/dev:formal-setup` 으로 그 영역의 형식 검증 스킬을 만든다.

# 유지

기능 지도는 앱이 바뀌는 순간 낡는다. 이 절은 「만들기」로 만든 스킬(또는 기능 지도가 있는 프로젝트 검증 스킬)을 사실대로 유지한다. 엄밀함의 단위는 문장이 아니라 기능이다. 모든 기능 파일을 소스로 덮고 모든 기능을 실제로 몰아 보되, 모든 글머리를 하나하나 끝까지 확인하지는 않는다.

## 결과

셋 중 하나를 고르고 무엇인지 말한다.

- **clean.** 모든 기능이 소스와 실제 몰기로 덮였고 고칠 것이 없다. 브랜치도 PR 도 없다.
- **changed.** 증명된 문서·장치·지도 수정을 PR 하나로 낸다.
- **blocked.** 덮기를 끝내지 못했거나 증명된 수정을 안전하게 내지 못했다. 무엇이 막았는지 정확히 말한다.

## 고칠 수 있는 범위

검증 스킬 자기 폴더(SKILL.md, `features/`, 그 스킬이 가진 장치 스크립트)만 고친다. 실행 중에 제품 코드를 고치지 않는다. 지도가 적었는데 앱이 더는 하지 않는 동작은 문서가 낡은 것(지도를 고친다)이거나 제품 회귀(보고한다. 문서로 덮지 않는다)다.

## 순서

0. **대상 찾기.** 맞출 검증 스킬을 찾는다. Launch·Drive 절과 기능 지도가 있는 프로젝트 스킬이다(보통 `.claude/skills/verify-*/`). 후보가 여럿이면 최근 커밋에서 바뀐 앱에 해당하는 것을 고르고 이유를 보고한다. 갈 수 없으면 `AskUserQuestion` 으로 하나만 묻는다. 없으면 대상을 지어내지 말고 「만들기」로 간다.
1. **색인 정리.** 기능 지도 README 를 읽고 옆 파일들을 glob 한다. 빠진 것, 남는 것, 겹치는 것, 죽은 항목을 고친다. 가볍게 한다. 생성된 목록을 만들지 않는다.
2. **소스 물결.** 기능 파일마다 `Agent` 하나(`subagent_type: "Explore"`, `model: "sonnet"`)를 한 메시지로 동시에 띄운다. 브리프에 「앱을 몰지 마라. 파일을 고치지 마라」를 적는다. 각자 「이 사용자 기능은 어떻게 동작하나」를 소스로 설명하고, 문서가 낡았을 곳을 인용과 함께 짚고, 실제 검증 방법 하나를 짧게 돌려준다. 돌려줄 모양: 기능 요약 / 소스 진입점 / 낡았을 곳 또는 없음 / 방법 하나.
3. **맞추기.** 모든 기능 파일에 돌아온 요약이 있는지 본다. 겹치는 방법을 합쳐 앱 상태를 되도록 적게 쓴다. 인용된 낡은 곳은 몇 개 골라 확인한다. 깨끗하다는 주장은 다시 증명하지 않는다. 최근 변경(`git log --since`)에서 지도에 없는 사용자 표면을 찾는다. 빠졌다고 하려면 구체 소스 경로가 있어야 한다.
4. **실제 몰기.** 소스가 깨끗해 보여도 반드시 한다. 몰기는 모두 내가 한다. Isolated run 이 있으면 그 컨테이너 안에서 몬다. 검증 스킬의 Launch 방식을 따른다. 서버와 UI 는 오래 사는 인스턴스 하나를 차례로 몰고, 짧은 CLI 는 몰 때마다 새 격리 세션을 쓴다. 이 스킬이 아니라 그 스킬의 Launch 절이 정한다. 모든 기능을 적어도 한 번 몬다. 어떤 실패가 나도 세 가지를 끝까지 지킨다.
   1. 마지막으로 이상한 일을 한 뒤 상태를 확인하지 않은 인스턴스는 몰지 않는다. 첫 몰기 전에 Doctor, 세션이 단위면 새 세션마다 Doctor, 실패한 몰기 뒤에 다시 Doctor. Doctor 가 못 보는 실패(프로세스는 멀쩡한데 UI 가 굳은 상태)면 바라지 말고 알려진 상태로 되돌리거나 다시 띄운다.
   2. 지금까지 잡은 증거는 모든 정리 뒤에도 남는다. 짐작하지 말고 정한 자리에서 확인한다.
   3. 몰기가 시작한 것은 그 몰기가 쓸모를 다하면 남지 않는다. 실패한 반복의 찌꺼기는 세션이 굳었든, 끝났든, 공유든 치운다. 공유 인스턴스면 인스턴스가 아니라 찌꺼기를 치운다.
   스킬이 낡아서 Doctor 가 실패하면 그것도 낡은 것이다. 고칠 수 있는 범위 안에서 고치고 한 번 다시 해 본다. 그 수정이 무효로 만든 것만 다시 띄운다. 그래도 안 되면 `blocked`. 닿을 수 없는 기능은 구체 전제(인증, 권한, OS, 외부 상태)와 시도한 경로가 있을 때만 `verified-unreachable` 이다. 지도에 그 전제가 없으면 그것도 낡은 것이다. 분류 중에 고친 장치는 내보내기 전에 다시 실제로 몬다. 마지막 정리는 다시 증명한 것까지 포함해 실행의 마지막 몰기 뒤에 한다. 그래야 실행보다 오래 사는 것이 없다(증거는 스킬 규칙대로 남는다).
5. **분류.** 사용자 눈의 설명이 틀렸거나 빠졌다: 문서 낡음, 고친다. 동작은 되는데 장치가 못 몬다: 장치 빈틈, 고친다. 장치 수정은 만들기의 Helpers 규칙(실행 권한, 본문에 부르는 법)을 따른다. 앱 동작이 정말 망가졌다: 제품 빈틈. 사용자에게 보고하고 그 저장소에 이슈로 남긴다. 이 PR 에는 넣지 않는다.
6. **내보내거나 멈추기.** changed 면 증명된 수정을 PR 하나로 내고, 내기 전에 바뀐 파일을 모두 다시 읽는다. clean 이나 blocked 면 PR 없이 결과와 덮은 범위를 정직하게 보고한다. 몬 기능마다 스크린샷이나 출력을 한 장씩 붙인다.

실행 메모(덮은 기능, 닿을 수 없는 전제, 확인된 낡은 곳, 결과)는 짧게 임시 자리에 둔다. 커밋하지 않는다.
